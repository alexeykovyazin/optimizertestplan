# План: набор тестов для оценки оптимизатора Firebird

*Версия 2.1, 14 октября 2026 — добавлен статус реализации: §2, §3.1, §3.2, §4.1, §12 и Приложение B. Изменения v1 → v2 — в Приложении A.*

## 1. Цель и принципы

**Цель.** Количественно оценивать каждое изменение оптимизатора: что стало лучше, что хуже и нет ли регрессий. Режимов два: быстрый прогон на каждый коммит (≤ 30 мин) и тщательный (ночной, еженедельный, релизный).

**Принципы**

1. **Сортировка вместо «маленького бенчмарка».** Компиляция и разбор планов по корпусу занимают минуты. Исполняются только запросы с изменившимся планом плюс фиксированный контрольный набор.
2. **Эталон главной ветки хранится, а не пересчитывается.** Планы, оценки и логические счётчики детерминированы при одинаковых файле БД и конфигурации. Их снимает ночной прогон главной ветки, а быстрый контур запускает **только сборку-кандидата**. Живое A/B (база и кандидат вперемешку на одной машине) нужно только для времени и только для подозрительных запросов.
3. **Логические счётчики — сигнал, время — решение.** Счётчики (page fetches, record reads) почти не шумят, но не видят CPU-работу: hash join, сортировки, агрегации в памяти. Если план не изменился, счётчиков достаточно. Если изменился, окончательное решение принимается по времени с подтверждением.
4. **Истина считается один раз.** Истинные кардинальности зависят только от данных.
5. **Храповик.** Каждая найденная регрессия становится постоянным тестом.
6. **Время подготовки (prepare) — отдельная метрика.** Улучшения перебора легко раздувают его на запросах с 10+ таблицами.
7. **Нет ложного PASS.** Если контур не успел проверить всё, что должен был, его статус — `INCOMPLETE`, а не `PASS`.

**Почему нельзя взять просто маленький набор.** В статье STATS-CEB полный прогон 146 запросов на PostgreSQL занял ≈ 11,3 ч, а JOB-light (70 запросов) — ≈ 3,7 ч. При этом «лёгкая» часть STATS-CEB выполнилась меньше чем за минуту, а почти всё время пришлось на несколько тяжёлых запросов. Отсюда правило: каждый набор один раз прогоняется целиком и размечается на `fast` / `heavy` по эталонному времени.

**Конфигурация индексов — явное измерение.** Для каждой БД фиксируется DDL минимум в двух вариантах: `pk` и `pk_fk`. Результаты сравниваются только внутри одной конфигурации.

### 4.2 Золотые копии и эталоны

- **Создание.** Загрузка → `SET STATISTICS INDEX` по всем индексам → проверка → `gbak` в архив (для пересоздания) → **файл БД** становится золотой копией.
- **Прогоны идут на побайтовой копии одного и того же файла, а не на результате gbak-restore.** Restore может по-другому разместить страницы (особенно в другой сборке), и тогда page fetches изменятся без всякой связи с оптимизатором. Файл копируется только при остановленном сервере или через nbackup.
- **Read-only** (`gfix -mode read_only`): нет сборки мусора и sweep, а файл можно не копировать перед каждым прогоном.
- **Ключ эталона:** `(сборка главной ветки, SHA-256 файла БД, ODS, хеш конфигурации, index_config)`. Эталон с другим ключом не используется для сравнения счётчиков.
- **Смена ODS** (возможна в ветке FB 6): золотые копии пересоздаются из gbak-архивов, эталоны снимаются заново, а сравнение через смену ODS идёт только по времени (живое A/B невозможно, если старая сборка не открывает новый файл, — тогда сравнивается кандидат с последним эталоном до смены ODS и это явно помечается в отчёте).
- **Режим «кандидат пересобирает статистику».** Золотая копия фиксирует статистику базовой сборки. Если изменение затрагивает сбор или формат статистики, нужен отдельный режим: копия с правом записи, `SET STATISTICS` кандидатом, затем прогон. Это отдельный тип запуска, а не быстрый контур.

### 4.3 Структура репозитория

```
bench/
  datasets/<db>/
    ddl_pk.sql
    ddl_pk_fk.sql
    load/                      # скрипты загрузки
    README.md                  # источник, версия, лицензия, контрольные суммы
  queries/<suite>/
    original/<id>.sql          # оригинал, без изменений
    <id>.sql                   # порт под Firebird
  manifest/<suite>.yaml        # статические метаданные (4.4); меняются только руками
  config/
    firebird.conf / databases.conf     # для всех прогонов
    optimizer_matrix.yaml              # измерения конфигурации оптимизатора (раздел 7)
  truth/<suite>/subplans.parquet       # истинные кардинальности подпланов
  harness/                     # collector, runner, truth, compare, report
  regressions/                 # храповик
  accepted/                    # принятые регрессии: обоснование + срок действия
results/                       # вне git или в отдельном хранилище
  calibration/<key>.parquet    # baseline_ms, fast/heavy, бюджет компиляции
  baselines/<key>/<suite>.parquet   # планы, оценки, счётчики главной ветки
  runs/<run_id>/...
```

Динамические данные (`baseline_ms`, `fast` / `heavy`) хранятся в `results/calibration`, а не в манифесте. Иначе ночной прогон будет каждый раз менять файлы под git.

Словарь тегов: `string_join`, `non_pk_fk_join`, `fk_fk_join`, `outer_join`, `subquery`, `exists_in`, `aggregate`, `window`, `cte`, `recursive`, `top_n`, `skewed_param`, `many_tables` (≥ 8), `cyclic_join`, `like_predicate`, `in_list`, `range_predicate`.

### 4.5 Конвейер портирования запросов

1. **Сохранить оригинал** в `original/`.
2. **Автоматические правила переписывания:**
   - `LIMIT n` → `FETCH FIRST n ROWS ONLY`
   - `expr::type` → `CAST(expr AS type)`; строковые литералы дат → `DATE '...'` / `TIMESTAMP '...'`
   - `ILIKE` → `UPPER(..) LIKE UPPER(..)`, `CONTAINING` (только для поиска подстроки) или case-insensitive collation
   - арифметика с `INTERVAL` → `DATEADD` / `DATEDIFF`
   - `STRING_AGG` → `LIST`
   - кавычки и регистр идентификаторов; зарезервированные слова в именах столбцов (проверить схемы STATS и SQLStorm)
   - `ROLLUP` / `GROUPING SETS` → `UNION ALL`, если в целевой версии их нет
3. **Главное правило: переписывание не должно менять то, что видит оптимизатор.**
   - Не оборачивать столбец в функцию, если в оригинале его не было. Предикат перестанет использовать индекс, и оценка селективности станет другой.
   - Сохранять форму предикатов: диапазон остаётся диапазоном, IN-список — IN-списком.
   - Любое вынужденное отклонение фиксируется в `port_notes` и помечается тегом.
4. **Лимиты.** Проверить лимит длины IN-списков в целевой версии (исторически он был 1500 элементов) и общий размер текста запроса. Это актуально для CEB.
5. **Валидация результата.** Тот же запрос на тех же данных выполняется в эталонном движке (PostgreSQL или DuckDB): сравниваются число строк и хеш отсортированного мультимножества. Нужны допуски для вещественных чисел и учёт семантики строк (регистр, хвостовые пробелы `CHAR`, collation). Недетерминированные запросы получают `deterministic: false`, и для них сравнивается только то, что определено однозначно (например, число строк).
6. **В корпус запрос попадает только после валидации.** Непереносимые запросы помечаются и исключаются.

### 4.6 Истинные кардинальности

- **Подпланы.** В STATS-CEB и CEB они готовые. Для JOB, JOB-Complex, JCC-H и DSB генерируются как связные подмножества таблиц запроса со всеми предикатами, которые ссылаются только на эти таблицы.
- **Область определения.** Подплан как множество таблиц корректно определён для внутренних соединений. Для запросов с внешними соединениями и подзапросами (`subplan_scope: root_only`) q-error считается только по корню.
- **Объём.** У отдельных запросов JOB число подпланов доходит до ~10⁴. Поэтому полный перебор ограничен подмножествами до k таблиц. К ним добавляются все подпланы, которые встречаются в выбранных планах эталона и кандидатов.
- **Покрытие.** Кандидат может выбрать план с подпланом, которого ещё нет в таблице истины. Отчёт показывает процент покрытия, а недостающие подпланы ночной контур досчитывает и кеширует.
- **Расчёт.** `COUNT(*)` выполняется один раз, быстрее в DuckDB или PostgreSQL. Затем выборочная сверка с Firebird из-за различий в семантике строк.
- **Хранение.** `truth/<suite>/subplans.parquet`: `query_id`, множество алиасов, текст подплана, `true_rows`.

### 4.7 Сопоставление оценок Firebird с подпланами

- **Вариант B (основной, в том числе в быстром контуре).** Разбор дерева `RDB$SQL.EXPLAIN` полного запроса. По `PARENT_RECORD_SOURCE_ID`, `OBJECT_NAME` и `ALIAS` для каждого узла определяется множество алиасов под ним. Оценка берётся из **верхнего** узла, который покрывает ровно это множество: над `Table` может стоять `Filter`, и у них разные оценки. Истина берётся из таблицы 4.6. Исполнение не нужно.
- **Вариант A (ночью и для STATS-CEB).** EXPLAIN каждого подзапроса подплана отдельно и CARDINALITY корня. Покрывает всё пространство подпланов, а не только узлы выбранного плана.
- **Профайлер** (`PLG$PROF_RECORD_SOURCE_STATS`: `OPEN_COUNTER`, `FETCH_COUNTER`). Используется только ночью, на отдельной копии с правом записи и не в замерных прогонах: он пишет в таблицы базы и вносит накладные расходы. Задача — сверять фактическое по узлам и ловить ошибки сопоставления.
- **Проверить в фазе 0:**
  - совпадают ли `RECORD_SOURCE_ID` у EXPLAIN и профайлера для одного текста запроса;
  - нормировку внутренней стороны nested loop (фактическое значение на одно открытие ≈ `FETCH_COUNTER / OPEN_COUNTER`);
  - учитывается ли завершающий пустой fetch.

## 5. Обвязка (harness)

| Компонент | Что делает |
|---|---|
| **collector** | `prepare` + `RDB$SQL.EXPLAIN`: нормализованный план и его хеш, оценки по узлам, время подготовки. Запросы не исполняются. |
| **runner** | Исполнение, прогрев, повторы; логические счётчики, время, число строк и checksum. |
| **truth** | Расчёт и пополнение таблицы истинных кардинальностей (4.6). |
| **compare** | Сравнение с эталоном и живое A/B. Классы: `improved`, `regressed`, `neutral`, `plan_changed_no_effect`, `new_timeout`, `wrong_result`, `error`, `not_executed`. |
| **report** | Markdown/HTML-отчёт + машиночитаемый статус для CI. |

**Технические требования**

- Язык: Python + `firebird-driver`; результаты в Parquet или SQLite; гейт рядом с `firebird-qa` (pytest).
- **Счётчики** удобнее снимать информационными запросами соединения до и после запроса: `isc_info_fetches`, `isc_info_read_seq_count`, `isc_info_read_idx_count` — это те же данные, что показывает isql в `SET STATS`. Это дешевле, чем `MON$`. Если используется `MON$`, помните, что снимок фиксируется на транзакцию, и для дельты нужна новая транзакция.
- **Таймауты.** На исполнение — statement timeout (FB 4+). На prepare он не действует, поэтому нужен клиентский сторож, который отменяет операцию через `fb_cancel_operation` из другого потока.
- **Нормализация плана** перед хешированием. **Сохраняется:**
  - порядок соединения и метод соединения (nested loop, hash, merge); у hash — какая сторона строится;
  - метод доступа и имя индекса, тип совпадения сегментов (full / partial match, число сегментов в границах), range / unique scan, bitmap AND / OR;
  - сортировки, агрегации, semi- и anti-соединения, вид обработки подзапросов.

  **Удаляется:** только оценки кардинальности и стоимость, они хранятся отдельно. Слишком агрессивная нормализация даст ложный вывод «план не изменился», и запрос не будет исполнен.

## 6. Метрики

Везде используется **r = значение кандидата / значение эталона**. r < 1 — улучшение, r > 1 — ухудшение. Ускорение = 1 / r.

| Метрика | Как считать | Роль |
|---|---|---|
| Изменённые планы | Число, доля и список по хешу нормализованного плана | Триаж |
| Логические счётчики | page fetches, record reads (seq / idx), r по каждому | Гейт для неизменённых планов; сигнал для изменённых |
| Физические чтения | page reads | **Не для гейта** (зависят от кэша); только в холодных прогонах |
| Время выполнения | Медиана из N прогретых прогонов, r | Гейт для изменённых планов (с подтверждением) |
| Сводка | **Геометрическое среднее r** по изменённым запросам + доля изменённых. Не сумма времени: её определяют несколько тяжёлых запросов. | Сводка |
| Таймауты | Цензурированные значения: в r подставляется значение таймаута (оценка снизу), и они отдельно считаются | Гейт |
| Улучшения / регрессии | Число запросов за порогом в каждую сторону | Сводка, гейт |
| Время подготовки | r и абсолютная разница | Гейт |
| q-error по подпланам | Медиана, p90, p99, max; разрез по числу соединений; **отдельно недо- и переоценка**; процент покрытия истиной | Информационная (детерминирована, A/A не нужен) |
| P-Error | Стоимость плана, выбранного по оценкам, делённая на стоимость плана по истинным кардинальностям (обе — при истинных кардинальностях) | Информационная → гейт после внедрения (раздел 11) |
| Зазор до оптимума | Время плана по умолчанию / время лучшего известного плана | Еженедельная |
| Разрезы | Всё перечисленное по тегам и по измерениям конфигурации (раздел 7) | Диагностика |

**Почему q-error не блокирует.** Авторы STATS-CEB сравнили методы оценки кардинальности: корреляция между q-error метода (медиана и p90) и итоговым временем выполнения оказалась ≈ 0,04, а у P-Error ≈ 0,8. Q-error одинаково штрафует ошибки на маленьких и больших подпланах и не различает недо- и переоценку.

**Статистическая значимость времени.** 3–5 повторов надёжно ловят только крупные изменения. В быстром контуре используются отношение медиан, порог из A/A-калибровки и подтверждение. В ночном добавляется бутстреп-интервал для r и для геометрического среднего.

## 7. Конфигурация оптимизатора как измерение

Параметры, которые влияют на выбор плана, фиксируются в `config/`, а их хеш входит в ключ эталона:

- `OptimizeForFirstRows` (по умолчанию ALL ROWS; на уровне сессии — `SET OPTIMIZE`, на уровне запроса — `OPTIMIZE FOR`);
- `SubQueryConversion` (FB 5.0.1+): преобразование IN / EXISTS / ANY / SOME в semi-join; по умолчанию выключено, в будущем может стать безусловным;
- `OuterJoinConversion`;
- все прочие параметры памяти и сортировки, влияющие на исполнение.

| Измерение | Быстрый контур | Ночной контур |
|---|---|---|
| Основная конфигурация (значения по умолчанию) | да | да |
| `SubQueryConversion = true` | — | да (запросы с тегами `subquery`, `exists_in`) |
| `OPTIMIZE FOR FIRST ROWS` | — | да (запросы с тегом `top_n`); метрика — время до первой строки |
| Конфигурация индексов `pk` | — | да |

Top-N и FIRST ROWS почти не покрыты наборами семейства JOB. Источники таких запросов — SQLStorm, DSB и TPC-H (запросы с `ORDER BY ... FETCH FIRST`).

## 8. Контуры прогонов

### 8.1 Быстрый контур (на каждый коммит, ≤ 30 мин)

Запускается **только сборка-кандидат**. Сравнение идёт с хранимым эталоном главной ветки (принцип 2). Живое A/B — только на этапе 3.

| Этап | Бюджет | Состав |
|---|---|---|
| 0. Подготовка | ~1 мин | Старт сервера кандидата; золотые копии read-only уже на диске |
| 1. Компиляция | ≤ 6 мин (замерить в фазе 0) | P1-корпус (JOB, JOB-Complex, JOB-light, Scale, Synthetic, STATS-CEB + подпланы по варианту A) и JCC-H SF1. Результат: diff планов, q-error по варианту B, время подготовки, CERT по корпусу. CEB-IMDb-3k — только если укладывается в бюджет, иначе ночью. |
| 2a. Изменённые планы | ≤ 10 мин (лимит) | Все `fast`-запросы с изменившимся планом; таймаут = k × эталонное время |
| 2b. Контрольный набор | ~6 мин | Фиксированный набор: счётчики + время |
| 3. Подтверждение | ≤ 5 мин | Живое A/B (ABAB, база и кандидат) только для подозрительных запросов из этапов 2a и 2b |
| 4. Отчёт и гейт | ~1 мин | |
| Резерв | ~1 мин | |

**Статус `INCOMPLETE`.** Если этап 2a не успел исполнить все изменённые `fast`-запросы, или изменились планы `heavy`-запросов, или покрытие истиной ниже порога — контур не выставляет `PASS`. Выставляется `INCOMPLETE` со списком непроверенного, и автоматически запускается внеочередной ночной прогон для этой ветки.

**Отбор контрольного набора** (раз в калибровку):
1. Только запросы класса `fast`.
2. Жадно добавляем самые дешёвые, пока каждый тег и каждое семейство шаблонов не покрыты минимум 2 запросами.
3. Добираем до бюджета запросами, у которых план исторически чаще всего менялся.

**Храповик.** Проверяется отдельно и дёшево: по плану (ожидаемый план или запрещённый план) и по счётчикам (верхняя граница). Исполнение по времени — только для храповика с эталонным временем < 1 с. Так храповик растёт, не съедая бюджет.

### 8.2 Ночной контур (несколько часов)

- **Эталон главной ветки:** планы, оценки и счётчики по всему корпусу. Это источник эталона для быстрого контура.
- **Полное исполнение:** семейство JOB, STATS-CEB **включая тяжёлые запросы**, CEB-IMDb-3k, TPC-H SF10, JCC-H SF10 (normal + skewed), DSB SF10 с 5–10 наборами параметров на шаблон.
- **Изменённые и непроверенные запросы** из быстрых контуров за день, включая `INCOMPLETE`.
- **Измерения конфигурации** из раздела 7.
- **Холодный режим** для подмножества: сброс кэша ОС, перезапуск сервера, учёт физических чтений.
- **Профайлер** (отдельная копия): сверка фактического по узлам, проверка сопоставления 4.7.
- **Истина:** досчёт недостающих подпланов.
- **Время:** 3–5 повторов, ABAB, бутстреп-интервалы.
- **SQLancer** (CERT + логические оракулы) со случайными seed на N часов.
- **Калибровка:** обновление `results/calibration` (`baseline_ms`, `fast` / `heavy`).

### 8.3 Еженедельный и релизный контур

- **SQLStorm:** выборка из нескольких тысяч запросов на 1 ГБ; перед релизом — всё переносимое.
- **CEB-IMDb-full:** q-error только через компиляцию; исполнение — по выборке.
- **Hollywood SF10:** поведение на масштабе.
- **Перебор порядков соединения** в стиле TAQO (с ограничениями из 3.2): таблица лучших известных планов и зазор до оптимума.
- **CH-benCHmark:** стабильность планов при дрейфе данных и устаревшей статистике.
- **A/A-прогон** (одна сборка дважды): контроль дрейфа среды и пересмотр порогов.
- По необходимости: Stack Parametric, LDBC SNB BI.

## 9. Правила гейта (стартовые пороги, калибруются по A/A)

Статусы: `PASS`, `WARN`, `FAIL`, `INCOMPLETE`.

| Условие | Статус |
|---|---|
| Неверный результат (checksum / число строк) у детерминированного запроса | **FAIL** (это корректность) |
| Новый таймаут или ошибка | **FAIL** |
| План не изменился, а счётчики выросли (r > 1,05) | **FAIL** — изменилось исполнение при том же плане; разобрать |
| План изменился: время r > 1,5 и > 100 мс, подтверждено живым A/B | **FAIL** |
| План изменился: счётчики r > 1,2, но время не ухудшилось | WARN (например, переход на hash join) |
| Время подготовки r > 2 и > 50 мс | **FAIL** |
| Нарушение храповика (запрещённый план или превышена граница счётчиков) | **FAIL** |
| Геометрическое среднее r по изменённым запросам > 1,0 при отсутствии FAIL | WARN + ручной разбор |
| q-error p90 ухудшился > 20% в любом разрезе по числу соединений | WARN |
| P-Error p90 ухудшился > 10% (после внедрения) | WARN, позже FAIL |
| Непроверенные изменения (раздел 8.1) | **INCOMPLETE** |

**Принятые регрессии.** Изменение оптимизатора может сознательно ухудшить часть запросов ради общего выигрыша. Такие регрессии заносятся в `accepted/`: id запроса, допустимое r, обоснование, автор, срок действия. Гейт их не блокирует, отчёт показывает отдельно. После слияния в главную ветку ночной прогон снимает новый эталон, и записи в `accepted/` для этого изменения закрываются.

**Калибровка порогов.** A/A-прогон, пороги выше p99 шума каждой метрики. Пересматриваются при смене железа и конфигурации и по еженедельному A/A.

## 10. Шум и воспроизводимость

- Побайтовая копия золотого файла, режим read-only, ключ эталона (раздел 4.2).
- Конфигурация `firebird.conf` / `databases.conf` хранится в репозитории, её хеш входит в ключ.
- Прогрев: первый прогон отбрасывается, берётся медиана из 3–5. Холодный режим — отдельно ночью.
- Выделенная машина для измерений времени, фиксированная частота CPU (без turbo и энергосбережения), никаких фоновых задач.
- Живое A/B — чередованием ABAB, а не блоками.
- Профайлер — только в отдельных прогонах, не в замерных.
- Сборки главной ветки хранятся как артефакты, чтобы этап 3 мог их запускать.

## 11. Доработки движка (отладочная сборка)

1. **Подстановка кардинальностей из файла (режим TrueCard).** Оптимизатор берёт оценки подпланов из внешнего файла. Это даёт:
   - **Ориентир выигрыша от улучшения оценок.** Это не строгий потолок: при ошибках стоимостной модели истинные кардинальности могут привести к худшему плану. В PostgreSQL план по истинным кардинальностям был оптимальным для > 98% запросов STATS; истинные кардинальности ускорили STATS-CEB почти на 50%, а JOB-light — лишь на ~14%. Так видно, какие наборы чувствительны к оценке.
   - **Разделение причин.** Ошибка оценки отделяется от ошибок стоимостной модели и перебора.
   - **P-Error без исполнения** (вместе с пунктом 3).
   - Требование: истина должна покрывать все подпланы, о которых спрашивает оптимизатор. Непокрытые подпланы отражаются в отчёте вместе с откатом к обычным оценкам.
2. **Трасса оптимизатора** (опционально): дамп всех рассмотренных подпланов с оценками и стоимостями. Даёт q-error по всему пространству подпланов без отдельных EXPLAIN.
3. **Стоимость заданного плана:** оценить стоимость плана из `PLAN` при заданных кардинальностях. Нужно для P-Error.

## 13. Риски и открытые вопросы

- **Версия Firebird.** CARDINALITY в `RDB$SQL.EXPLAIN` есть только в FB 6. Для веток FB 5 доступны лишь счётчики, время и профайлер, без оценок; q-error и CERT там недоступны.
- **Смена ODS** в разрабатываемой ветке ломает живое A/B со старой сборкой и требует пересоздания эталонов (4.2).
- **Сопоставление узлов.** Совпадение `RECORD_SOURCE_ID` у EXPLAIN и профайлера — проверить в фазе 0.
- **Неизвестное время прогона на Firebird.** Цифры PostgreSQL дают только порядок величины; реальная разметка — в фазе 0–1.
- **Бюджет компиляции.** Prepare запросов с 10+ таблицами может оказаться дорогим; тогда часть корпуса уходит из быстрого контура в ночной.
- **Возможности SQL.** ROLLUP / GROUPING SETS в TPC-DS и DSB; лимит IN-списков для CEB; часть запросов SQLStorm непереносима.
- **Недетерминированные результаты** (SQLStorm, top-N) — источник ложных FAIL, если не размечены (`deterministic`).
- **Форматы.** Запросы CEB хранятся в pickle (networkx), нужен скрипт извлечения.
- **Семантика строк.** Различия collation, регистра и `CHAR` могут разводить результаты и истинные кардинальности между Firebird и эталонным движком.
- **Лицензии.** Проверить условия использования каждого датасета и генератора (IMDb, инструменты TPC и производный от них DSB, дампы Stack Exchange — CC BY-SA) до публикации корпуса.
- **Ресурсы CI.** Измерения времени — только на выделенной машине. На общих раннерах допустимы этапы 1, 2 и храповик по счётчикам, а этап 3 переносится на выделенную машину.

### A.1 Фактические и технические ошибки

| # | Было в v1 | Проблема | Исправлено в v2 |
|---|---|---|---|
| 1 | Основная метрика гейта — «page fetches / reads» | Физические чтения (reads) зависят от состояния кэша и шумят | Для гейта только fetches и record reads; физические чтения — в холодных прогонах (6) |

### B.2 Принятые решения и закрытые вопросы

- **CEB-IMDb оригинал** (13,6K pickles) закрыт как недоступный: ссылки Dropbox мертвы, зеркал нет (проверено 13.10.2026). Канон — regen-версия.
- **Три класса числовых расхождений FB ↔ PG**, канонизированы в валидаторе: масштаб AVG/вещественных агрегатов; экспоненциальная форма `0E-8` у FB Decimal на нулевых объёмах; сохранение CHAR-padding в `\|\|` и `SUBSTRING` (правило порта: `TRIM(TRAILING ...)`).
- **FB5 не имеет** INTERSECT / ROLLUP / GROUPING: 60 DSB-запросов исключены с записанными причинами (`bench/manifest/dsb-*-excluded.yaml`). Прочее: `SELECT FIRST n DISTINCT` валиден, `SELECT DISTINCT FIRST` — нет; перед ADD PRIMARY KEY на nullable-колонке нужен явный `SET NOT NULL`.
- **JCC-H под Windows**: 64-битная арифметика phash ломалась на LLP64 (`unsigned long` = 32 бита) — фикс `uint64_t` в `third_party/dbgen.JCC-H/skew/`; данные воспроизводимы (одинаковые SHA на разных машинах). lineitem = ровно 6 000 000 строк.
- **DSB на Windows**: msbuild Win32 + v142; `distcomp` обязан отработать до `dsqgen`; Win32-сборка dsqgen флакает (heap corruption, пустые выводы) — ретраи с валидацией размера/содержимого. Пустые поля `.dat` = NULL.
- **Инфраструктура прогонов**: сторож prepare через `fb_cancel_operation`; `--resume` валидатора (переживает AV firebird-driver); ровно один attachment_reaper (age > timeout + 45); осиротевшие аттачменты снимаются `DELETE FROM MON$ATTACHMENTS`; golden > 2 ГБ переносится gbak + scp + restore через service_mgr. Подробности — §8 в `porting-plan-remaining-suites.md`.

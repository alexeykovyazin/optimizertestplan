## 1. Канонический конвейер порта набора (8 шагов)

Каждый набор проходит одни и те же шаги. Шаги S0–S2, S5 выполняются в

| Шаг | Что делается | Поток | Критерий готовности |
|---|---|---|---|
| **S0** Источник | Найти репозиторий/генератор набора, проверить лицензию (план §13), зафиксировать объём и диалект | A | URL + лицензия записаны в манифест набора; файлы запросов получены/сгенерированы |

| **S2** Загрузка | CSV → EXECUTE BLOCK по 200 строк (потоки 3–4); манифест со счётчиками таблиц и sha каждой CSV | A | счётчики строк совпали с источником; время загрузки записано |

## 2. Правила порта диалекта PG → FB (копить в общий модуль)

Уже проверено на JOB/STATS (живут в `port_job.py` и заметках):

1. Reserved words → в кавычки: `at` → `"at"`, `AS character` → `AS "character"`,
   `"Date"`, `"Count"`; **не** цитировать `role` (non-reserved).
2. Столбцы строк длиннее 8191 байт UTF8 → `BLOB SUB_TYPE TEXT` на этапе S1;
   соответствующие `MIN(col)` в запросах → `MIN(SUBSTRING(col FROM 1 FOR 8000))`
   со статусом match_truncated.
3. Строковые литералы >16383 байт → чанк `"…' || '…"` по ≤12000 байт.
4. Нет multi-row `INSERT VALUES(…),(…)`; EXECUTE BLOCK ≤256 контекстов →
   батчи по 200 строк.
5. Соединение драйвера — всегда `charset="UTF8"`; DDL коммитить отдельно от
   DML (в одной транзакции драйвера DDL+DML ломается).
6. Дополнить при порте TPC-H/DSB (ожидаемо): `LIMIT n` → `FIRST n`,
   `EXTRACT(EPOCH …)` → DATEDIFF-эквиваленты, дата-арифметика, `FILTER (WHERE …)`
   → CASE, `::тип` → CAST, ILIKE → UPPER+LIKE, lateral → перезапись.
7. IN-списки: на этапе S5 каждого набора тестировать предельный размер
   (исторический лимит 1500 элементов) — CEB-IMDb содержит длинные IN.

## 3. Наборы: источники, объём, специфика, трудоёмкость

### 3.1 P1 — остаются от быстрого контура

#### 3.1.1 JOB-Complex (30 запросов + ~6000 планов)
- **S0**: 30 запросов из статьи JOB-Complex (по плану §3.1 — «из статьи»);
  на S0 зафиксировать точный источник и, если SQL не выложен, — либо
  восстановить по описанию шаблонов, либо исключить с записью в манифест.
  ~6000 планов — только истина для сравнения, в FB не исполняются.
- **Данные**: тот же снимок IMDb — **новая загрузка не нужна**, golden уже есть.
- **S5**: порт 30 SQL по правилам §2 (наиболее тяжёлые формы: соединения не
  по PK/FK, строковые соединения, сложные фильтры).
- **Специфика**: запросы до 17 таблиц — prepare может быть дорогим (бюджет
  компиляции замерить на S5).
- **Трудоёмкость**: S0/S5 ~0.5 дня; S6–S8 ~2–3 ч окна dellg15.
- **Готовность**: 0 mismatch; 30/30 prepare.

#### 3.1.2 JOB-light / Scale / Synthetic (70 / ≈500 / ≈5000)
- **S0**: репозиторий `learnedcardinalities` (Kipf et al.) — workload-файлы
  `job-light*.sql`, `scale*.sql`, `synthetic*.sql`; проверить лицензию.
- **Данные**: тот же IMDb-golden — запросы звёздные PK-FK по тем же таблицам.
  Сверить на S0, что имена таблиц/столбцов совпадают с нашим снимком
  (иначе — таблица соответствий).
- **S5**: синтетические шаблоны → рендер параметров по правилам §2;
  5000 synthetic — рендерить скриптом, не руками.
- **Трудоёмкость**: S0/S5 ~1 день (большая часть — рендер synthetic);
  S6–S8: ~4–6 ч окна (PG: 5200 EXPLAIN; FB: 5200 prepare + прогон
  тяжёлых).
- **Готовность**: ≥99% match (допустимы truncations с причинами), полный
  прогон synthetic допустим в ночной контур.

### 3.2 P2 — ночной контур

#### 3.2.2 JCC-H (22 × normal/skewed поверх TPC-H)

## 5. Известные ловушки (выстрадано на JOB/STATS — читать перед стартом)

- ssh/scp файлов >2 ГБ виснет; большие данные генерировать/грузить на месте.
- `copy /y` молча обрезает большие файлы — только python `shutil` + размер.
- psql: `\copy` строго в одну строку; `\o` — прямые слэши; `\timing`
  пишет `Time: X,YYY ms` в stdout — чистить регэкспом; пустая CSV-строка =
  все-NULL строка результата.
- cmd: `.bat` с LF-концевиками ломает `call :label`; `subprocess` со
  списком аргументов калечит пути — `shell=True`; findstr/copy — только
  backslash-пути.
- firebird-driver: `charset="UTF8"` всегда; DDL отдельной транзакцией;
  `set_statement_timeout` — property соединения; сторож на клиенте
  обязателен (серверный timeout не спасает от сетевых клинов).
- dellg15 иногда уходит в сон/теряет mDNS — длинные задачи вести с
  логом в файл и идемпотентным рестартом (`--tags`), на время замеров
  отключать автосон.
- golden read-only в заголовке БД — рабочим копиям `gfix -mode read_write`
  (attrib недостаточно).

### Новые ловушки (дополнение к §5)

- **PG-эталон, параллельные COPY/EXPLAIN**: тяжёлые звёздные COUNT
  висят в `IPC/BgworkerShutdown`; statement_timeout срабатывает с
  опозданием (300 с → отмена на 17.6 мин), pg_cancel/terminate
  возвращают t, но не действуют, пока воркер не выйдет. Лечение:
  terminate лидера+воркера и ждать; watchdog-скрипт в E:\pgdumps.
- **PowerShell-скрипты на dellg15**: ExecutionPolicy Restricted —
  запускать только `powershell -ExecutionPolicy Bypass -File ...`
  (первый watchdog молча не работал).
- **firebird-driver, exec_timeout → краш процесса**: брошенное после
  таймаута соединение в GC даёт access violation в detach и убивает
  python (валидация job-light умерла на 058). Per-qid json спасает;
  монстры валидировать по процессу на запрос.

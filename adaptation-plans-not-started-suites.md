# Планы адаптации наборов «Не сделано» под Firebird

*Исследование от 25.10.2026. Дополнение к `README.md` (раздел «Корпус: статус сюит», таблица
«Не сделано») и `firebird-optimizer-testing-plan_1.md` (§3.1–3.2). Факты проверены по живым
репозиториям/статьям (fetch, разбор файлов, частично — локальная сборка генераторов); всё
непроверенное помечено. Для каждого набора: суть, поправки к плану v2.1, план по конвейеру
S0–S8, трудоёмкость, риски.*

**Метод.** Каждый набор прогоняется через отработанный конвейер **S0–S8** (источник → DDL →
загрузка → индексы → golden → порт+prepare → PG-эталон → валидация «0 mismatch / 0 error» →
бейслайн), переиспользуя существующую обвязку (`port_*.py`, `suite_pg_reference`,
`job_validate`, `prepare_test`, `s8_supervisor`, `phase0_make_baseline`). Отличия — только
в DDL-генераторе, правилах порта и источнике данных.

## Главные поправки к плану v2.1 (найдены при исследовании)

1. **Hollywood: SF10/SF100 не существуют.** Выпущен только Hollywood-200K
   (19,7 млн строк ≈ 0,27× нашего IMDb). Это тест *смены распределения*, а не масштаба.
2. **TAQO — это Gu/Soliman/Waas (DBTest 2012)**, не Rigger. Критерий статьи
   (корреляция cost↔время) на FB невоспроизводим — у Firebird нет числовых стоимостей.
   Переносим критерий из репозитория qvad/taqo: «зазор до оптимума» (best/default).
3. **CH-benCHmark**: первоисточник — Cole et al., DBTest 2011 (не Dey/Fekete/Röhm);
   «10 млн строк на склад» — миф, реально ≈ 0,6 млн строк/склад.
4. **CardBench**: вопреки «TODO» в документации, CSV-дампы **10 из 20 датасетов лежат
   в бакете** — 233 тыс. готовых SQL-запросов с воспроизводимыми метками.
5. **SQLStorm**: готовых эталонных результатов в репозитории нет (в выложенных CSV
   столбец `result` пуст) — S6 (свой PG-эталон) обязателен; ~13 % запросов сами авторы
   оценивают как содержательно ошибочные.

## 1. SF10-масштаб TPC-H / JCC-H / DSB (P2 — начинать первым)

**Суть.** Те же 22/22/465 уже портированных запросов на данных ×10. Портирование запросов
не требуется вообще — только данные, золотые копии, эталон и новые бейслайны.

**Проверенные объёмы SF10:**

| Набор | Raw CSV | Ключевые счётчики | Генератор |
|---|---|---|---|
| TPC-H | ≈10–12 ГБ | lineitem ≈60 млн, orders 15 млн | `dbgen -s 10 -C N -S i` (чанки подтверждены) |
| JCC-H | ≈10–12 ГБ | lineitem **ровно** 60 млн (`-k` выравнивает), буфер ~0,3 ГБ RAM | наш dbgen 2.17.2 с `uint64_t`-фиксом; `-k -s 10`; генерация медленнее из-за populous-заказов |
| DSB | ≈13 ГБ | store_sales 28,8 млн, **inventory 117,45 млн** (растёт линейно — станет главной таблицей), web_sales ≈7,2 млн (не 3,9, как в старых таблицах v2.6-эры) | `dsdgen /scale 10 -parallel N -child i`; distcomp не зависит от масштаба; все таблицы генерировать вместе (частичный порядок) |

**План.**

1. **S0–S2 (dellg15, на месте):** генерация CSV на машине замеров (правило «не таскать
   >2 ГБ»); проверить диск (пик ~80 ГБ на все три: CSV + golden + PG).
2. **S1/S2 FB:** DDL SF1 переиспользуется без изменений (типы те же); загрузка —
   существующий loader; inventory 117 млн строк — самая долгая загрузка, заложить ночь.
3. **S3–S4:** индексы как SF1; golden — gbak + scp + restore через service_mgr (правило
   для >2 ГБ уже выстрадано); read-only + SHA-256; **новый ключ эталона**.
4. **S6–S7:** PG-эталон пересчитать полностью (монстры Q17/Q20 TPC-H станут тяжелее —
   класс `no_pg_reference` расширится); валидация с поднятыми таймаутами (300→600/1800 с);
   дивергенции известны (AVG-масштаб, `0E-8`, CHAR-паддинг) — валидатор уже умеет.
5. **S8:** бейслайны, затем перекалибровка fast/heavy — часть «быстрых» SF1-запросов
   перейдёт в heavy; настройка ночных целей (§8.2) наконец получает свои SF10-данные.

**Трудоёмкость:** TPC-H ~1–2 дня, JCC-H ~1 день, DSB ~2–3 дня (медленный dsdgen + ретраи
heap-corruption + 117 млн inventory). Итого **~1–1,5 недели**.
**Риски:** PG-эталон SF10 потребует тихих окон и монстро-проходов; дисковое пространство;
таймауты валидации.
**Критерий готовности:** 0 mismatch/0 error на SF10, бейслайны с новыми ключами,
обновлённая калибровка.

**Ссылки:** [dbgen/TPC-H](https://github.com/electrum/tpch-dbgen) ·
[ldbc/dbgen.JCC-H](https://github.com/ldbc/dbgen.JCC-H) · [microsoft/dsb](https://github.com/microsoft/dsb) ·
[TPC-DS spec v2.7.0 (row counts)](http://www.tpc.org/tpc_documents_current_versions/pdf/tpc-ds_v2.7.0.pdf)

## 2. CERT-оракул (P2)

**Суть** (Ba & Rigger, ICSE 2024, «CERT: Finding Performance Issues in Database Systems
Through the Lens of Cardinality Estimation», arXiv:2306.00355). Запросы не исполняются.
Ужесточение Q→Q′ (12 правил: LEFT/RIGHT JOIN→INNER, добавление предиката, ALL→DISTINCT,
добавление GROUP BY/HAVING и т.д.) не должно увеличивать **оценку** кардинальности корня
плана: EstCard(Q′) ≤ EstCard(Q). Нарушение = потенциальный perf-баг. В SQLancer CERT
поддерживает только TiDB/CockroachDB/MySQL и жёстко связан со случайным генератором
запросов — но инвариант локален по запросу, **готовый корпус применим**, если написать
собственный мутатор и парсер плана (в SQLancer вся DBMS-специфика — ~200 строк: парсер
оценки + edit-distance-защита).

**Ключевой факт для нас:** полный CERT требует оценок кардинальности, которых на FB 5 нет.

**План — два этапа.**

- **Этап FB5 (подготовка, ~1 неделя):**
  1. `cert_mutate.py`: применение правил к текстам корпуса. Правила для FB:
     LEFT→INNER JOIN; ALL→DISTINCT; добавление GROUP BY по fetch-колонкам; добавление
     HAVING; обертка WHERE `P AND p`; удаление операнда OR. Правила FULL JOIN (3–5)
     **неприменимы — FULL JOIN во Firebird нет**; правило LIMIT исключаем сразу
     (в SQLancer признано шумным, false positives).
  2. Пары (Q, Q′) прогнать через collector: prepare + нормализованный план обеих версий;
     корпус пар с планами сохраняется.
  3. Суррогат-эксперимент (пометить как экспериментальный, не CERT): структурная
     монотонность плана — ужесточённый запрос не должен получать «худший» план.
     Модель ложных срабатываний не изучена — только разведка.
- **Этап FB6 (полный CERT, при появлении snapshot):** парсер `RDB$SQL.EXPLAIN` (нужен для
  4.7 вариант B в любом случае) → оценка корня; проверка инварианта по парам из этапа FB5;
  защита как в SQLancer — edit distance ≤1 по последовательности операторов плана, иначе
  пара пропускается; требование непустых таблиц (у golden-баз выполнено, проверять явно).

**Контур:** ночной (SQLancer-блок §8.2). Ожидаемая частота нарушений по опыту статьи
~0,2 % пар — каждое срабатывание разбирается вручную и становится храповиком.
**Трудоёмкость:** FB5-этап ~1 неделя, FB6-этап ~1 неделя поверх парсера EXPLAIN.
**Риски:** мутации текста SQL без полного парсера → часть пар отбрасывается (честно
фиксировать); «CERT может давать ложные тревоги» — оговорка самой статьи. Найденные в
статье баги: 13 issues (MySQL 3, TiDB 6, CockroachDB 4); правило «добавление WHERE» —
самое продуктивное.

**Ссылки:** [arXiv:2306.00355](https://arxiv.org/abs/2306.00355) ·
[PDF автора](https://bajinsheng.github.io/assets/pdf/cert_icse24.pdf) ·
[sqlancer/sqlancer](https://github.com/sqlancer/sqlancer)
(`src/sqlancer/common/oracle/CERTOracle.java`, `CERTOracleBase.java`, `common/gen/CERTGenerator.java`) ·
[issue #822](https://github.com/sqlancer/sqlancer/issues/822)

## 3. TAQO (P3 — но разблокирован и дешев, рекомендую вторым)

**Суть** (Gu, Soliman, Waas, DBTest 2012, «Testing the Accuracy of Query Optimizers»,
DOI 10.1145/2304510.2304525; фреймворк qvad/taqo + форк yugabyte/taqo). Принудительно
перебираются альтернативные планы одного запроса, каждый исполняется; сравниваются план
по умолчанию и лучший найденный. Метрика репозитория: `score = best/default`,
классификация `better_plan_found` / `same_execution_plan` (допуск 5–15 %), контроль
результата по хешу. (Метрика статьи — корреляция ранжирований cost↔время (Kendall tau) —
на FB невоспроизводима: стоимостных чисел в плане нет.)

**План.**

1. **Инъекция планов:** вместо pg_hint_plan — `PLAN JOIN/HASH/MERGE (...)` прямо в тексте;
   на каждом узле: порядок (`ORDER`), метод (nested loop / hash / merge) и доступ
   (NATURAL / INDEX ix / ORDER ix). Удобнее хинтов PG: не нужны session-переменные,
   а применимость плана **верифицируется повторным prepare** (получили ожидаемый
   нормализованный план — считаем вариант; ошибка PLAN = вариант пропущен). Дедуп
   вариантов по хешу нормализованного плана (готовый `normalize.py`).
2. **Пространство перебора** (факториальный рост — главный риск): ≤4 таблиц — полный
   перебор порядков × методы × доступ; 5–6 таблиц — сэмплирование с капом ~200–500
   вариантов (как в статье: 500) или pairwise; ≥7 таблиц — только scan-варианты +
   затравки из ~6000 планов JOB-Complex и будущих TrueCard-планов (§3.2, §11 плана).
   Запросы, где PLAN не управляет формой (подзапросы, декорреляция), помечаются
   и исключаются.
3. **Замеры:** только выделенная машина; warmup + best-of-5 (политика статьи) или медиана
   из `runner.py`; таймаут варианта = текущий best + дельта (приём `look-near-best-plan`);
   бесплатный оракул корректности — checksum результата должен совпадать у всех вариантов.
4. **Отчёт:** optimality (доля запросов, где дефолт уже оптимален), распределение score,
   геосреднее best/default. Для ориентира: у зрелых CBO дефолт оптимален лишь в 45–77 %
   (TPC-H) и 31–61 % (JOB) — цифры Yugabyte CBO-блога.
5. **Контур:** еженедельный (§8.3) по подмножеству корпуса (job, job-light, scale, tpch,
   jcch, dsb-s1/s2, stats-ceb — все уже есть).

**Трудоёмкость:** каркас для ≤4-табличных запросов ~1–1,5 недели; сэмплирование для 5–6
таблиц ещё ~неделя. Новых данных **не нужно**.
**Риски:** FB-специфика OUTER JOIN в PLAN (проверить применимость на JOB 17f и др.);
heavy-запросы умножают время на число вариантов — держать их в еженедельном контуре
с жёстким таймаутом.

**Ссылки:** [PDF статьи (CMU mirror)](https://15799.courses.cs.cmu.edu/spring2025/papers/21-orca/gu-dbtest2012.pdf) ·
[ACM DL](https://dl.acm.org/doi/10.1145/2304510.2304525) · [qvad/taqo](https://github.com/qvad/taqo) ·
[yugabyte/taqo](https://github.com/yugabyte/taqo) ·
[YFTT-слайды](https://info.yugabyte.com/hubfs/YFTT%20Slide%20Decks/2023_02_17_YFTT_Dmitry%20Sherstobitov_TAQO%20-%20Testing%20Accuracy%20of%20Query%20Optimizer.pdf) ·
[Yugabyte CBO blog](https://www.yugabyte.com/blog/yugabytedb-cost-based-optimizer)

## 4. SQLStorm (P3)

**Суть** (Schmidt, Leis, Boncz, Neumann; PVLDB 18(11) 2025, «SQLStorm: Taking Database
Benchmarking into the LLM Era»). 18 251 запрос, сгенерированных GPT-4o-mini на данных
StackOverflow (снимок до 03.10.2024); PostgreSQL-подобный диалект; один запрос = один
файл; параметризации нет. Репозиторий `SQL-Storm/SQLStorm` — **MIT**; данные
**CC BY-SA 4.0**; дампы живые: `stackoverflow_dba.tar.gz` 377 МБ (1 ГБ-вариант, ~3,1 млн
строк), `stackoverflow_math.tar.gz` 4,2 ГБ (12 ГБ), полный 78 ГБ.

**Схема:** 13 таблиц (8 больших + 5 enum), 19 FK, 32-битные PK, `text` в AboutMe/Body/Text —
максимум строки **116 293 символа** → BLOB SUB_TYPE TEXT обязательны; только PK-индексы.

**Оценка переносимости (regex-скан всех 18 251):** «как есть» ≈22,8 %, механические
rewrite ≈64,6 % (LIMIT→FIRST, INTERVAL→DATEADD, STRING_AGG→LIST, `::`→CAST,
ILIKE→UPPER LIKE, EXTRACT(EPOCH)→DATEDIFF, FILTER→CASE), тяжёлые ≈12,6 % (в основном один
паттерн `string_to_array+UNNEST` по `Posts.Tags` — выбрасывается). Итого потенциально ~87 %.

**План.**

1. **S0:** зафиксировать v1.0, лицензии; корпус ограничить готовыми фильтрами репозитория:
   `valid_queries.csv` (12 587 парсится и совпадает в ≥2 системах) ∩ `correct_joins.csv`
   (14 771 корректные join) — реальный чистый корпус ~10–12 тыс.
2. **S1–S2:** DDL из `schema.sql` (text→BLOB TEXT, bool→BOOLEAN, reserved words в кавычки:
   `Count`, `Date`, `Text`); пилот — **только dba-дамп (377 МБ)**; загрузка существующим
   loader'ом.
3. **S5:** `port_sqlstorm.py` с правилами выше + prepare-батч; Tier-C помечать excluded
   с записью причины.
4. **S6:** PG-эталон считаем сами (в репо результатов нет) — 10K запросов с таймаутом 10 с
   (как в статье).
5. **S7 — главная методическая развилка:** ~48 % запросов — `ORDER BY … LIMIT n` без
   полного tie-break → недетерминированный top-N. Политика: `deterministic: false`,
   сравнение только числа строк (и/или мультимножества без порядка). Запросы, где FB
   результат расходится с PG *содержательно* (авторы оценивают 13 % как ошибочные),
   исключаются как невалидные с записью — гейт «0 mismatch» достигается на отфильтрованном
   подмножестве (прецедент — DSB excluded).
6. **S8 + контур:** еженедельный — выборка из нескольких тысяч; релизный — всё переносимое
   на 1 ГБ.

**Трудоёмкость:** пилот ~1,5–2 недели; полный — месяц+ (отдельное решение).
**Риски:** BLOB-сравнения (MIN/LIKE по Body — трюки от JOB уже есть); недетерминизм top-N;
объём ручного триажа исключений.

**Ссылки:** [SQL-Storm/SQLStorm](https://github.com/SQL-Storm/SQLStorm) ·
[статья](https://www.vldb.org/pvldb/vol18/p4144-schmidt.pdf) ·
[OLAPBench](https://github.com/SQL-Storm/OLAPBench) ·
[данные dba 1GB](https://db.in.tum.de/~schmidt/data/stackoverflow_dba.tar.gz) ·
[math 12GB](https://db.in.tum.de/~schmidt/data/stackoverflow_math.tar.gz) ·
[полный](https://db.in.tum.de/~schmidt/data/stackoverflow.tar.gz) ·
[schema.sql](https://db.in.tum.de/~schmidt/data/stackoverflow_schema.sql)

## 5. Hollywood (P3 — переосмыслить: не «масштаб», а смена распределения)

**Суть** (Iachnyk, Stoian, Kipf — UTN Nuremberg; arXiv:2607.19666, AIDB@VLDB 2026;
репозиторий `utndatasystems/hollywood`; `vorms/hollywood` — 404). Синтетический
IMDb-совместимый датасет: LLM генерирует семантические словари, кортежи материализует
детерминированный seeded-код. Код — **MIT**, датасет и запросы — **CC BY-NC 4.0**
(для внутреннего QA ок, при внешней публикации — нет).

**Проверенные факты:** выпущен только **Hollywood-200K**: 21 таблица канонической
JOB-схемы, 19,7 млн строк (title 351 455, cast_info 4,98 млн — это **~27 % нашего IMDb**);
CSV 932 МБ с заголовками, NULL=`''`; большие файлы в Git LFS (нужен `git lfs pull`).
Запросы: **213 = JOB 113 + JOB-light 70 + JOB-Complex 30** с перепривязанными литералами
(структура сохранена, меняются только константы). Приложены истинные кардинальности
(`experiments/paper_results/raw_csv/full_query_cardinality_raw.csv`) и результаты
PG 16.14: медианы q-error ниже, чем на IMDb, но хвосты резко тяжелее (p95 до 3·10⁵
на JOB-Complex).

**План (дешёвый благодаря переиспользованию).**

1. **S0:** клон + LFS; зафиксировать недетерминизм LLM-шага (регенерация не воспроизводит
   релиз — работаем только с выпущенным снапшотом).
2. **S1–S2:** **наш IMDb-DDL-генератор 1:1** (та же схема; `movie_info.info` → BLOB TEXT
   как раньше); их 23 индекса — как референс, но для сопоставимости с IMDb-бейслайном —
   наш набор индексов; загрузка ~27 % IMDb.
3. **S5:** правила `port_job/port_joblight/port_jobcomplex` поверх их файлов; решить:
   валидируем оригинальную проекцию `min(...)` (как в нашем JOB), а не их COUNT-обёртку.
4. **S6–S7:** свой PG-эталон (их `run_postgres_workload.py` — хороший образец: без
   параллельных воркеров, EXPLAIN ANALYZE JSON); кросс-чек против их true-count меток.
5. **S8 + контур:** еженедельный. Интерпретация: тест **обобщения оценщика/перебора за
   пределами фиксированного IMDb-снимка** — ценен для FB6 (q-error) и как дополнительные
   затравки для TAQO.
6. **Отдельная запись в плане:** SF10/SF100 — только обещание авторов («we plan to
   release…»). Если настоящий масштаб нужен — генерировать самим (LLM-шаг ~$100/100K
   фильмов, reproducibility не гарантирована) — **не рекомендую**; для масштаба существуют
   SF10 TPC-H/JCC-H/DSB (план №1).

**Трудоёмкость:** **2–3 дня** (после IMDb всё готово).
**Риски:** лицензия NC; маленький проект (3 коммита, bus-factor); «IMDb-подобность»
распределений не доказана (для теста обобщения это фича, не баг).

**Ссылки:** [arXiv:2607.19666](https://arxiv.org/abs/2607.19666) ·
[utndatasystems/hollywood](https://github.com/utndatasystems/hollywood)

## 6. Stack Parametric / Kepler SPQD (P4)

**Суть** (Doshi и др. + R. Marcus; SIGMOD 2023, «Kepler: Robust Learning for Faster
Parametric Query Optimization», DOI 10.1145/3588963). 87 шаблонов (`@param0…` — текстовая
подстановка, prepared-семантика не нужна) по нормализованной **multi-site** схеме
StackExchange: 10 таблиц `account, answer, badge, comment, post_link, question, site,
so_user, tag, tag_question`. В файле шаблонов вшито 100–350 наборов параметров на шаблон;
до 50 тыс. — в execution-JSON. Датасет — **CC BY 4.0**, код — Apache-2.0; репозиторий
google/kepler **архивирован 17.10.2024**.

**Главная проблема:** у SPQD **нет данных** — только шаблоны, параметры и метаданные
(distinct values / MCV). Исходные данные — Bao-era Stack-дамп с rmarcus.info (его живость —
не проверено). Наша STATS (сырой дамп, 8 таблиц) — **другая схема**: прямое исполнение
невозможно.

**План — три варианта по убыванию цены, выбрать после S0-проверки:**

1. **(а) Восстановить данные:** проверить живость дампа rmarcus.info/stack.html; если
   жив — построить БД по `pg_configs.json` (DDL 10 таблиц + 52 индекса приложены) — тогда
   шаблоны идут почти как есть (правки: LIMIT, ILIKE, IN-параметры со встроенными
   кавычками).
2. **(б) Смаппить на нашу STATS:** `question→posts`, `so_user→users`, `site_name→константа`…
   — ручная работа, селективности изменятся, `tag_question`/`account` потребуют решений.
3. **(в) Взять только методологию:** двухрежимный эксперимент поверх наших шаблонов —
   и это главная ценность для FB5 независимо от (а)/(б):
   - **режим literal:** каждый набор параметров — отдельный prepare с литералами
     (оптимизатор видит значения);
   - **режим prepared:** один statement-handle с `?`, исполняемый разными значениями
     (план зафиксирован).

   Разница планов (по хешу нормализованного плана) и времени между режимами = цена
   value-blindness — то, что KDE-системы вроде Kepler пытаются сэкономить. Метрики: число
   различных планов на шаблон, частота смены, регрессии >10 %.

4. **FB6-расширение:** CARDINALITY узлов vs значения параметров — воспроизведение Fig. 3
   статьи.

**Трудоёмкость:** (а) ~2 недели; (б) ~2–3 недели; (в) как самостоятельный эксперимент на
нашем корпусе — ~1 неделя.
**Риски:** архивный статус проекта; метки времени PG13 с базой в RAM непереносимы — берём
только шаблоны/параметры/алгоритм генерации параметров (`ORDER BY random() LIMIT n` по
distinct-значениям, range-пары из соседних значений).

**Ссылки:** [google/kepler](https://github.com/google/kepler) ·
[SIGMOD 2023](https://dl.acm.org/doi/abs/10.1145/3588963) · [arXiv:2306.06798](https://arxiv.org/abs/2306.06798) ·
[SPQD zip (2.7 ГБ, шаблоны ~1 МБ внутри)](https://storage.googleapis.com/gresearch/stack_parametric_query_dataset/stack_parametric_query_dataset.zip) ·
[rmarcus.info/stack.html](https://rmarcus.info/stack.html)

## 7. CH-benCHmark (P4)

**Суть** (Cole et al., DBTest 2011, «The mixed workload CH-benCHmark», DOI
10.1145/1988842.1988850; в BenchBase через OLTP-Bench). TPC-C (OLTP) + 22 аналитических
запроса (CH1–CH22, «TPC-H-эквивалент» на TPC-C-схеме + region/nation/supplier) в одной БД.
Код — Apache-2.0.

**Проверенные факты:** запросы в BenchBase — строковые константы в `Q1.java…Q22.java`
(извлекаются регуляркой, ~1 час); DDL — 9 диалектов; в запросах нет параметров, CTE,
оконных функций, INTERSECT/EXCEPT — предельно переносимы; единственная несовместимость
с FB5 — **`MOD(x,y)`** (заменить на `x-(x/y)*y`). Данные: TPC-C ≈ **0,6 млн строк
на склад** (не 10 млн!) → для объёма уровня TPC-H SF1 нужен W≈50–100 (30–60 млн строк).

**План.**

1. **S0:** зафиксировать BenchBase-коммит; извлечь Q1–Q22.
2. **Данные (без Java в рантайме):** разовый `--load --execute=false` BenchBase в PG
   (или Python-порт TPC-C-генератора — 2–5 дней, зато детерминированный; зафиксировать
   seed supplier'а, который в BenchBase случаен) → дамп CSV → наш loader. **W=50** для
   старта.
3. **S1–S5:** DDL = 9 таблиц TPC-C + 3 измерения; порт тривиален (MOD, проверка неявного
   приведения строковых литералов к timestamp).
4. **S6–S8:** обычный конвейер; все 22 запроса `deterministic: true`.
5. **Дрейф данных — отдельный тип прогона, вне базового плана:** read-only golden не умеет
   обновляться. Будущее расширение: рабочая копия read_write + батчи NewOrder/Payment
   (эмуляция OLTP нашим runner'ом, без BenchBase) + замеры до/после без `SET STATISTICS` —
   измерение устаревания статистики. Это новые механизмы (запись на golden-копию,
   восстановление после прогона) — закладывать как фазу 2 этого набора.

**Трудоёмкость:** **~1 неделя** (базовый статичный вариант).
**Риски:** ценность 22 простых запросов сама по себе скромна — основная ценность в новой
схеме (коррелированные ключи order_line/stock) и в заделе под дрифт-сценарий.

**Ссылки:** [cmu-db/benchbase](https://github.com/cmu-db/benchbase) ·
[wiki CH-benCHmark](https://github.com/cmu-db/benchbase/wiki/CH-benCHmark) ·
[DOI 10.1145/1988842.1988850](https://doi.org/10.1145/1988842.1988850) ·
[TUM project page](https://db.in.tum.de/research/projects/CHbenCHmark/?lang=en) ·
[OLTP-Bench paper](http://www.vldb.org/pvldb/vol7/p277-difallah.pdf)

## 8. LDBC SNB BI (P4 — самый дорогой)

**Суть** (Szárnyas et al., PVLDB 2022; спецификация v2.2.5 от 09.2024; совет переименован
в GDC). 20 параметризованных read-запросов: join-heavy паттерны, иерархии, **взвешенные
кратчайшие пути**, top-k; 38 choke points. Официальные реализации: neo4j (Cypher),
TigerGraph (GSQL) и **umbra (SQL в PostgreSQL-диалекте)** — последний наш источник текста.
Код Apache-2.0, данные CC BY-4.0.

**Данные (проверено):** предгенерированные снапшоты SF1–SF10000 (composite-merged-fk,
tar.zst+MD5) скачиваются с datasets.ldbcouncil.org — datagen не нужен вообще.
SF1: Person 10 620, Post 1,19 млн, Comment 2,39 млн — итого ~16–20 млн строк (~1–2 ГБ CSV).
Альтернатива — DuckDB community extension `ldbc_data_gen` (генерация BI-датасета прямо
в DuckDB без Spark — идеально для harness). Параметры запросов — готовые substitution
parameters SF1.

**Специфика порта (скан umbra-SQL):** `DISTINCT ON` в 4 запросах (→ GROUP BY/оконные);
`EXCEPT` в bi-10 (в FB5 есть); **bi-15, bi-19, bi-20 — рекурсивные CTE с ORDER BY/LIMIT
внутри рекурсии и агрегатами — в FB5 напрямую невоспроизводимы** → переписывать как
`EXECUTE BLOCK` с явным WHILE-BFS (5–10 дней) или исключить с записью (но это главная
фишка набора — 3 из 20 запросов определяют его ценность).

**План.**

1. **S0:** зафиксировать версию снапшота SF1 + substitution parameters.
2. **S1–S2:** своя FB-DDL по CSV (имена наши, CamelCase не обязан сохраняться); загрузка
   loader'ом.
3. **S5:** 17 запросов — порт umbra-SQL; 3 path-запроса — EXECUTE BLOCK (или excluded,
   решение по остатку бюджета).
4. **S6–S7:** PG-эталон из umbra-SQL (мелкие правки) — официального Postgres-эталона нет;
   сверка с yaml-описаниями запросов.
5. **S8 + контур:** по необходимости; SF1 всё, SF10 — кроме, возможно, path-запросов.

**Трудоёмкость:** **~3 недели**.
**Риски:** реляционных прецедентов BI мало (Umbra — единственный официальный SQL);
тяжёлые запросы даже для column-store; 20 запросов — малая выборка.

**Ссылки:** [страница BI](https://ldbcouncil.org/benchmarks/snb/bi/) ·
[PVLDB 2022](https://vldb.org/pvldb/vol16/p877-szarnyas.pdf) ·
[ldbc_snb_docs (bi-read-01..20.yaml)](https://github.com/ldbc/ldbc_snb_docs) ·
[ldbc_snb_bi (umbra/queries)](https://github.com/ldbc/ldbc_snb_bi) ·

## 9. CardBench (P4)

**Суть** (Chronis et al., arXiv:2408.16170, NeurIPS 2024 D&B — «не проверено» на
первоисточнике). 699 461 запрос над 20 реальными BigQuery-БД: 216 978 single-table
(1–4 предиката), 211 573 binary-join (по PK-FK, 1–3 предиката на таблицу), 270 910
multi-join. ML-пайплайн нам не нужен — только workload. Код Apache-2.0, данные CC BY 4.0.

**Ключевая находка:** запросы лежат в бакете
`gs://gresearch/CardBench_zero_shot_cardinality_training/cardbench_workloads_for_github/`
как **чистый исполняемый SQL** (`SELECT count(*) … WHERE col >= const`), один на строку;
BigQuery-специфика — только backticks и трёхчастные имена. **CSV-дампы 10 из 20 датасетов
реально выложены** (`datasets_complete_csv/`: accidents, airline, consumer, employee,
movielens, omop, covid19, bitcoin_cash, ethereum, openstreetmap) — проверено, row_count
CSV совпадает с schema.json. Для остальных 10 (включая stackoverflow/wikipedia/github/
tpch_10G) данных нет — их метки непереносимы (downsampling с неизвестным seed).

**План (вариант A — «CardBench как ещё 10 мини-БД»).**

1. **S0:** скачать CSV 10 датасетов (объёмы не задокументированы — начать с самого
   мелкого accidents: главная таблица 509 тыс. строк); **обязательная сверка row_count
   каждой таблицы против `<db>.schema.json`**.
2. **S1–S2:** DDL из готовых `create_tables_pg_oss.sql` (типы BIGINT/TEXT/DOUBLE/DATE —
   тривиальный порт); загрузка; golden-копии (10 маленьких БД — дёшево).
3. **S5:** `port_cardbench.py`: снять backticks, `bq-cost-models-exp.<db>.<table>` →
   `<table>`; prepare-тест; **сэмплировать** — 2–5 тыс. запросов на датасет, не 233 тыс.
4. **S6/истина:** вместо PG-эталона для COUNT(*) — **DuckDB** (быстрее), выборочная
   сверка с BigQuery-метками из npz-графов (расхождение = сигнал несовпадения
   данных/семантики); PG-эталон точечно для сомнительных.
5. **S7–S8 + контур:** новые сюиты `cardbench-<db>-single` / `cardbench-<db>-join`;
   теги `single_table`, `range_predicate`, `null_predicate`, `like_predicate`, `in_list`;
   ценность — широта однотабличной селективности и PK-FK join'ов по 10 новым предметным
   областям (сейчас таких нет, кроме IMDb/STATS).

**Трудоёмкость:** пилот (1–2 датасета) ~1 неделя; полный ~3–4 недели.
**Риски:** «TODO»-документация бакета (выгрузки могут быть неполными/исчезнуть — снять
локальную копию сразу); семантика строк/collation при сверке меток; смещение корпуса
(пустые и тяжёлые запросы уже отфильтрованы авторами).

**Ссылки:** [репозиторий](https://github.com/google-research/google-research/tree/master/CardBench_zero_shot_cardinality_training) ·
[arXiv:2408.16170](https://arxiv.org/abs/2408.16170) ·
[бакет gresearch](https://storage.googleapis.com/storage/v1/b/gresearch/o?prefix=CardBench_zero_shot_cardinality_training/&delimiter=/)

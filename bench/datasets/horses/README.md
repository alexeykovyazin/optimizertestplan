## Запросы

Все запросы возвращают одно число (`COUNT(*)`). Запрос 01 взят из отчёта о дефекте; запросы 02–08 — его
варианты, они отделяют конструкцию, на которой портится план.

| Запрос | Что проверяет |
|--------|---------------|
| `horses_fdb_01` | запрос из отчёта: `LATERAL` с оконной функцией и `FETCH FIRST`, затем `LEFT JOIN COVER` |
| `horses_fdb_02` | контроль: только `HORSE LEFT JOIN COVER` |
| `horses_fdb_03` | только `LATERAL`, без `COVER` |
| `horses_fdb_04` | `COVER` присоединена до `LATERAL` |
| `horses_fdb_05` | как 01, но `COVER` через `INNER JOIN` |
| `horses_fdb_06` | `LATERAL` без оконной функции (первая строка `REGISTRATION`), затем `LEFT JOIN COVER` |
| `horses_fdb_07` | `LATERAL` с агрегатом `MIN` без GROUP BY, затем `LEFT JOIN COVER` |
| `horses_fdb_08` | обычная производная таблица с GROUP BY вместо `LATERAL`, затем `LEFT JOIN COVER` |

Правило проверки плана: таблица `COVER` читается либо по индексу `FK_COVER_HORSE`, либо под узлом
`Hash Join (outer)`. Полное чтение `COVER` под `Nested Loop Join (outer)` — дефект: запрос не завершается.

Манифест строит `bench/harness/port_horses.py`.

## Первый прогон (23.11.2026, стенд dellg15)

Прогрев и один замер на запрос. Контрольные суммы результатов совпадают на обоих движках во всех завершённых
запросах. Движок «18.11» — сборка ветки `v5.0-impr-opt` от 18.11.2026; «23.11» — ветка PR 60 с PR 61–63.

| Запрос | 18.11, с | 23.11, с | Чтение `COVER` на 23.11 | Вывод |
|--------|----------|----------|-------------------------|-------|
| 01 | 9,85 | **не завершён за 120 с** | полное чтение под Nested Loop | **дефект 1** |
| 02 | 1,29 | 0,94 | Hash Join (outer) | норма |
| 03 | 9,50 | 8,84 | — | норма |
| 04 | 9,95 | 11,30 | Hash Join (outer) | норма |
| 05 | 10,83 | 10,77 | индекс `FK_COVER_HORSE` | норма |
| 06 | 4,53 | 4,35 | Hash Join (outer) | норма |
| 07 | 3,36 | 3,16 | Hash Join (outer) | норма |
| 08 | 3,96 | **54,07** | Hash Join (outer) | **дефект 2** |

- **Дефект 1 (запрос 01).** На сборке 18.11 `COVER` идёт через `Hash Join (outer)`, время равно времени
  ванильного Firebird из отчёта (9,96 с). На сборках с 21.11 вместо него стоит `Nested Loop Join (outer)` с
  полным чтением `COVER` на каждую строку `HORSE`. Граница по сборкам стенда: 20.11 11:07 — план верный,
  21.11 11:59 — план испорчен.
- **Дефект 2 (запрос 08).** План соединений тот же, но производная таблица с GROUP BY выполняется заново для
  каждой строки `HORSE` (578 228 раз), и в ней теперь стоит `Hash Aggregate` вместо сортировки. Время выросло в
  13,7 раза. Сборка от 22.11 до PR 58 даёт прежний план.

Файлы прогона: `reviews/2026-11-17_impropt/results/horses_1123/`.

# Десять запросов, которые выиграли от последних изменений (27.11.2026)

Задача: найти в наборах тестов запросы, которые могут выиграть от последних изменений ветки
`v5.0-impr-opt`, выбрать десять и сравнить три времени: PostgreSQL в одном процессе, Firebird до
изменений, Firebird с изменениями.

## Версии

- **База** — `v5.0-impr-opt`, коммит `2c5719ddff`.
- **Последняя** — вершина `v5.0-impr-opt` (`2a6a824a7d`) плюс pull request 83 и pull request 84
  репозитория hqbird. Это локальное слияние для замера; в репозиторий оно не отправлено.
- **PostgreSQL** 17.5, `max_parallel_workers_per_gather = 0`.

Что вошло в последнюю версию после базы:

| Изменение | Заметка | Где |
|---|---|---|
| Условие, которое есть в каждой руке `OR`, выносится из `OR` | 4.65 | в ветке (pull request 81) |
| Условие с подзапросом вычисляется после внутреннего соединения | 4.69 | pull request 83 |
| Поток с одним совпадением не считается | 4.67 | pull request 84 |
| Таблица без ссылок идёт на хешируемую сторону | 4.68 | pull request 84 |
| Только для чтения: распаковка начала записи до последнего нужного поля | — | в ветке, `2a6a824a7d` |

## Результат

Время в секундах, медиана трёх измерений. Лимит одного запроса 200 с.

| Запрос | PostgreSQL, 1 процесс | Firebird, база | Firebird, последняя | Выигрыш |
|---|---|---|---|---|
| DSB 010 (вариант 3) | 1,82 | >200 | 0,10 | >1900 раз |
| DSB 069 (вариант 3) | 0,74 | >200 | 0,11 | >1800 раз |
| JCC-H 21 (обычные данные) | 1,07 | >200 | 2,06 | >97 раз |
| DSB 094 (вариант 3) | 0,58 | >200 | 17,9 | >11 раз |
| TPC-H 19 | 1,17 | 28,7 | 1,80 | 16 раз |
| JCC-H 19 (перекошенные данные) | 1,16 | 28,4 | 1,81 | 16 раз |
| JCC-H 19 (обычные данные) | 1,23 | 26,1 | 1,66 | 16 раз |
| TPC-H 21 | 1,34 | 15,9 | 3,11 | 5,1 раза |
| DSB 085 (вариант 3) | 0,14 | 0,94 | 0,20 | 4,6 раза |
| DSB 013 (вариант 3) | 1,05 | 3,51 | 1,05 | 3,3 раза |

Что видно:

- Четыре запроса не укладывались в лимит на базе. Теперь они выполняются.
- DSB 010 и DSB 069 теперь быстрее PostgreSQL в одном процессе. DSB 013 сравнялся с ним.
- Запросы 19 и 21 остаются медленнее PostgreSQL в 1,3–2,3 раза.
- DSB 094 остаётся медленнее PostgreSQL в 31 раз. Его `EXISTS` читает `WEB_SALES` целиком для каждой
  строки. Нужно полусоединение хешем; это отдельный пункт плана `PLAN-tpch-gap.md`.

## Как выбраны запросы

1. На обеих сборках подготовлены все 600 запросов наборов: TPC-H (22), JCC-H (44), DSB (230),
   CEB (121), JOB (113), JOB-light (70). Сохранены планы.
2. Планы сравнены без оценок числа строк. Различия разделены на классы.
3. В десятку взяты запросы, у которых изменились соединения или место фильтра. У запроса DSB взят
   третий вариант из пяти (одно правило для всех).

Классы различий:

| Класс | Запросов | Что изменилось |
|---|---|---|
| Вынос условия из `OR` | 13 | TPC-H 19, JCC-H 19 (2), DSB 013 (10 вариантов): hash join вместо чтения по индексу для каждой строки |
| Место условия с подзапросом и условие `OR` | 28 | TPC-H 21, JCC-H 21 (2), DSB 010, 069, 085, 094: фильтр перенесён выше соединения |
| Узел `Count` или отметка `counted streams` | около 340 | узел или отметка убраны, порядок соединений тот же |

Вне десятки остался один запрос с изменённым местом фильтра: JCC-H 21 на перекошенных данных. По замеру
`OR-SUBQ-2026-11-27.md` он не укладывается в лимит и до, и после изменений.

## Изменения без запроса в десятке

- **Таблица без ссылок на хешируемой стороне (заметка 4.68).** Правило не сработало ни в одном из 600
  запросов: старый текстовый план изменился только у запросов с `OR`.
- **Поток с одним совпадением не считается (заметка 4.67).** План стал короче у около 340 запросов.
  Время этих запросов не измерялось: порядок соединений тот же.
- **Частичная распаковка записи.** План не меняется, поэтому взяты два запроса с полным чтением
  `LINEITEM`: TPC-H 1 — 7,28 → 7,06 с, TPC-H 6 — 1,43 → 1,35 с. Это 3–5 %; разброс измерений одного
  запроса в этом замере до 1,26 раза, то есть разница в пределах шума.

## Проверка результата

- Число строк и контрольные суммы результата совпадают на обеих сборках у каждого запроса, который
  выполнился на базе.
- Число строк совпадает с PostgreSQL у всех двенадцати запросов.
- Ошибок подготовки нет ни у одного из 600 запросов на обеих сборках.

## Что не проверено

- Локальное слияние pull request 83 и pull request 84 не проходило набор регрессионных тестов. Код двух
  pull request сливается без конфликтов. Конфликт есть только в двух файлах документации: оба вставляют
  заметки в конец раздела 4.
- Запросы с изменением только узла `Count` не измерены.

# TPC-H SF1: где Firebird отстаёт от PostgreSQL и как закрыть разрыв (24.11.2026)

Сравнение: PostgreSQL 17.5 и Firebird (HQbird 5.0.5), ветка оптимизатора `v5.0-impr-opt`, коммит `ddd4169f9a`.
Вторая колонка Firebird: ветка `v5.0-release` с PR 71 (хеш-соединение внешних соединений).
Обе СУБД работают **на одной машине** (стенд dellg15), на одних данных, с одинаковыми индексами (только первичные ключи).
Изменений в коде движка нет. Это разбор и план.

**Обновление 26.11.2026.** Firebird замерен заново с настройками, равными PostgreSQL: `DefaultDbCachePages = 128K`
и `UseFileSystemCache = true`. Все времена Firebird в документе — из этого прогона. Планы и результаты запросов не
изменились. Сравнение с первым прогоном — в разделе «Паритет настроек».

## Вывод

1. **Разрыв.** На 19 запросах, которые выполняют обе СУБД: PostgreSQL 11,7 с (параллельные процессы) и 23,4 с
   (без параллельных процессов), Firebird `v5.0-impr-opt` 103,5 с, Firebird `v5.0-release` + PR 71 108,1 с.
   Отношение: **8,9 раза** к параллельному PostgreSQL, **4,4 раза** к PostgreSQL в один процесс.
2. **Три запроса Firebird не выполняет за 600 с**: 17, 20, 22. PostgreSQL не выполняет 17 (более 1800 с) и 20
   (более 300 с), а запрос 22 выполняет за 0,3 с.
3. **Около 63 с из 103 с — это оптимизатор и вычисление выражений, а не скорость чтения.** Это измерено: запросы
   переписаны вручную так, как их должен переписать оптимизатор. Сумма 19 запросов падает с 103,5 до 40,8 с.
4. **Основные причины (Парето):**
   - **Условие `OR` не разбирается** (запросы 19 и 7): 31,5 с.
   - **Константные выражения** `CAST('...' AS DATE)` и `DATEADD(...)`: 16,4 с на 11 запросах. Причин две.
     Выражение вычисляется заново на каждой строке. И оценка диапазона не считает его константой.
     Из них 1,5 с — запрос 7, он же входит в предыдущий пункт; сумма 63 с посчитана без повтора.
   - **Подзапрос-условие проверяется до селективных соединений** (запрос 21): не меньше 9,8 с.
   - **Полусоединение всегда выполняется последним** (запрос 18): 4,6 с.
   - **Нет анти-соединения** для `NOT EXISTS` (запрос 22) и **нет раскрытия коррелированного агрегатного
     подзапроса** (запросы 17, 20): эти запросы не заканчиваются.
5. **Остаток — исполнение.** После всех правок Firebird остаётся в 1,7 раза медленнее PostgreSQL в один процесс
   (40,8 с против 23,4 с). Пример: запрос 6 (один полный просмотр `LINEITEM`) с литералами дат идёт 1,64 с,
   PostgreSQL в один процесс 0,80 с, с параллельными процессами 0,28 с. План у них одинаковый.
6. **Новая сборка не понадобилась.** Вершина `origin/v5.0-impr-opt` (`13d75d9106`) отличается от `ddd4169f9a` одним
   коммитом: ограниченная сортировка для `FETCH FIRST` / `ROWS`. В запросах стенда нет ограничения числа строк.
   После написания плана в ветку добавлено ещё 5 коммитов (вершина `631465affc`): заявленная кардинальность
   процедур, файлы `src/jrd/extstat/*` и `src/dsql/DdlNodes.epp`. В TPC-H процедур нет; эта сборка не запускалась.
7. **Паритет настроек (26.11.2026).** С кэшем 128K страниц и кэшем файловой системы ветка идёт 103,5 с вместо
   114,9 с, `v5.0-release` + PR 71 — 108,1 с вместо 133,9 с. Отрыв ветки от mainline уменьшился с 19 с до 4,6 с.
   Причина: в запросах 21, 10 и 12 план mainline (доступ по первичному ключу) быстрее плана ветки на 9,3 с.

- планы `EXPLAIN ANALYZE` сняты под чужой нагрузкой: часть параллельных процессов не запустилась (`Workers Launched`

## Причины по запросам

Число строк «факт» взято из `EXPLAIN ANALYZE` PostgreSQL: данные одинаковые. Номера строк исходников — по вершине
`origin/v5.0-impr-opt` (`13d75d9106`), репозиторий hqbird.

### Запрос 19: общее равенство внутри `OR` (28,7 с против 1,2 с)

Условие запроса: три ветки `OR`, в каждой есть `p_partkey = l_partkey`. План Firebird:

```
Nested Loop Join (inner) (rows=17842615.56)
    -> Table "LINEITEM" Full Scan (rows=6001215.00)
    -> Filter -> Table "PART" Access By ID
           -> Bitmap Or -> Bitmap Or -> Index "PART_PK" Unique Scan (три раза)
```

Firebird читает все 6 млн строк `LINEITEM` и для каждой делает три поиска в `PART_PK`. Оценка 17,8 млн строк неверна,
факт 101 строка. План PostgreSQL:

```
Hash Join  Hash Cond: (lineitem.l_partkey = part.p_partkey)   Join Filter: исходное OR
  -> Seq Scan on lineitem (act=120140)  Filter: l_shipmode = ANY(...) AND l_shipinstruct = ... AND (диапазоны l_quantity через OR)
  -> Hash -> Seq Scan on part (act=489)  Filter: p_size >= 1 AND (три ветки по p_brand, p_container, p_size)
```

PostgreSQL выносит общее равенство из `OR` и строит из `OR` условия по каждой таблице. Проверка по коду:
`Optimizer::decomposeBoolean` (`src/jrd/optimizer/Optimizer.cpp`, строка 3421) кладёт `OR` в список условий одним
элементом. Общие члены веток не ищутся.

### Запрос 7: условия на таблицы внутри `OR` (6,1 с против 0,8 с)

Условие: `(n1.n_name = 'JAPAN' and n2.n_name = 'JORDAN') or (n1.n_name = 'JORDAN' and n2.n_name = 'JAPAN')`.
Firebird не знает, что `N1` и `N2` отфильтрованы:

```
Hash Join -> Hash Join -> Hash Join
    -> Hash Join (ORDERS Full Scan 1500000, CUSTOMER, N2 без фильтра)
    -> Record Buffer (record length: 57) (rows=2943032.31) -> Filter -> Table "LINEITEM" Full Scan
```

В буфер идёт 1,8 млн строк `LINEITEM`, условие `OR` проверяется в самом конце. PostgreSQL выводит
`n2.n_name = 'JORDAN' OR n2.n_name = 'JAPAN'` (2 строки), получает 11 981 клиента и 120 141 заказ, и читает
`LINEITEM` по первичному ключу.

### Запрос 21: подзапрос-условие до соединений (16,9 с против 1,5 с)

`EXISTS (L2)` и `NOT EXISTS (L3)` содержат неравенство с внешней таблицей, поэтому остаются подзапросами. Это верно:
PostgreSQL тоже выполняет их вложенным циклом по первичному ключу. Разница в месте проверки:

```
Firebird:   Filter (rows=1784171.89) -> Table "LINEITEM" as "L1" Full Scan (rows=6001215.00)
PostgreSQL: Nested Loop Anti (loops=151237) над Hash Join(l1, supplier + nation 'VIETNAM')
```

Firebird проверяет оба подзапроса на каждой строке `L1`, прошедшей `l_receiptdate > l_commitdate` (факт 3,79 млн
строк). PostgreSQL сначала соединяет с `SUPPLIER` и `NATION` (остаётся 151 237 строк), потом проверяет подзапросы.
Оценка фильтра подтверждает, что три условия стоят вместе: 0,5 × 0,5^(1/2) × 0,5^(1/4) = 0,297, в плане
1 784 172 / 6 001 215 = 0,297. Проверка по коду: `Optimizer::generateRetrieval` (`Optimizer.cpp`, цикл по условиям
около строки 6063) ставит на просмотр потока каждое условие, которое вычисляется по одному этому потоку. Цена условия
не учитывается.

В `v5.0-release` план другой: полный просмотр `ORDERS` с фильтром `o_orderstatus = 'F'`, затем `L1` по первичному
ключу, затем `SUPPLIER` и `NATION`. Подзапросы проверяются на меньшем числе строк `L1`. С кэшем 128K страниц этот
план идёт 9,4 с, план ветки — 16,9 с. С кэшем 50 000 страниц разница была меньше (14,7 с против 16,8 с).

Тот же дефект в запросе 20: скалярный подзапрос стоит в фильтре над `PARTSUPP` (800 тыс. строк), до полусоединения с
`PART`, которое оставляет около 8,5 тыс. строк.

### Запрос 18: полусоединение последним (6,7 с против 2,2 с)

```
Hash Join (semi)
    -> Batch Hash Join (inner) (batches: 16)            <- 1,5 млн заказов × 6 млн строк LINEITEM
    -> Record Buffer -> Filter (rows=754656.00) -> Hash Aggregate -> Table "LINEITEM" Full Scan
```

Подзапрос `IN (select l_orderkey ... group by l_orderkey having sum(l_quantity) > 312)` даёт 10 строк. Firebird
сначала соединяет все заказы со всеми строками `LINEITEM`, и только потом применяет полусоединение. PostgreSQL
превращает полусоединение в обычное соединение (ключ подзапроса уникален из-за `GROUP BY`) и начинает с этих 10 строк.
Проверка по коду: `RseNode::processPossibleJoins` (`src/jrd/RecordSourceNodes.cpp`, строка 4777) оборачивает **весь**
исходный запрос и подзапрос в новый узел с флагом `FLAG_SPECIAL_JOIN`. `Optimizer::compile` (`Optimizer.cpp`,
строки 1222–1246) добавляет подзапрос после того, как все внутренние соединения собраны в одну реку.

### Запрос 22: нет анти-соединения (более 600 с против 0,3 с)

```
Sub-query -> Filter (rows=10.00) -> Table "ORDERS" as "CUSTSALE ORDERS" Full Scan (rows=1500000.00)
```

`NOT EXISTS (select * from orders where o_custkey = c_custkey)` выполняется полным просмотром `ORDERS` на каждого из
13 597 клиентов. PostgreSQL: `Hash Join Right Anti`. Проверка по коду: `findPossibleJoins`
(`RecordSourceNodes.cpp`, строка 151) принимает только `blr_any` и `blr_ansi_any`, то есть `EXISTS` и `IN`.
`NOT EXISTS` — это `NotBoolNode` над `RseBoolNode`, его функция не видит. `Optimizer::compile` ставит только
`SEMI_JOIN` (строка 1231). **Исполнитель анти-соединение уже умеет**: `HashJoin` (`src/jrd/recsrc/HashJoin.cpp`,
строки 745–766) и `NestedLoopJoin` обрабатывают `ANTI_JOIN`.

Запрос 16: `NOT IN (select s_suppkey ...)` выполняется подзапросом с двумя поисками по `SUPPLIER_PK` на каждую строку.
PostgreSQL использует хешированный подплан.

### Запросы 17 и 20: коррелированный агрегатный подзапрос (обе СУБД не справляются)

```
Sub-query -> Singularity Check -> Aggregate -> Filter (rows=29.74) -> Table "LINEITEM" Full Scan (rows=6001215.00)
```

`l_quantity < (select 0.2 * avg(l_quantity) from lineitem where l_partkey = p_partkey)`: индекса по `l_partkey` нет,
подзапрос читает всю `LINEITEM` на каждую строку. PostgreSQL строит такой же план (`SubPlan` с `Seq Scan on
lineitem`) и тоже не заканчивает. Раскрытие подзапроса в соединение с группировкой даёт Firebird преимущество перед
PostgreSQL.

### Запросы 10, 12, 4: оценка диапазона дат

Оценка `ORDERS` в запросе 10: 677 532 строки, факт 56 434. Из-за этого оптимизатор берёт хеш-соединение и кладёт в
буфер 1,48 млн строк `LINEITEM`:

```
Hash Join (inner) -> ... ORDERS, CUSTOMER, NATION ...
    -> Record Buffer (record length: 49) (rows=1504904.68) -> Filter -> Table "LINEITEM" Full Scan
```

В `v5.0-release` здесь доступ к `LINEITEM` по первичному ключу, и запрос идёт 2,9 с вместо 4,2 с. Причин две, обе
проверены по коду:

- `ExtStatistics::prepareLiteral` (`src/jrd/extstat/ext_stats.cpp`, строка 141) принимает только цепочку `CAST` над
  литералом. `DATEADD(3 MONTH TO CAST('1993-04-01' AS DATE))` не принимает, эта граница получает оценку 0,5.
- `Optimizer::isInvariantValue` (`src/jrd/optimizer/Optimizer.h`, строка 523) считает константой только литерал,
  параметр и переменную. `CAST('1993-04-01' AS DATE)` — узел `CastNode`, поэтому
  `Optimizer::computeConjunctSelectivities` (`Optimizer.cpp`, строка 2706) не объединяет две границы в один диапазон.
  Границы оцениваются по отдельности и перемножаются с поправкой на корреляцию: 0,229 × 0,816^(1/2) = 0,207. Факт 0,038.

Замер с литералами `DATE '...'` в обеих границах: оценка 57 279 строк, план меняется на доступ по первичному ключу,
время 2,4 с.

### Константы вычисляются на каждой строке

Запросы 4 и 6 с литералами дат идут быстрее **при том же плане**: 0,99 → 0,48 с и 3,55 → 1,64 с. Проверка по коду:
`CastNode::execute` (`src/dsql/ExprNodes.cpp`, строка 3685) вычисляет аргумент и преобразует его при каждом вызове.
Кэш неизменного значения (`FLAG_INVARIANT`) среди узлов-значений есть только у `SubQueryNode`, `SubstringSimilarNode`
и `UdfCallNode`; среди условий — у `ComparativeBoolNode` (шаблон `LIKE` / `CONTAINING` / `SIMILAR`).
Поэтому `CAST('1997-01-01' AS DATE)` (строка в дату) и `DATEADD` выполняются 6 млн раз за просмотр. PostgreSQL
сворачивает такие выражения при планировании: в его планах стоит `'1998-01-01 00:00:00'::timestamp`.

### Запросы 9 и 8: порядок хеш-соединений

Запрос 9: `LINEITEM` (6 млн строк) соединяется хешем с `SUPPLIER`, потом с `NATION`, и только третьим — с `PART`,
где фильтр оставляет 5,4 % строк. Все 6 млн строк проходят два лишних поиска. С `JoinOrderDP = true` `PART` идёт
первым: 5,30 → 3,57 с. Запрос 8 с `JoinOrderDP` получает план PostgreSQL (`LINEITEM` + `PART`, затем `ORDERS` и

### 1. Константные выражения

- **Доказательство.** 11 запросов с литералами `DATE '...'` вместо `CAST` и `DATEADD`: 41,9 → 25,5 с, результаты те
  же. План меняется только в трёх запросах (10, 12, 14). В остальных восьми выигрыш даёт одно вычисление константы.
- **Что менять.**
  - Исполнение: выражение без ссылок на поля, параметры времени и недетерминированные функции вычислять один раз
    на выполнение запроса. Механизм есть: `FLAG_INVARIANT` и `csb_invariants`, как в `SubQueryNode::pass2`
    (`src/dsql/ExprNodes.cpp`, строка 11438). Добавить его в `CastNode::pass2`, `SysFuncCallNode`, `ArithmeticNode`.
  - Оценка: `Optimizer::isInvariantValue` (`Optimizer.h`, строка 523) должна принимать такое выражение.
    `ExtStatistics::prepareLiteral` (`ext_stats.cpp`, строка 141) должна вычислять его значение при компиляции.
- **Осторожно.** `CAST('TODAY' AS DATE)` и `CAST('NOW' AS TIMESTAMP)` зависят от времени выполнения. Их можно

- **Проверка.** Планы и времена запросов 4, 6, 10, 12, 14, 15 должны совпасть с вариантами `rw4_NN.sql`. Тест:

### 2. Условие `OR`: общие члены и условия по таблицам

- **Доказательство.** Запрос 19, переписанный вручную: 28,7 → 1,8 с. Запрос 7 с добавленными `n1.n_name in (...)` и
  `n2.n_name in (...)`: 6,1 → 1,5 с. Результаты те же.
- **Что менять.** `Optimizer::decomposeBoolean` (`Optimizer.cpp`, строка 3421), ветка `blr_or`:
  - разложить каждую ветку `OR` на члены `AND`; члены, которые есть во всех ветках (сравнение через `sameAs`),
    вынести в общий список условий. Так `p_partkey = l_partkey` становится ключом хеш-соединения;
  - для каждого потока: если в каждой ветке есть члены только по этому потоку, добавить выведенное условие
    `OR` по этому потоку. Исходное `OR` остаётся фильтром соединения.
- **Осторожно.** Выведенное условие повторяет часть исходного. Его селективность нельзя умножать второй раз на
  уровне соединения. PostgreSQL решает это поправкой селективности исходного условия
  (`extract_restriction_or_clauses`).
- **Проверка.** Планы запросов 19 и 7: хеш-соединение по `l_partkey` и фильтры на `N1`, `N2`. Времена как у
  `rw_19.sql` и `rw_07.sql`. Прогон JCC-H и DSB на регрессии.

### 3. Место проверки подзапроса-условия

- **Доказательство.** Запрос 21, где подзапросы вынесены выше соединений: 16,9 → 7,1 с. В этом варианте порядок
  соединений хуже, чем в исходном плане, поэтому 7,1 с — верхняя граница. Ожидаемое время с исходным порядком:
  около 5 с (оценка, замера нет). План `v5.0-release` без этой правки идёт 9,4 с.
- **Что менять.** `Optimizer::generateRetrieval` (`Optimizer.cpp`, строка 5918): условие с `RseBoolNode` или
  `SubQueryNode` не ставить на просмотр потока, если после него идут соединения, которые уменьшают число строк.
  Ставить такое условие после последнего уменьшающего соединения реки. Простой первый шаг: откладывать такие условия
  до `generateResidualBoolean`, когда оценка числа строк после соединений меньше числа строк потока.
  Второй шаг: внутри одного фильтра дешёвые условия проверять раньше дорогих.
- **Осторожно.** Если соединения увеличивают число строк, раннее место лучше. Нужно сравнение оценок.
- **Проверка.** Запрос 21: подзапросы выполняются около 151 тыс. раз вместо 3,8 млн (счётчик чтений по
  `LINEITEM_PK`). Запрос 20: подзапрос стоит после полусоединения с `PART`.

### 4. Анти-соединение

- **Доказательство.** Запрос 22, где `NOT EXISTS` записан как `LEFT JOIN ... WHERE o_orderkey IS NULL`: 0,80 с,
  результат совпадает с PostgreSQL.
- **Что менять.** `findPossibleJoins` (`RecordSourceNodes.cpp`, строка 151): принимать `NotBoolNode` над
  `RseBoolNode(blr_any)`. `RseNode::processPossibleJoins`: передавать признак анти-соединения.
  `Optimizer::compile` (`Optimizer.cpp`, строка 1231): ставить `ANTI_JOIN`. Исполнитель менять не нужно.
- **Осторожно.** `NOT IN` при `NULL` ведёт себя иначе, чем `NOT EXISTS`. Преобразовывать `NOT IN` только когда обе
  стороны ключа объявлены `NOT NULL`. Нужна оценка числа строк анти-соединения.
- **Проверка.** План запроса 22: `Hash Join (anti)`. Тесты на `NULL` в ключах с обеих сторон.

### 5. Полусоединение в порядке соединений

- **Доказательство.** Запрос 18 с соединением вместо `IN`: 6,7 → 2,1 с. PostgreSQL в один процесс: 2,2 с.
- **Что менять.** Шаг 1: если ключ подзапроса уникален (`GROUP BY` по ключу, `DISTINCT`, первичный ключ), делать его
  обычным участником внутреннего соединения в `RseNode::processPossibleJoins`. Тогда поиск порядка сам поставит его
  первым. Шаг 2: общий случай — река полусоединения участвует в выборе порядка в `Optimizer::compile`.
- **Осторожно.** Оценка `HAVING` сейчас 0,5 (754 656 строк при факте 10). С такой оценкой порядок может не
  измениться; в переписанном запросе он изменился.
- **Проверка.** План запроса 18 начинается с группировки `LINEITEM`.

### 6. Раскрытие коррелированного агрегатного подзапроса

- **Доказательство.** Запросы 17 и 20, переписанные как соединение с производной таблицей с `GROUP BY`: 4,8 с и
  4,6 с. Результаты совпадают с PostgreSQL на тех же переписанных запросах (PostgreSQL: 3,3 с и 1,5 с).
- **Что менять.** Новое преобразование рядом с `RseNode::processPossibleJoins`: условие
  `выражение оператор (select агрегат from T where T.k = внешнее.k and ...)` заменить внутренним соединением с
  `(select k, агрегат from T where ... group by k)`. Хеш-группировка и хеш-соединение рек в ветке уже есть.
- **Условия.** Корреляция только равенствами. Агрегат не `COUNT` (для пустой группы `COUNT` даёт 0, а соединение
  теряет строку). Условие отбрасывает `NULL`. Выбор по цене: раскрывать, когда подзапрос не имеет индекса по ключу
  корреляции. В запросе 2 подзапрос идёт по индексу, и раскрывать его не нужно (0,19 с).
- **Осторожно.** Внешнее хеш-соединение сейчас хеширует только таблицу, не выражение (раздел 4.11 заметок). Поэтому
  нужна форма с внутренним соединением.
- **Проверка.** Запросы 17 и 20 заканчиваются; результат равен результату `rw_17.sql` и `rw_20.sql`.

### 7. `JoinOrderDP` по умолчанию

- **Доказательство.** Запрос 9: 5,30 → 3,57 с. Запрос 8: 1,63 → 1,56 с. Остальные планы TPC-H не меняются, кроме

### 8. Сторона хеш-таблицы

- **Что менять.** `InnerJoin::estimateCost` и `InnerJoin::formRiver`: разрешить хешировать уже собранную часть, если
  она меньше нового потока. `OuterJoin`: правое внешнее хеш-соединение (хешировать сохраняемую сторону, отмечать

- **Выигрыш** не измерен. Оценка для запроса 13: с 2,4 с до примерно 1,5 с.

### 3.3. Исполнение Batch Hash Join (7a)

- Батчи делят только 8‑байтовые массивы `{position, hash}`, не записи. Каждый из 8 батчей читает
  весь буфер ведущей стороны вразброс → I/O ×8. Батчинг уменьшает хэш‑таблицу, но не улучшает
  локальность.
- `partition()` сначала сканирует хэшируемую сторону, даже если ведущая пуста (plain HJ строит
  хэш только на первой строке лидера).
- Слоты BufferedStream фиксированной ширины: VARCHAR хранится по максимальной длине + все поля
  всех потоков → 4798 байт на строку. Нет режима refetch (ключи + DBKEY).
- Запись лидера восстанавливается (`locate` + `getRecord`) **до** проверки точного хэша
  (`BatchHashJoin.cpp:265-271`).
- `TempCacheLimit` (1 ГБ) вмещает ~200k строк по 4798 байт, дальше — чтения из файла.
- `equiMatches` объявлен вне цикла по потокам (`InnerJoin.cpp:703`): соединение получает все
  предыдущие условия, O(k²) проверок, и каждое проверяется дважды.
- Число батчей фиксировано по оценке, не адаптируется к реальному объёму.

## 4. Методология и процесс

1. **Сравнивать каждый прогон с бейслайном и с PG**, не только с предыдущим прогоном. PG‑эталон
   (121 JSON с истинными кардинальностями) есть только локально:
   `E:\Projects_Big\optimizertestplan\results\ceb-imdb-regen_pg_reference\` — положить в репозиторий.
2. **Бейслайн несимметричен**: кеш 2048/256M против 50000/2000M. Перемерить стоковый HQbird в той же среде.
3. **Мерить q‑error по узлам плана.** В ветке уже есть `rows=` в EXPLAIN, а PG‑JSON даёт истинные
   размеры подпланов. Это прямая мера «уровня PG» для оценок, без шума времени исполнения.
4. **Прогонять не только CEB.** JOB, JOB‑light, TPC‑H, DSB, JCC‑H уже портированы. Калибровка под
   один корпус даёт «качели» (121/121 планов меняются за прогон).
5. **Нет функциональных регрессионных тестов.** Падение на `HAVING` без `GROUP BY` прошло незамеченным.
   Нужен минимальный набор (firebird‑qa стиль): агрегаты без GROUP BY, LEFT JOIN с не‑equi ON,
   ORDER BY + большой JOIN, NUMERIC со scale, DDL статистики, кодировка NONE.
6. **Константы калиброваны на одной машине и зашиты в код** (`Optimizer.h:66-126`). Вынести в
   конфиг или хотя бы в одну таблицу; калибровать по нескольким машинам.
7. **Документация отстаёт**: модель стоимости (7e52b410a5, f4bd6be7fa, b34f7dbb47) и BHJ (be3c956409)
   не описаны в `README.optimizer-improvement.md`.
8. **Гигиена коммитов**: сообщения по 1–2 КБ одной строкой, коммит «correction», пары коммит/revert.
   Короткий заголовок + тело упростят ревью и bisect.

### Этап 1 — корректность модели стоимости (≈1 неделя)
1. **Главный переключатель**: новая модель стоимости только при `ExtendedStatistics=true`
   (или отдельный `OptimizerCostModel = legacy | new`). Без статистики — стоковое поведение.
2. `leafCount` = оценка всех листьев (произведение fan‑out уровней или из `idx_selectivity`/gstat‑данных).
3. Ширина записи в цене HJ/BHJ: build и probe ∝ байтам; у BHJ — запись и чтение лидера, проход партиционирования.
4. BHJ — внутри перебора порядков с честной ценой и альтернативой NL; не по порогу `maxCapacity`.
5. Детерминированный тест спила: по `TempCacheLimit`, не по текущей занятости.
6. Копировать `scratch` в `makeInversion`; убрать двойной учёт локальных фильтров (C5, C7);
   пол кардинальности соединения ≥1 и LEFT JOIN ≥ внешней стороны.
7. Цена случайной страницы с учётом кэша (аналог `effective_cache_size`: доля таблицы в page buffers).
8. Проверка: CEB + JOB + TPC‑H + DSB, сравнение с бейслайном и PG, q‑error. Цель — 7a и 8a не хуже бейслайна.

### Этап 2 — оценки до уровня PG (2–3 недели)
1. **LIKE/CONTAINING как в PG**: применять шаблон к значениям MCV и к выборке границ гистограммы

2. Полная формула `eqjoinsel` (E4), убрать двойной NULL (E5), `sampleFraction` (E6), исправить E7/E8.
3. FK fanout с перекосом (E2): при фильтре внешней стороны брать частоты FK‑колонки из MCV

4. Порядок соединений (E3): динамическое программирование для ≤10–12 потоков (как PG до

### Этап 3 — исполнение BHJ (1–2 недели, параллельно этапу 2)
1. Физическое разбиение записей по батчам (grace hash join): каждый батч пишется и читается последовательно.

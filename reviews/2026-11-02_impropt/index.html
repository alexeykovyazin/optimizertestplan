Ревью оптимизатора v5.0-impr-opt

Изменения оптимизатора за 06.10–02.11.2026: ошибки, причины регрессов на IMDb CEB и план, как дойти до уровня PostgreSQL.

80 файлов +20 096 / −817 строк 91 коммит база сравнения e605bad332 данные: results/ceb_full_1102

1Главное

  • Прогресс есть. На CEB (121 запрос) среднее геометрическое FB / PostgreSQL 17.5 упало с 4.22 (стоковый HQbird) до 2.77 (прогон 5). До уровня PG остаётся примерно ×2.8.
  • Отчёт прогона 5 не показывает регрессы. Он сравнивает только с прогоном 4. Против стокового HQbird группа 8a медленнее в ×2.36 (3 таймаута при 272/138/61 с в бейслайне), 7a — в ×2.20, 11a — в ×1.18.
  • Простой SQL роняет процесс. select count(*) from t having count(*) > 0 падает на сборке от 02.11 при конфиге по умолчанию (S1). В SuperServer падает весь сервер.
  • ExtendedStatistics=false не возвращает старое поведение. Новые константы стоимости, полы кардинальности, BHJ и тест спила работают всегда. Все пользователи релиза получат новую модель стоимости, даже без статистики.
  • Главные причины регрессов: цена hash join не учитывает ширину записи (C2), leafCount индекса неверный (C1), оценки падают до 0.00 из-за двойного учёта фильтров (C4, C5), оценка CONTAINING почти не зависит от длины подстроки (E1), FK fanout берётся как среднее (E2).

3Ошибки корректности и стабильности

Метки: тест — воспроизведено на локальной сборке output_x64_release от 02.11 (embedded isql); код — путь выполнения прослежен по коду; подозрение — нужен тест. Номера строк — на HEAD da654eb492.

Критические и высокие — исправить до любого релиза

  • S1критичнотест

    Падение процесса на агрегате без GROUP BY

    RecordSourceNodes.cpp:1895 · AggregateSourceNode::getGroupCountCap

    group->expressions читается без проверки group != NULL. Запросы select count(*) from t having count(*) > 0 и select * from (select max(x) m from t) where m > 0 убивают процесс (rc=3). С GROUP BY всё работает. Вызов идёт из Optimizer.cpp:3094, 4398 без проверки ExtendedStatistics.

  • S2критичнокод

    Разыменование NULL при диапазоне по колонке без статистики

    extstat/StatisticsCache.cpp:465

    column->dtype читается до проверки !column (строка 468). Диапазонный предикат по колонке, которой нет в STAT$COLUMNS (например, добавлена после REFRESH), роняет сервер при prepare. Нужен ExtendedStatistics=true.

  • S3высококод

    BINS стал зарезервированным словом

    dsql/parse.y · common/ParserTokens.h

    BINS нет в non_reserved_word, в ParserTokens.h у него флаг false. create table t (bins int), а также старые базы и приложения с колонкой BINS перестают компилироваться.

  • S4высококод

    REFRESH … SAMPLE выполняет полный SCAN

    dsql/parse.y:4676

    У ветки SAMPLE нет action, режим остаётся 1 (SCAN) из конструктора. Дешёвого режима для больших баз нет, весь код !exactCounts мёртвый и не тестировался. После правки оживут E6 и ошибки оценки ND по выборке.

  • S5высококод

    Масштаб NUMERIC/DECIMAL не хранится

    extstat/StatisticsCache.cpp:1113–1127 · extstat/ext_stats.cpp:271

    В STAT$COLUMNS нет scale, CachedColumn.scale всегда 0. Для NUMERIC(9,2) условие price = 12.34 ищется в MCV как raw 12, а там лежит 1234. Диапазоны ошибаются в 10scale раз. В IMDb таких колонок нет, поэтому CEB этого не видит.

  • S6высококод

    Нет existence lock при выборочном сканировании

    recsrc/SamplingScan.cpp:62

    CMP_post_resource вызывается без MET_post_existence. Параллельный DROP TABLE освобождает страницы во время сбора. При commit счётчик использования уменьшается у чужого владельца.

  • S7высококод

    Старые форматы записи читаются без конвертации

    extstat/Collector.cpp:113–147, 1951

    Значение берётся из формата версии записи, а дескриптор — из текущего формата. После ALTER COLUMN TYPE (INTEGER→BIGINT, INTEGER→VARCHAR) 4 байта читаются как int64 или как varying с мусорной длиной: чтение за границей, мусор в MCV и гистограмме.

  • S8высококод

    Batch Hash Join ломает ORDER BY через навигацию по индексу

    recsrc/BatchHashJoin.cpp:250–313 · optimizer/InnerJoin.cpp:707, 719, 819

    BHJ отдаёт строки в порядке батчей, а Sort сверху не добавляется. Режим ALL ROWS, ORDER BY a.id по индексу, хэшируемая сторона больше 4 млн строк — результат не отсортирован. Plain HashJoin порядок лидера сохраняет.

  • S9высококод

    HLL занимает 256 КБ на колонку до конца REFRESH

    extstat/Collector.cpp:932 · extstat/DistinctCounter.h

    В документации 64 КБ. REFRESH всей базы держит 256 КБ на каждую собранную колонку: 30 тыс. колонок — около 7.5 ГБ памяти сервера.

  • S10высококод

    Страница 0 не учитывается в выборке

    recsrc/SamplingScan.cpp:51, 75

    Диапазон 0 добавляется, но не считается. Кардинальность без строк страницы 0 пишется с CARD_EXACT=TRUE, null fraction у NOT NULL колонок отрицательная, строки последнего диапазона не выбираются никогда.

  • S11высококод

    REFRESH падает на базах с кодировкой NONE

    extstat/Collector.cpp:158–191 · valueToText

    Debug JSON переводит значения в UTF8. Национальный текст в NONE даёт isc_malformed_string, и весь REFRESH откатывается из-за отладочной колонки.

  • S12высококод

    REFRESH и таблицы STAT$ обходят права на таблицы

    dsql/DdlNodes.epp ~14174 · AlterDatabaseNode

    Проверяется только право ALTER DATABASE, права SELECT на собираемые таблицы не проверяются. Текст MCV и гистограмм в STAT$*_TEXT показывает значения любых таблиц всем, кто может читать STAT$.

Под этот фильтр в разделе ничего нет.

Средние

  • M1среднетест

    Hash outer join не выбирается даже в простом случае

    optimizer/OuterJoin.cpp ~236–345 · порт ec3910caed

    Таблицы A и B по 20k строк, без индексов. a JOIN b ON a.x = b.x даёт Hash Join (inner). a LEFT JOIN b ON a.x = b.x даёт Nested Loop Join (outer) с полным сканом B на каждую строку A: 400 млн строк, больше 200 с.

  • M2среднеподозрение

    Не-equi условия ON могут теряться в хэш-ветке outer join

    optimizer/OuterJoin.cpp:296, 375

    Residual-фильтр оборачивает innerRsb, который потом выбрасывается, а конъюнкты уже помечены USED. a LEFT JOIN b ON a.x = b.x AND b.y > a.z может вернуть совпадения с b.y <= a.z. Проверить после исправления M1.

  • M3среднекод

    Чтение за началом массива ключей сортировки

    optimizer/Optimizer.cpp:2906 (и 2682)

    setSkdOffset(&sort_key[-1]) для первого ключа при ignoreNulls (merge join со строгим равенством): смещение берётся из байтов заголовка пула.

  • M4среднекод

    Стороны пары с разными типами декодируются одним дескриптором

    extstat/StatisticsCache.cpp:1708, 1846

    MCV внутренней стороны читаются дескриптором внешней. SMALLINT FK ⋈ INTEGER PK: 4 байта читаются из 2-байтового значения. Разные кодировки — ошибка MOV_compare при prepare. После смены типа без REFRESH старый blob читается неверно.

  • M5среднеподозрение

    Фолд LIKE(UPPER) → CONTAINING не строго эквивалентен

    dsql/BoolNodes.cpp ~365–435

    CONTAINING использует upcase коллации, а не LOWER. UPPER литерала выполняется в кодировке литерала, а не колонки. Греческая конечная сигма, турецкая i, знак Кельвина, кодировка NONE — результат может отличаться от исходного запроса.

  • M6среднекод

    Неполная инвалидация кэша статистики

    dsql/DsqlStatementCache.cpp:212 · DdlNodes.epp ~14066

    Кэш чистится только через AST кэша операторов. При MaxStatementCacheSize=0 или пустом кэше старая статистика живёт до отключения. DROP EXTENDED STATISTICS чистит кэш до commit, и другие соединения загружают старые строки снова.

  • M7среднекод

    План зависит от текущей загрузки temp-кэша

    optimizer/Optimizer.cpp:2224–2231 · tempSpillExpected

    Функция читает getTempCacheFree() без блокировки. Два запуска одного запроса получают разные планы, и в кэш попадает случайный.

  • M8среднекод

    В firebird.conf нет ключа ExtendedStatistics

    builds/install/misc/firebird.conf:559

    Описание ExtendedStatistics стоит над строкой #ExtStatisticsConstraints = false, а у настоящего блока ExtStatisticsConstraints ключа нет. DBA включит не тот параметр.

  • M9среднекод

    Сбор статистики: коллации, длинные значения, откат всего прогона

    extstat/Collector.cpp:1920, 1970, 1552–1582, 1773–1787, 2386–2419

    ND в режиме SCAN считается по сырым байтам без коллации (CI/AI, хвостовые пробелы). Длинные значения попадают в границы гистограммы. Одно длинное значение убивает всю многоколоночную структуру. Больше 16 имён в STAT$FIELDS переполняют стековый массив. DROP TABLE во время REFRESH всей базы откатывает весь прогон.

Под этот фильтр в разделе ничего нет.

Лишний addStructure(segs, 4, false) в Collector.cpp:2174. Мёртвые capped, AUTO_MULTI_MAX_ROWS, MAX_MCV_ENTRIES. Список имён в STAT$FIELDS через запятую ломается на имени с запятой. 4Модель стоимости и оценки: причины регрессов CEB

Ошибки модели стоимости

  • C1высококод

    leafCount — узлы одной страницы, а не все листья индекса

    jrd/btr.cpp:1220 · BTR_get_cost_factors

    Берётся число узлов одной страницы уровня 1. Для индекса глубины 3 и больше полный и диапазонный проход дешевле реального в сотни раз (например, 300 листьев вместо 100 тыс.).

  • C2высококод

    Цена hash join не зависит от ширины записи

    optimizer/Optimizer.h:702–734 · getHashJoinCost, getBatchHashJoinCost

    Параметр bufferWidth не используется. У BHJ нет цены записи ведущей стороны и прохода партиционирования. Лидер шириной 4798 байт стоит как запись в 50 байт — так появились регрессы 7a в ×10–40.

  • C3высококод

    BHJ выбирается по порогу кардинальности, без сравнения с NL

    optimizer/Optimizer.cpp ~4056 · generateEquiJoin · InnerJoin.cpp:266

    BHJ создаётся, если сырая кардинальность больше maxCapacity (около 4 млн). Оценка всегда считает новый поток хэшируемым. MOVIE_INFO (14.8 млн строк, BLOB IN) уходит в BHJ даже при пустом лидере: 7a_006 — 1.5 → 60 с.

  • C4высококод

    makeInversion теряет scratch

    optimizer/Retrieval.cpp:2765–2775, 2961–2973, 517–527, 582

    Цена уникальной пробы всегда DEFAULT_INDEX_COST (17.2, раньше 4), измеренная глубина не используется. Проверка joinDriven мёртвая, пол оценки применяется всегда, и оценка прыгает в 1/residual раз.

  • C5высококод

    Локальные фильтры учитываются дважды

    optimizer/Optimizer.cpp:4498, 4613 · recsrc/FilteredStream.cpp:51–66

    FilteredStream внутри соединения умножает на полную селективность, хотя BitmapTableScan уже применил локальные фильтры. Отсюда rows=0.4 в планах. Планов с оценкой соединения меньше 0.1 строки: прогон 4 — 14, прогон 5 — 39.

  • C6среднекод

    Кардинальность соединения не ограничена снизу единицей

    optimizer/InnerJoin.cpp:463 · NestedLoopJoin.cpp:86

    При floorLimited итоговая оценка может быть меньше 1. Цены NL глубже по дереву умножаются на число меньше 1, и глубокие потоки выглядят бесплатными.

  • C7среднекод

    LEFT JOIN без пола «не меньше внешней стороны»

    optimizer/OuterJoin.cpp ~252–331 · recsrc/HashJoin.cpp ~452–507

    LEFT JOIN оценивается в 0.3 от строк внешней стороны. Матч-селективность HJ учитывает локальные фильтры дважды. getHashJoinCost вызывается без ширины и спила.

  • C8среднекод

    Цена случайной страницы не зависит от кэша

    optimizer/Optimizer.h ~66–126 · COST_RANDOM_PAGE

    Константа 3.8 одинакова для таблицы в кэше и для CAST_INFO на 36 млн строк. Миллионы NL-проб оцениваются как попадания в кэш — причина 8a и 3b_005. Нет стартовой цены HJ/BHJ.

  • C9среднекод

    Стоимость выборки не монотонна

    optimizer/Retrieval.cpp:540–543 · fetchPrice

    Формула меняется на 100 записях. Два диапазона около 100 строк сравниваются в неверном порядке, выбор индекса переключается.

  • C10среднекод

    У диапазонного сканирования индекса нет цены за ключ

    optimizer/Retrieval.cpp ~2365–2455

    Цена — только глубина плюс листья, поэтому большие диапазоны дешевле примерно в 500 раз. maximumCost в старых единицах смешивается с новыми. Навигация платит 2.0 за запись — меньше, чем bitmap (3.0) и случайная выборка (5.8).

Под этот фильтр в разделе ничего нет.

Исполнение Batch Hash Join (7a)

  • Батчи делят только 8-байтовые массивы {position, hash}, а не записи. Каждый из 8 батчей читает весь буфер лидера вразброс — ввод-вывод растёт в 8 раз.
  • partition() сначала сканирует хэшируемую сторону, даже когда лидер пуст. Plain HashJoin строит хэш только на первой строке лидера.
  • Слоты BufferedStream фиксированной ширины: VARCHAR хранится по максимальной длине плюс все поля всех потоков — 4798 байт на строку. Режима refetch (ключи + DBKEY) нет.
  • Запись лидера восстанавливается (locate + getRecord) до проверки точного хэша (BatchHashJoin.cpp:265–271).
  • TempCacheLimit 1 ГБ вмещает около 200k строк по 4798 байт, дальше идут чтения из файла.
  • equiMatches объявлен вне цикла по потокам (InnerJoin.cpp:703): каждое соединение получает условия всех предыдущих, O(k²) проверок, и каждая выполняется дважды.
  • Число батчей фиксируется по оценке и не подстраивается под реальный объём.

5Методология и процесс

  1. Сравнивать каждый прогон с бейслайном и с PG, а не только с прошлым прогоном. PG-эталон с истинными кардинальностями (121 JSON) сейчас есть только локально, его нужно положить в репозиторий.
  2. Перемерить бейслайн в той же среде. Сейчас кеш 2048/256M против 50000/2000M.
  3. Считать q-error по узлам плана. В ветке уже есть rows= в EXPLAIN, PG-JSON даёт истинные размеры подпланов. Это прямая мера качества оценок без шума времени исполнения.
  4. Прогонять не только CEB. JOB, JOB-light, TPC-H, DSB, JCC-H уже портированы. Калибровка под один корпус даёт «качели»: 121 из 121 плана меняются за прогон.
  5. Добавить функциональные регрессионные тесты. Падение S1 прошло незамеченным. Минимум: агрегаты без GROUP BY, LEFT JOIN с не-equi ON, ORDER BY над большим JOIN, NUMERIC со scale, DDL статистики, кодировка NONE.
  6. Вынести константы стоимости в конфиг (Optimizer.h:66–126) и калибровать их на нескольких машинах, а не на одной.
  7. Описать модель стоимости и BHJ в README.optimizer-improvement.md: коммиты 7e52b410a5, f4bd6be7fa, b34f7dbb47, be3c956409 там не отражены.
  8. Писать коммиты с коротким заголовком. Сейчас сообщения по 1–2 КБ одной строкой, есть коммит «correction» и пары коммит/revert. Это мешает ревью и bisect.

6План действий

  1. Стабильность

    1–2 дня · до любых замеров
    1. Исправить падения S1 и S2.
    2. BINS — в non_reserved_word и флаг true в ParserTokens.h (S3).
    3. Action для SAMPLE в parse.y:4676 (S4).
    4. Хранить и загружать scale (S5).
    5. Existence lock в SamplingScan, конвертация старых форматов, проверка прав SELECT (S6, S7, S12).
    6. Ключ ExtendedStatistics в firebird.conf (M8).
    7. Запретить BHJ при sortUtilized или ставить Sort над ним (S8).
    8. Выяснить, почему не выбирается hash outer join, затем проверить M2.
    9. Тесты на каждый пункт.

  2. Корректность модели стоимости

    около 1 недели
    1. Главный переключатель: новая модель только при ExtendedStatistics=true или отдельный параметр OptimizerCostModel = legacy | new.
    2. leafCount = все листья индекса (C1).
    3. Ширина записи в цене HJ/BHJ; у BHJ — запись и чтение лидера и проход партиционирования (C2).
    4. BHJ — внутри перебора порядков с честной ценой и альтернативой NL, не по порогу maxCapacity (C3).
    5. Детерминированный тест спила по TempCacheLimit, а не по текущей занятости (M7).
    6. Копировать scratch, убрать двойной учёт, пол соединения ≥ 1 и LEFT JOIN ≥ внешней стороны (C4–C7).
    7. Цена случайной страницы с учётом кэша — аналог effective_cache_size (C8).

    Проверка: CEB + JOB + TPC-H + DSB, сравнение с бейслайном и PG, q-error. Цель — 7a и 8a не хуже стокового HQbird.

  3. Оценки до уровня PostgreSQL

    2–3 недели
    1. LIKE/CONTAINING как в PG: применять шаблон к значениям MCV и к выборке границ гистограммы (histogram_selectivity), а не константу (E1).
    2. Полная формула eqjoinsel, один учёт NULL, доля выборки, границы бинов, перестановка операндов (E6–E9).
    3. FK fanout с перекосом: при фильтре словаря брать частоты FK-колонки из MCV, расширить условную оценку 4.13 на LIKE/CONTAINING (E2).
    4. Динамическое программирование для порядка соединений до 10–12 потоков, как PG до geqo_threshold; жадный поиск — только выше (E3).
    5. Цена чтения BLOB в фильтрах и статистика по префиксу текста BLOB (E4).

  4. Исполнение Batch Hash Join

    1–2 недели · параллельно этапу 2
    1. Физическое разбиение записей по батчам (grace hash join): каждый батч пишется и читается последовательно.
    2. Режим refetch: в буфере только ключи и DBKEY; узкие слоты для VARCHAR.
    3. Проверка точного хэша до восстановления записи; не строить хэш при пустом лидере.
    4. Адаптивное число батчей; обработка перекоса ключей (раздел 5.8 документации).
    5. Убрать накопление equiMatches между потоками.

  5. Процесс

    постоянно
    1. PG-эталон и истинные кардинальности — в репозиторий.
    2. В каждом отчёте: п(N) / п(N−1), п(N) / бейслайн, п(N) / PG, q-error.
    3. Симметричный бейслайн.
    4. Гейт стабильности планов (fast_contour.py) перед полным прогоном.

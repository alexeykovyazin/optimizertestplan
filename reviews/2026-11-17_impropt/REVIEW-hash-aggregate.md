# Ревью хеш-агрегации и hash unique (22.11.2026, черновик)

Код: `origin/v5.0-impr-opt`, коммит `8d6c1d0568`. Коммиты: `6c7c834cd6` (Hash Aggregate), `e22f591368`,
`9fb180d41b` (Hash Unique), `8d6c1d0568` (сброс обоих методов на диск, выбор по оценке числа значений).
Сборка: движок `hu1` этого коммита (md5 `ea3f5ebc2e38`). Параметр: `AggregateHashMemory` (по умолчанию 8M,
0 = выключено).

Метод: два независимых чтения кода (исполнение и выбор плана), затем каждая находка проверена запросом на
сборке. Эталон — тот же запрос с `AggregateHashMemory = 0` (путь с сортировкой).
Тесты: `tests/71_hash_agg_defects.sql` (настройки по умолчанию), `tests/72_hash_agg_spill.sql`
(`AggregateHashMemory = 512K`). Вывод: `tests/out_hash_71_*`, `tests/out_sorted_71_*`, `tests/out_hash_72_*`,
`tests/out_sorted_72_*`.

Состояние: ничего не исправлено. При настройках по умолчанию сборка даёт неверные результаты и падает.
Рекомендация: поставить `AggregateHashMemory = 0`, пока не исправлены A1-A5.

## Подтверждено тестом: неверные результаты, падения, память

| № | Важность | Дефект | Результат теста |
|---|----------|--------|-----------------|
| A1 | Высокая: неверный результат, падение. Настройки по умолчанию | `HashPartitionReader::next` (HashPartition.h) смешивает два пути чтения. Запись, которая пересекает границу блока временного пространства, читается через буфер порции. Следующие записи приходят из `peekMemory` и не двигают `m_chunkOffset`. На следующей границе порция не читается заново, и адрес `m_chunk + (m_position - m_chunkBase) * length` уходит далеко за буфер. Условие: секция больше 2 МБ и длина записи, которая не делит размер блока (1 МБ). Здесь длина 48 байт. | `select id, count(*) from t where id < N group by id`, индекса по `id` нет. N = 80 000: верно. ## Найдено чтением кода, не запускалось

| № | Важность | Дефект |
|---|----------|--------|
| C1 | Средняя: утечка ресурсов | Объекты записи секций никогда не удаляются. `close()` не освобождает `impure->partitions`. При раннем закрытии (FIRST n, EXISTS) или ошибке `~TempSpace` не выполняется: использование временного кэша базы не возвращается, временные файлы остаются открытыми. Сортировки защищены от этого через `req_sorts`. |
| C2 | Средняя: производительность | Номер секции и номер корзины берут одни и те же младшие биты хеша. Внутри секции используется только 1 / 2^shift корзин. При shift 0 настоящего повторного разбиения нет. `hash >> shift` при shift >= 32 не определён (64 секции, уровень 5). |
| C3 | Низкая | Проверка точного числа значений принимает частичный индекс и пропускает выражения, которые не являются полями (`group by a, b + 0` считается как distinct(a)). |
| C4 | Низкая | В заметках об оптимизаторе два раздела 4.36 и два раздела 4.37. |

Найдено чтением, но не воспроизведено: ключ группы `COALESCE(int, numeric)` копируется с длиной времени
компиляции (тест дал верный результат `1.00 3`).

## Проверено, ошибок нет

- После совпадения хеша сравнивается полный ключ. NULL и ноль — разные группы в Hash Aggregate.
- Ключи Hash Aggregate: сравнения CI/AI, дополнение строк пробелами, DECFLOAT, -0 / +0, типы с часовым поясом.
- Группа никогда не делится между таблицей в памяти и секцией.
- `AggregateHashMemory = 0` выключает оба метода на всех путях.
- ORDER BY над хеш-GROUP BY сохраняется во всех формах. Оконные функции и merge join сортируют сами.
- Веса строк подсчитывающего агрегата (4.32) не встречаются с хешем: им нужен запрос без GROUP BY.
- COUNT, SUM, AVG, STDDEV / VAR, CORR хранят состояние внутри impure-области: сохранение через `memcpy` верно.

## Стенд

Черновик: замеров времени ещё нет.

- Планы 691 запроса стенда (job-light, scale, CEB) с хешем и без него. В job-light и scale нет GROUP BY, их
  планы не изменились. Все 90 запросов CEB с GROUP BY получают Hash Aggregate, когда хеш включён. Когда хеш
  выключен, планы те же, что до этих коммитов.
- Наборы для замера времени: TPC-H, JCC-H (norm, skew) и DSB (s1, s2) из этого репозитория, масштаб 1. Базы
  уже на стенде. Сейчас собираются расширенная статистика и планы.

## Предложения по исправлению

1. A1: один путь чтения на читателя. Или проверять порцию по диапазону позиций: `m_position < m_chunkBase ||
   m_position >= m_chunkBase + m_chunkCount`.
2. A2: хранить строковое состояние внутри слота (область фиксированной длины по объявленному типу). Или не
   выбирать хеш, когда аргумент MIN/MAX — строка или dbkey.
3. A3: строить ключ хеша Hash Unique из нормализованного ключа сортировки (выполнять шаг `diddleKey`), как это
   делает Hash Aggregate.
4. A4: `request->req_rpb[partStream.stream]`.
5. A5: сбрасывать буфер при `m_pendingCount + m_recordLength > BUFFER_SIZE`.
6. A6, C1: деструктор для `GroupHashTable`. Регистрировать таблицу, объекты записи и секции в запросе (как
   делает `req_sorts`) и освобождать их в `close()`.
7. A7, B4: передавать оценку с верхней границей. Брать кардинальность так же, как `compileRelation`. Не меньше
   2 секций после начала сброса. `m_groupsFit = MAX(1, ...)` и отказ от хеша при `groupsFit < 1` (A8).
8. B1, B2: не выбирать хеш в режиме первых строк и при пользовательском PLAN. Или оценивать навигацию так же,
   как это делает выбор доступа к таблице.
9. B3: выбирать метод до `checkSorts`. Или сохранять внешнюю сортировку, только когда итоговый выбор — хеш.
10. B5: печатать `SORT (` в старом формате плана, как путь с сортировкой.

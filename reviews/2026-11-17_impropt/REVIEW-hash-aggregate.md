### D1. Новое падение: повторное выполнение запроса с Hash Unique (регрессия коммита `b6f5cabd4b`)

Важность: высокая, настройки по умолчанию. С `AggregateHashMemory = 0` падения нет.

- Коммит `b6f5cabd4b` (исправление A3) создаёт в `HashUniqueStream::internalOpen` объект `Sort` (`impure->diddler`)
  и регистрирует его в `request->req_sorts`. `close()` его не удаляет. При завершении запроса владелец сортировок
  удаляет объект, а указатель в impure-области остаётся. Следующее открытие того же запроса выполняет
  `delete impure->diddler` второй раз.
- Воспроизведение 1: `create table t1 (id int not null primary key, v int); create table t2 (id int not null
  primary key, v int); commit;` — процесс падает на второй таблице (системный запрос DDL выполняется повторно).
- Воспроизведение 2: процедура `select count(*) from (select distinct k from c) into :n`. Первый вызов
  `select n from p` возвращает результат, второй роняет процесс.
- Найдено пересборкой коммитов: `21a988afd5` работает, `b6f5cabd4b` падает.
- Исправление: `HashUniqueStream::close()` удаляет `impure->diddler` и обнуляет указатель, как
  `SortedStream::close()` делает с `irsb_sort`. PR: https://github.com/IBSurgeon/hqbird/pull/56.
- Тест: `tests/74_hash_unique_reexecute.sql`. С исправлением: три вызова процедуры возвращают результат, обе
  таблицы создаются.

### D2. Падение при подготовке GROUP BY по столбцам 5 и более таблиц (старый дефект, PR 55)

`ExtStatistics::getGroupCountEstimate` хранит группы потоков в `HalfStaticArray<StreamGroup, 4>`; группа владеет
вложенным массивом. Пятый поток заставляет массив расти: элементы копируются побитово, новый элемент
записывается в неинициализированную память. Найдено на запросе DSB 64 (`dsb_064_01`). Дефект не связан с
коммитами Hash (код от 13.10.2026, `e144e8c5cf`). Исправление: https://github.com/IBSurgeon/hqbird/pull/55.
Тест: `tests/73_group_estimate_five_streams.sql`.

### D3. Hash Unique отключён отладочной строкой (коммит `496ba0453b`, база `c646a9360c`)

Важность: средняя. Неверных результатов нет, но метод не работает совсем.

- `Optimizer::decideHashUnique()` (Optimizer.cpp:4102) начинается со строки
  `return false;	// BISECTION A8-debug: gate disabled`. Весь остальной код функции не выполняется.
- Проверка: таблица 100 000 строк, столбец `a` с индексом (1000 значений, статистика индекса собрана), затем
  собрана расширенная статистика. `select distinct a`, `select distinct d`, `select distinct a, d` получают
  Unique Sort во всех случаях. `group by` по тем же столбцам получает Hash Aggregate. На базе `f8f4b80b43`
  `select distinct a` получал Hash Unique.
- Стенд: на базе `f8f4b80b43` Hash Unique был в 18 запросах DSB (по 9 в s1 и s2), на базе `c646a9360c` — в 0.
- Следствие: находки B3 и B5 и исправления A3 и D1 на базе `c646a9360c` не проверяются: код Hash Unique не
  выполняется.
- Вторая отладочная строка того же коммита: `if (true)	// BISECTION: nav candidate ON`
  (RecordSourceNodes.cpp:2258). Поведение не меняет.

## Проверено, ошибок нет

- После совпадения хеша сравнивается полный ключ. NULL и ноль — разные группы в Hash Aggregate.
- Ключи Hash Aggregate: сравнения CI/AI, дополнение строк пробелами, DECFLOAT, -0 / +0, типы с часовым поясом.
- Группа никогда не делится между таблицей в памяти и секцией.
- `AggregateHashMemory = 0` выключает оба метода на всех путях.
- ORDER BY над хеш-GROUP BY сохраняется во всех формах. Оконные функции и merge join сортируют сами.
- Веса строк подсчитывающего агрегата (4.32) не встречаются с хешем: им нужен запрос без GROUP BY.
- COUNT, SUM, AVG, STDDEV / VAR, CORR хранят состояние внутри impure-области: сохранение через `memcpy` верно.

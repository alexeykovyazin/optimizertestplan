## Вывод

1. **Исполнение хорошее там, где метод выбран.** Микротест: хеш быстрее сортировки в 1,6–5 раз.
2. **Главная потеря — охват.** В DSB на хеш попадают 90 узлов группировки, на сортировке остаются 385.
   Правило выбора отказывает по формальным признакам, без оценки цены.
3. **Связка с хеш-соединением не используется.** В DSB 169 узлов «сортировка + агрегат» стоят прямо над
   Hash Join. Подсчёт строк без чтения (`AggregateJoinCounting`) при GROUP BY выключен.
4. **Исполнение можно ускорить**, но это второй приоритет: сначала охват.

## Замечания к правилу выбора

| № | Место | Замечание |
|---|-------|-----------|
| G1 | `decideHashAggregate`, `favorFirstRows()` | Любой `FIRST` / `ROWS` / `EXISTS` отменяет хеш. Выигрыш «первых строк» есть только при навигации по индексу в порядке группировки. Если вход всё равно сортируется или есть внешний `ORDER BY` по агрегату, читаются все строки, и хеш дешевле. |
| G2 | `decideHashUnique`, `rse->rse_sorted` | Любой `ORDER BY` отменяет Hash Unique. При малом числе значений «хеш + сортировка результата» дешевле сортировки всего входа. |
| G3 | `decideHashAggregate` до `compile` | Решение принимается до компиляции входа. Число входных строк — размер самой большой таблицы ключей, без фильтров и соединений. Hash Unique решает после компиляции (`generateSort`), и это правильнее. |
| G4 | Число групп | Берётся только для полей базовых таблиц со статистикой. Ключ-выражение проходит, только если есть индекс по этому выражению и ключ один. Иначе отказ. |
| G5 | Цена сброса | `passes = ceil(groups / groupsFit)`, цена `spillRows × 2 × (passes − 1)`, предел 8 проходов. Исполнение делит вход на секции (до 64): каждая сброшенная строка пишется и читается один раз на уровень. Формула завышает цену до 7 раз, а предел 8 отсекает группировки, которые исполнение выполнит за один уровень. |
| G6 | Бюджет 8M | Слот 200 байт: в памяти помещается около 30 тыс. групп. Сортировка при этом использует временный кэш (64M и больше). |
| G7 | Модель цены | `inputRows × HASH + groups × MEMCOPY` против `2 × MEMCOPY + n log n`. Не учитываются ширина записи сортировки, длина ключа, число агрегатов, сортировка результата для внешнего `ORDER BY`. |
| G8 | `MIN` / `MAX` по строке | Весь запрос остаётся на сортировке (так закрыта ошибка A2). |
| G9 | Ключ шире нужного | Все столбцы GROUP BY входят в ключ. `tpch_10`: ключ сортировки 940 байт при 675 тыс. строк, хотя группу определяет `c_custkey`. |
| G10 | `rse->rse_plan` | Любой пользовательский PLAN отменяет хеш, даже без `ORDER` для таблицы группировки. |

## Замечания к исполнению

| № | Место | Замечание |
|---|-------|-----------|
| E1 | `internalOpen`, цикл по входу | `saveState` вызывается на каждой строке, `restoreState` — при каждой смене группы. Оба идут по всем агрегатам, вызывают виртуальный `getImpureIntervals` и копируют интервалы по одному. Достаточно сохранять состояние только при смене группы и один раз вычислить список интервалов. |
| E2 | `computeGroupKey` | Строковый ключ дополняется до объявленной длины. Ключ VARCHAR(200) UTF8 — сотни байт: обнуление, копирование и хеш на каждой строке. Слот хранит ключ и ещё раз исходное значение. |
| E3 | `GroupHashTable` | Коэффициент заполнения 4: средняя цепочка из 4 записей, каждый шаг — чтение записи в другом месте памяти. `getSlot` делает деление и остаток при каждом совпадении хеша и при каждом сохранении состояния. |
| E4 | `storeOriginals` | Выражения ключа вычисляются второй раз для новой группы. Мало влияет при малом числе групп. |
| E5 | Память | Бюджет считает только слоты. Массив записей и корзин в него не входит. |

Влияние E1–E3 не измерено: нужен профиль. По микротесту 7 дополнительных агрегатов стоят 0,60 с на 2 млн
строк на хеш-пути и 0,69 с на пути сортировки, то есть основное время — вычисление самих агрегатов.

## Паттерны: хеш-соединение и хеш-группировка

При сортировке порядок используется повторно: merge-соединение, группировка и `ORDER BY` по одному ключу
делят одну сортировку. У хеш-методов аналог — общий ключ, общая хеш-таблица и общее разбиение на секции.

| № | Паттерн | Суть | Что уже есть |
|---|---------|------|--------------|
| P1 | Подсчёт строк под GROUP BY | Потоки соединения, на которые не ссылаются ключи и агрегаты, не читаются: берётся их число (вес строки). | Вес строки проходит через `HashAggregateStream` (`computeRowWeight`, `aggPassWeighted`, вес в образе секции). Запрещает только `applicableRowWeights`: `if (group ...) return false`. |
| P2 | Группировка до соединения | Сначала хеш-группировка большой таблицы по внешнему ключу, затем соединение малого числа групп со справочником. | Свёрнутая сторона hash join со счётчиком (`counted streams`) — это группировка по ключу соединения с `COUNT`. Нужно обобщить на `SUM`, `MIN`, `MAX`. |
| P3 | Одна таблица на соединение и группировку | Ключ группировки равен ключу соединения хешируемой стороны, и он уникален: состояние агрегатов хранится в записи хеш-таблицы соединения. Второй хеш не нужен. | Ключ группы строится тем же кодом, что ключ соединения. |
| P4 | Общее разбиение на секции | Батчированный hash join делит вход по хешу ключа соединения. Если ключ группировки включает ключ соединения, группы разных батчей не пересекаются: группировка идёт по батчам и сама на диск не сбрасывает. | Секции есть у обоих методов, но биты хеша разные. |
| P5 | Повторное использование хеша | При равных ключах хеш строки соединения годится для поиска группы. | — |
| P6 | Ключ группировки в поиске порядка соединения | Аналог «интересных порядков»: при равной цене выбирать порядок, где последнее хеш-соединение идёт по ключу группировки. | Поиск порядка знает только порядок сортировки. |
| P7 | `DISTINCT` и `IN (подзапрос)` | Удаление дублей хешируемой стороны полусоединения тем же Hash Unique; `DISTINCT` не нужен, если в списке есть уникальный ключ. | Свёрнутая сторона по ключу (`keyOnlyCondition`). |

Локальный пример P1–P3: `select t.k100, count(*) from t join s on s.id = t.k100 group by t.k100`. Сейчас:
Hash Aggregate над Hash Join, 0,77 с; без хеша 1,64 с. Группировка `t` без соединения: 0,33 с.

# Риск nested loop: худший случай вместо константы (исследование, 19.11.2026)

Вопрос рецензента к заметкам 4.23 (`E:\Projects_Big\hqbird-impropt\doc\README.optimizer-improvement-ru.md`):
почему риск оценён константой `LOOP_JOIN_FANOUT_RISK = 2.0`? Предложение: сравнивать
`cost(worst NL) / cost(worst HJ)` с `cost(NL) / cost(HJ)`. Второй вопрос: «стрельнёт» ли PR 42
(https://github.com/IBSurgeon/hqbird/pull/42, цена промахов кэша) в этом исследовании.

Кода для слияния нет. Есть опытный прототип и замеры. Файлы: `results/wc_risk_1119/`.

Пометки: **замер** — число получено на стенде; **расчёт** — выведено из других чисел.

## 0. Итог

| Вопрос | Ответ |
|---|---|
| Можно ли заменить константу худшим случаем? | Да. Правило работает, если «худший случай» — взвешенная степень ключа `Σc²/Σc`, а не максимум |
| Даёт ли это выигрыш? | Только вместе с PR 42: 482 → 355 с на 26 изменившихся запросах, ни одной заметной потери |
| Без PR 42? | Проигрыш: 385 → 784 с. Правило уводит поиск на плохой порядок соединения |
| Максимум степени ключа как худший случай | Не годится: проигрыш и с PR 42 (1 393 → 1 926 с), и без него |
| «Стреляет» ли PR 42? | Да. Он условие, при котором правило худшего случая вообще работает |
| Что нужно для реализации | Одно новое число на индекс: `Σc²` по ключам. Его даёт тот же проход, что считает селективность |

Выигрыш на всём наборе мал: 11 595 → 11 468 с (1.1%) на 537 запросах с известным временем. Польза правила не в
секундах, а в том, что константа исчезает, а результат не хуже.

## 1. Формула

Обозначения: `E` — оценка числа строк префикса, `W` — худшее число строк префикса, `NL(x)` и `HJ(x)` — цены
nested loop и hash join при `x` строках префикса.

- Выбрали NL, случился худший случай: проигрыш `NL(W) / HJ(W)`.
- Выбрали HJ, оценка оказалась верной: проигрыш `HJ(E) / NL(E)`.

Правило рецензента: взять HJ, когда первый проигрыш больше второго:

```
NL(W) / HJ(W) >= HJ(E) / NL(E)      то же самое:      NL(E) * NL(W) >= HJ(E) * HJ(W)
```

Следствия (расчёт):

- Это сравнение цен в точке `sqrt(E * W)` — геометрическое среднее оценки и худшего случая.
- NL линеен по префиксу, HJ почти плоский. Тогда правило равно прежнему с множителем риска `sqrt(W / E)`.
- Константа 2.0 на одно соединение в этих терминах значит: худший случай в 4 раза выше оценки.
- Обобщение с весом `θ`: `θ * ln(NL(W) / HJ(W)) >= (1 - θ) * ln(HJ(E) / NL(E))`. Формула рецензента — `θ = 0.5`.

`W / E` в прототипе — произведение по всем предыдущим неуникальным соединениям префикса отношения «худшее число
строк на ключ / среднее число строк на ключ». Первый поток не считается, как и сейчас. Цены `NL(W)` и `HJ(W)`
считаются теми же функциями цены, что и обычные, включая цену промахов PR 42.

### 2.1. Реальная ошибка оценки

Расчёт по готовым прогонам: 349 запросов `COUNT(*)` наборов scale (279) и job-light (70) с известным истинным
размером. `A` — истина, `E` — оценка верхнего соединения, `k` — число неуникальных соединений после первого потока.
Скрипт `results/wc_risk_1119/theta.py`.

| `k` | Запросов | `A/E` p50 | p75 | p90 | p95 | На одно соединение: p50 / p75 / p90 / p95 |
|---|---|---|---|---|---|---|
| 1 | 107 | 1.35 | 3.0 | 8.4 | 12.8 | 1.35 / 3.0 / 8.4 / 12.8 |

  (`Σc²/Σc`), 1.87 (максимум), 2.45 без поправки. В этих наборах все соединения идут по `movie_id`, поэтому степени

## 5. Почему без PR 42 правило проигрывает

- Правило выбирает hash join там, где по оценке он дороже nested loop. Цена позиции растёт: поиск порядка
  использует цену выбранного метода.
- Поиск уходит на другой порядок, где правило не срабатывает. Без PR 42 такой порядок выглядит дешёвым, потому что
  цена nested loop не знает о чтениях мимо кэша. Четыре из пяти худших потерь v1 на базе — смена порядка.
- PR 42 делает такие порядки дорогими. С ним у тех же пяти запросов план не меняется.
- Это та же ловушка, что записана в заметках 4.23 для коэффициента 2.15 (`ceb_10a_013`).

## 6. Что нужно для реализации

- **Статистика:** `Σc²` по ключам индекса (или сразу `Σc²/Σc`). Одно число на индекс.
- **Сбор:** проход по листьям индекса при пересчёте селективности уже считает дубликаты ключа. Сумма квадратов —
  один накопитель в том же проходе. Это не проверено в коде.
- **Хранение:** открытый вопрос. В корне индекса места нет (ODS). Варианты — таблицы расширенной статистики HQbird.
- **Связь с предложением 3:** это вариант (c1) «сводка степеней колонки» в самом малом виде. Раздел 10.5 файла
  `PROPOSAL-3-key-sample.md` отклоняет (c1) как **оценку** размера. Здесь она нужна как число **риска** — другая
  роль.
- **Зависимость:** PR 42. Без него правило включать нельзя.

## 7. Что не сделано

- Один замер на запрос. Разница меньше 10–15% — в пределах шума стенда.
- v4 и v5 не замерены по времени, только планы.
- Локальные тесты (fuzz, набор 43–70) на прототипе не запускались, кроме теста 69 в режиме v0.
- Только база IMDB. Наборы с другим перекосом (JCC-H, DSB) не проверены.
- Вес `θ` подогнан на тех же запросах scale и job-light, на которых потом мерилось время.
- Известные потери PR 42 (`ceb_10a_003`, `ceb_10a_004`) правило не исправляет: их план с правилом тот же.
- Правило применяется, как и константа, только когда текущий поток присоединяется неуникальным доступом. Вариант
  «и для уникального доступа» в прототипе есть (флаг), не проверялся.

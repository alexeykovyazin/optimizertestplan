## 2. Причины

### J1. BHJ читает сброшенный на диск батч по одной записи

Проба батча, чей буфер записей ушёл во временный файл, читает каждую найденную запись хэшируемой стороны по позиции
(`RecordBuffer::fetch`). Совпадения одного ключа разбросаны по батчу, поэтому почти каждое чтение загружает свой
блок временного файла в 64 КБ.

Воспроизведение (тест 63): `p` 20 000 строк, `l` 1 млн строк, `g` 8 млн строк, соединение возвращает 16 млн строк,
`TempCacheLimit = 64M`. Сборка PR #31: 597 с. С буферами в памяти (`TempCacheLimit = 4000M`): 4.2 с.

### J2. Условие hash join повторяет равенства всей реки

`InnerJoin::formRiver` собирал условие проверки каждого hash join из массива `equiMatches` всей реки, а не одного
соединения. После реки `applyLocalBoolean` вычислял те же равенства ещё раз в узле `Filter`. Вместе с парами, которые
добавляет `distributeEqualities`, запрос 061 выполнял 18 сравнений на каждую из 493 млн строк вместо одного.

### J3. Обычный hash join со сброшенной хэшируемой стороной (не исправлено)

Тот же путь чтения по позиции. 30 млн строк соединения при хэшируемой стороне 3 млн строк по 129 байт: 107 с при
`TempCacheLimit` по умолчанию, 8.5 с в памяти. Переход на BHJ требует сравнения цен: BHJ материализует и ведущую
сторону.

## 3. Исправления (PR #35)

| Коммит | Находка | Что сделано |
|---|---|---|
| `686efad5e8` | J1 | Сброшенный батч в пределах `TempCacheLimit / 4` читается один раз по порядку в память батча; проба идёт по указателям. Число батчей учитывает объём стороны в байтах. |
| `24565d5ab6` | J2 | Условие содержит равенства только своего соединения. Повторное равенство, которое следует из префикса, убирается (только при одинаковых типе, длине, масштабе и collation). Фильтр над рекой эти равенства не повторяет. |

## 6. После ревью PR #35 (17.11, вечер)

- **Параметр `HashJoinBatchMemory`** (`a52ba2f4b0`): предел загрузки батча теперь задаётся абсолютным значением на
  одно соединение (байты, по умолчанию 16M, 0 выключает), а не долей `TempCacheLimit`. Тест 63-подобный запрос,
  `TempCacheLimit = 64M`: 0 - 323 с, 2M - 140 с, 16M - 18 с, 64M - 6 с. Замеры раздела 4 на dellg15 сделаны со
  старым правилом (`TempCacheLimit / 4` = 500M).
- **Слияние с `v5.0-impr-opt`** (`dfe4c726c1`): базовая ветка получила коммит 3eba645881 (слияние звёздных рек).
  У слитого узла нет условия, поэтому его равенства оставлены в фильтре над рекой. Ревью этого коммита:
  `REVIEW-star-fusion.md`. Он содержит ошибку с потерей строк (F1); случай H2 теста 64 на объединённой сборке
  неверен из-за неё.
- В тест 64 добавлен случай H6 (слитая звезда). Вывод `out_pr31_64_*` и `out_fix_64_*` снят до добавления H6;
  `out_merged_64_*` - на объединённой сборке.

## 7. Обычный hash join и временное хранилище (J3), цена формы (17.11, вечер)

Ревьюер PR #35 попросил вынести эти темы в отдельные PR и поставил условие: хэш-таблица всегда в памяти, предел
4 млн записей — не вопрос цены. Оба изменения хэш-таблицу не трогают.

### 7.1. J3 исправлен: сброшенная сторона HJ загружается или кластеризуется

[IBSurgeon/hqbird#37](https://github.com/IBSurgeon/hqbird/pull/37), ветка `v5.0-impr-opt-hj-temp` (`1d26c2e9ca`). Три изменения:

1. `RecordBuffer::fetch`: случайный промах читает одну запись, а не блок 64 КБ.
2. Сторона в пределах `HashJoinBatchMemory` загружается в память (`RecordBuffer::load`).
3. Сторона больше предела переписывается в порядке хэш-таблицы (`HashJoin::buildStream`): совпадения одной строки
   ведущей стороны лежат рядом и читаются одним чтением (`RecordBuffer::prefetch`). Сторона с почти уникальными
   ключами не кластеризуется.

Запрос J3 (ведущая сторона 1 млн строк, хэшируемая 3 млн строк по 129 байт, 30 млн строк соединения):

| Сборка | Время |
|---|---|
| до изменения | 98.6 с |
| только одиночное чтение записи | 45.3 с |
| с кластеризацией | 12.5 с |
| то же соединение в памяти | 7.7 с |

Тест 66 (`TempCacheLimit = 8M`, хэшируемая сторона 600 000 строк), до → после: кластеризованная сторона
39.7 → 1.9 с, загруженная 2.3 → 0.4 с, NULL-ключи 21.4 → 1.2 с, перекос 6.6 → 1.6 с, внешний hash join
11.5 → 0.7 с, три реки 12.0 → 3.3 с, уникальные ключи 0.7 с в обеих сборках. Числа результата равны на обеих
сборках и при `HashJoinBatchMemory` 16M, 64K и 0.

Регрессия: тесты 00–65 равны базовой сборке (кроме случайных выборок статистики), тест 42 — 198 из 198, fuzz —
1 200 из 1 200. Соединение в памяти не замедлилось (12.1 с на обеих сборках).

### 7.2. Цена hash join считается для той формы, которая строится

### 7.4. Слияние звёздных рек замедлило hash join с тремя хэшируемыми потоками (причина найдена, есть прототип)

Найдено при сравнении прогона job-light на сборке PR #35 до слияния (`24565d5ab6`, без `3eba645881`) с прогоном
`head36`. Слияние сменило план у 9 запросов: каскад hash join стал одним hash join с несколькими хэшируемыми
потоками. Шесть запросов стали медленнее:

| Запрос | Каскад, с | Слитая звезда, с |
|---|---|---|
| 041 | 68.9 | 100.9 |
| 042 | 31.6 | 42.4 |
| 043 | 83.4 | 120.7 |
| 049 | 26.5 | 33.2 |
| 050 | 19.9 | 24.7 |
| 058 | 171.4 | 284.6 |

024 (6.5 → 4.6 с) и 033 (7.8 → 7.9 с) не замедлились, 060 — таймаут в обоих прогонах.

Парный замер 18.11, сборки чередовались: 041 — 69.2 / 75.6 / 76.4 с против 99.0 / 99.7 / 109.4 с; 058 — 169.7 с
против 293.3 с. `HashJoinBatchMemory` не влияет: 058 с 500M — 291–293 с, с 16M — 271–285 с. Результаты равны.
В том же (не парном) сравнении 61 запрос с прежним планом стал быстрее: 1 018 → 798 с (019 с BHJ:
84.8 → 26.6 с).

**Причина.** Слитый узел создаётся без условия (`InnerJoin::formRiver`, `HashJoin(..., nullptr, ...)`). Равенства
всех его рёбер уходят в `filterMatches` и проверяются фильтром над всей рекой. Фильтр стоит на вершине реки,
у 058 — над BHJ, и считает все равенства на каждой строке результата. В каскаде каждое соединение проверяло
только своё равенство, нижние — на меньшем числе строк. Добавка времени постоянна на строку результата:

| Запрос | Строк результата | Добавка, с | нс на строку |
|---|---|---|---|
| 041 | 513 млн | 32.0 | 62 |
| 042 | 207 млн | 10.8 | 52 |
| 043 | 625 млн | 37.3 | 60 |
| 049 | 132 млн | 6.7 | 51 |
| 050 | 91 млн | 4.8 | 53 |
| 058 (фильтр над BHJ) | 1 353 млн | 113.2 | 84 |

024 и 033 дают 4.5 и 31 млн строк, добавка меньше шума.

**Прототип исправления** (`results/checks_1118/fused_conditions_prototype.diff`, поверх ветки PR #38): каждый
хэшируемый поток слитого узла получает своё условие. Узел проверяет его, когда читает запись этого потока.
В этот момент текущие — ведущий поток и предыдущие хэшируемые; условие потока ссылается только на них.
Фильтр над рекой эти равенства больше не считает. Замер на dellg15, сборки чередовались:

| Запрос | Каскад, с | Слитая звезда, с | Прототип, с |
|---|---|---|---|
| 041 | 69.2–76.4 | 98.9–109.4 | 64.5 / 66.7 / 69.3 |
| 043 | 83.4 | 120.7–123.8 | 81.7 / 89.5 |
| 058 | 169.7–171.4 | 284.6–293.3 | 168.6 |
| 024 | 6.5 | 4.6 | 5.2 |

Числа результата совпадают с манифестом. Локально тесты 64–67 на прототипе дают те же результаты; в планах
пропал только `Filter` над слитым узлом. Полная регрессия (тесты 00–63, fuzz, job-light и CEB целиком) на
прототипе не запускалась.

**Исправление: [IBSurgeon/hqbird#39](https://github.com/IBSurgeon/hqbird/pull/39)**, ветка
`v5.0-impr-opt-fused-conditions` (`b0111b650a` код, `18fbe6e789` заметки 4.29), поверх `51bfe3823f` (PR #38 слит
18.11). Тот же подход, что в прототипе; удалены `filterMatches` и `fusedSeedMatches`.

- Тест `tests/68_fused_conditions.sql` (псевдоним `tst18fused`): три реки, 53.9 млн строк соединения —
  13.4 с → 8.5 с; ребро относительно другой хэшируемой реки; BHJ над слитым узлом; три реки по 2 млн уникальных
  пар двух ключей (8 байт, коллизии хэша). Числа равны на сборках до и после и равны nested loop.
- Тесты 00–67: результаты равны базовой сборке; в планах тестов 64 и 65 пропал `Filter` над слитым узлом
  (7 мест), других отличий формы плана нет. Тест 42 — 198 из 198. Fuzz — 1 200 из 1 200.
- Полный прогон job-light и CEB на сборке ветки (`fusedcond`) запущен 18.11 в 7:40, результаты будут добавлены.

scale_036 проверен на сборке PR #38: план не изменился, это не случай PR #38 (см. `SCALE-interim.md`, S1).

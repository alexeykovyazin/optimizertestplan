# scale: промежуточный отчёт (17.11.2026)

Прогон остановлен вручную на запросе 361 из 500, чтобы освободить стенд для job-light и CEB.

- **Сборка:** `engine13_c1.dll` = PR #35 до слияния (`24565d5ab6`): загрузка сброшенного батча BHJ и условие hash
  join. В сборке нет: слияния звёздных рек (`3eba645881`), параметра `HashJoinBatchMemory` (действует старое
  правило `TempCacheLimit / 4` = 500M на батч), PR #37 и PR #38.
- **Стенд:** dellg15, IMDB, FB_impropt (порт 3056), `TempCacheLimit = 2000M`, лимит 300 с на запрос, один
  прогревочный и один замерный запуск.
- **Запросы:** `bench/queries/scale`, `COUNT(*)` над соединением от 1 до 5 таблиц по `movie_id` с фильтрами.
- **Базовой линии нет.** Прогон scale на сборке PR #31 был остановлен на третьем запросе. Сравнение «до/после»
  по этому набору невозможно.

## 6. Находки

- **S1. scale_036: nested loop там, где лучше hash join.** `title t, cast_info ci where t.kind_id < 7`:
  1 млн строк `title`, по 14 строк `cast_info` по индексу на каждую. 14.8 млн строк за 96.3 с — 0.15 млн строк/с,
  в 10 раз медленнее соседних запросов. Оценка верна (14.5 млн).
  **Проверено 18.11 на сборке PR #38: план тот же, 97–98 с (на сборке до PR #38 — 97 с).** Предположение
  «это случай PR #38» неверно. Тот же запрос с `PLAN HASH (CI NATURAL, T INDEX (KIND_ID_TITLE))` — 16.5–18.8 с,
  в 5–6 раз быстрее. Nested loop читает 8.34 млн страниц, hash join — 0.21 млн (кэш базы 50 000 страниц).
  Оптимизатор выбирает nested loop по цене: 1 млн поисков по индексу в таблице из 36 млн строк оценён дешевле
  полного чтения `cast_info`. Цена поиска по индексу не учитывает чтение страниц мимо кэша (моё объяснение,
  по узлам не разобрано).
- **S2. scale_160: оценка 46 строк при 115 млн.** Предикат `ci.role_id > 10` по индексу `ROLE_ID_CAST_INFO`
  оценён в 1 строку. Запрос выполнился за 36 с, но план — nested loop от `cast_info` по всей цепочке. Причина
  оценки не разобрана (диапазон у верхней границы значений).
- **S3. scale_014: таймаут при 994 млн строк.** Оценка 1.6 млн (занижение в 600 раз). План заканчивается nested
  loop в `cast_info` по индексу. С верной оценкой выбрался бы hash join; при 6–10 млн строк/с запрос занял бы
  100–170 с.
- **S4. scale_351: 40.7 млн строк за 84.7 с** (0.48 млн строк/с). Последнее соединение с `cast_info` — nested
  loop, 15 строк на ключ. Оценка 9.1 млн при 40.7 млн.

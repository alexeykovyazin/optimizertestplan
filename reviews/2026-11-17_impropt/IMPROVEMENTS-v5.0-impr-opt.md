# Улучшения оптимизатора в ветке `v5.0-impr-opt`

Состояние на 22.11.2026, коммит `e7537208f0`. Источник: `doc/README.optimizer-improvement-ru.md` ветки
(номера разделов ниже — из этого документа) и история git.

## Ветка в цифрах

- 301 коммит без учёта слияний, с 06.10.2026 по 22.11.2026 (от общей точки с `v5.0-release`).
- 87 файлов в `src`, +31 695 и −1 340 строк.
- Авторы: Денис Симонов (235 коммитов), Алексей Ковязин (66 коммитов).
- 14 новых параметров конфигурации, 4 таблицы хранилища статистики (`STAT$...`), новые команды SQL
  `ALTER DATABASE ADD / DROP EXTENDED STATISTICS` и `ALTER DATABASE REFRESH STATISTICS`.
- 42 раздела описания в главе 4 документации.

## 1. Расширенная статистика

- **Хранилище в базе (раздел 2).** Таблицы `STAT$SETTINGS`, `STAT$TABLES`, `STAT$COLUMNS`,
  `STAT$MULTI_COLUMNS`. Команды `ALTER DATABASE ADD EXTENDED STATISTICS` и `DROP EXTENDED STATISTICS`.
  Статистика переживает перезапуск сервера.
- **Сбор (раздел 3).** `ALTER DATABASE REFRESH STATISTICS [SAMPLE | SCAN | FULL] [FOR TABLE ... [COLUMN ...]]
  [BINS n]`. Собираются: число строк, доля NULL, число различных значений, список частых значений (MCV),
  гистограмма, профиль хранения BLOB.
- **Многоколоночные структуры (3.8, 3.9, 4.17).** Совместное число различных значений нескольких столбцов;
  именованные статистики.
- **Кэш (4.1).** Каждое подключение читает статистику один раз на таблицу, в отдельной транзакции чтения.
  `REFRESH` сбрасывает кэш скомпилированных запросов.
- **Степень ключа (4.33, 4.39).** Новые столбцы `STAT$WEIGHTED_DEGREE` и `STAT$AVERAGE_DEGREE`: сколько строк
  приходится на значение ключа с учётом перекоса. Считаются одним обходом индекса.
- **Включение.** `ExtendedStatistics = true` на базу. При `false` поведение то же, что у стандартной сборки.

## 2. Оценка фильтров по одной таблице

- **Число строк таблицы (4.2).** Собранное точное число, масштабированное текущим числом страниц.
- **Доля NULL (4.3).** `IS NULL` и `IS NOT NULL` оцениваются точно, без предела 0,5.
- **Число различных значений (4.4).** Равенство: `(1 − доля NULL) / число значений`. Список `IN`: сумма по
  значениям.
- **Частые значения и гистограммы (4.7).** Равенство с литералом получает точную частоту из MCV. Диапазоны
  с литералами оцениваются по гистограмме.
- **Индексы из одного сегмента (4.5).** Селективность индекса заменяется статистикой столбца.
- **Составной индекс (4.16).** Скан по нескольким сегментам равенства оценивается по совместной статистике
  пары столбцов.
- **Частичный индекс (4.14).** Измеряется доля строк, которые удовлетворяют условию индекса.
- **GROUP BY и DISTINCT (4.6).** Число групп берётся из статистики столбцов и из префикса составного
  индекса. Раньше: «входные строки × 0,001 на каждый столбец».
- **BLOB (4.21, 4.22).** Предикат, который читает содержимое BLOB, получает цену чтения. Текстовые BLOB
  получают MCV и гистограмму.
- **FIRST N (4.15).** Оценка `MIN(n, строки источника)`.
- **Корреляция предикатов (раздел 1).** `PredicateCorrelation = true`: несколько условий по одной таблице
  считаются частично зависимыми. Самое селективное условие берётся полностью, вклад следующих уменьшается.

## 3. Оценка соединений

- **По распределениям значений (4.9).** Соединение `t1.f1 = t2.f2` оценивается по MCV и гистограммам обеих
  сторон.
- **С учётом фильтра (4.13).** Если на одной стороне есть фильтр по литералу, оценка учитывает, какие
  значения ключа проходят фильтр. Это типичный случай схемы «звезда».
- **По ограничениям (4.18).** Соединение внешнего ключа со своим первичным ключом: каждая строка дочерней
  таблицы находит ровно одну родительскую. Параметр `ExtStatisticsConstraints`.

## 4. Hash join

- **Внешние соединения (4.11).** Hash join для LEFT JOIN; перенос работы из Firebird 6.
- **Проверка совпадений и NULL-ключи (4.12).** После совпадения хеша условие проверяется по реальным
  значениям.
- **Батчи (4.19, 4.25).** Сторона, которая не помещается в хеш-таблицу, делится на батчи. Батч, сброшенный
  на диск, загружается при построении.
- **Обычный hash join и временный файл (4.27).** Сброшенная на диск сторона загружается или упорядочивается
  по ключу.
- **Слияние звезды (4.24, 4.29).** Несколько hash join по одному ключу собираются в один узел; узел сам
  проверяет совпадения.
- **Условие без лишних равенств (4.26).** Hash join в цепочке проверяет только свои равенства.
- **Цена (4.20, 4.28).** Бюджет временного кэша не зависит от текущей нагрузки: план одинаков при каждой
  компиляции. Цена считается для той формы hash join, которая будет построена.
- Параметры: `HashJoinBatchMemory`, `TempCachePlanPercent`.

## 5. Порядок соединения и выбор метода

- **Риск вложенного цикла (4.23).** После соединения, которое размножает строки, ошибка оценки дороже для
  вложенного цикла, чем для hash join. Цена вложенного цикла получает надбавку.
- **Риск по степени ключа (4.33, 4.38, 4.39).** `LoopJoinWorstCase`: цена обоих методов считается дважды —
  при оценке и в худшем случае по степени ключа. Hash join выбирается, когда потеря вложенного цикла в
  худшем случае больше.
- **Динамическое программирование (4.30, 4.37).** `JoinOrderDP = true`: после обычного поиска порядок
  уточняется перебором с ограничением `JoinOrderDPBudget`. По умолчанию выключено.
- **Цена промахов кэша (4.31).** `OptimizerPageMissCost`: вложенный цикл по таблице больше страничного
  кэша получает цену чтений с диска.
- **ORDER или SORT (4.8).** Выбор между навигацией по индексу и сортировкой делается по цене; перенос
  FirebirdSQL/firebird PR 8316.

## 6. Агрегаты

- **Счёт без чтения строк (4.32, 4.40).** `AggregateJoinCounting`: `COUNT(*)`, `SUM`, `AVG` над соединением
  не читают строки потока, на который ничто не ссылается: берётся их число. Раздел 4.40 распространяет это
  на цепочки потоков с общим ключом.
- **Хеш-группировка (4.34).** GROUP BY с известным числом групп выполняется через хеш-таблицу, без
  сортировки входа. Параметр `AggregateHashMemory` (0 выключает).
- **Hash unique (4.41).** То же для `SELECT DISTINCT`.
- **Сброс на диск (4.42).** Оба метода пишут строки новых групп в секции на диске, когда бюджет занят.
- **Правило выбора (4.43).** Хеш-группировка работает с `FIRST`/`ROWS` и с `DISTINCT` + `ORDER BY`. Цена
  учитывает сброс на диск. Выбор откладывается до скомпилированного входа, когда группы не помещаются в бюджет.
- **Строковый ключ переменной длины (4.44).** Ключ `VARCHAR` занимает в группе столько байт, сколько в нём
  символов.

Следующие пункты находятся в открытых PR 60–62 и в ветку ещё не влиты.

- **Ключ-выражение (4.45).** GROUP BY по выражению идёт через хеш без индекса по выражению.
- **Перенос состояния агрегатов (4.46).** Состояние копируется в группу только при смене группы.
- **Память из временного кэша (4.47).** Узел берёт до `max(AggregateHashMemory, TempCacheLimit / 2)`.
- **`MIN` / `MAX` по строке (4.48).** Строковые агрегаты идут через хеш-группировку.
- **`UNION` без `ALL` (4.49).** Проекция объединения идёт через Hash Unique; оценка — сумма по ветвям.
- **Сокращение ключа (4.50).** Столбцы, зависящие от первичного ключа, выходят из ключа группы.
- **Подсчёт строк соединения при GROUP BY (4.51).** `AggregateJoinCounting` работает под хеш-группировкой.
- **Хеш-таблица групп (4.52).** Заполнение 1, блоки степени двойки, точный учёт памяти.
- **Неизвестное число строк входа (4.53).** Выбор откладывается, когда у таблицы нет собранной статистики.

## 7. Исправления ошибок

- **`SubQueryConversion` (4.35).** Подзапрос с внешней ссылкой внутри вложенного подзапроса превращался в
  полусоединение и давал неверный результат. Это ошибка Firebird 5.
- **Статистика составного индекса по убыванию (4.36).** `CREATE INDEX` и `SET STATISTICS` считали два значения
  как одно: 100 различных значений вместо 200.
- **Счёт агрегата и вложенные подзапросы (PR 47).** Неверный результат: 3600 вместо 3544.
- **Веса строк и правило худшего случая (4.38).** Четыре мелких дефекта.
- **Падение при GROUP BY по столбцам 5 и более таблиц (PR 55).** Найдено на запросе DSB 64.
- **Повторное выполнение запроса с Hash unique (PR 56).** Падение на втором вызове процедуры.
- **Хеш-методы: 8 дефектов исполнения и 5 дефектов выбора плана** из ревью 22.11.2026 (неверные результаты
  MIN/MAX по строке и DISTINCT, ошибки сброса на диск, утечки памяти, `FIRST ... GROUP BY`, пользовательский
  PLAN). Исправлены коммитами `ac09e98609` … `30e5fc5aaa`.

## Параметры конфигурации

Все параметры задаются на базу данных, если не сказано иное.

- `ExtendedStatistics = false` — использовать расширенную статистику.
- `ExtStatisticsMcvEntries = 100` — число записей в многоколоночных списках частых значений.
- `ExtStatisticsConstraints = false` — оценка соединений по ограничениям.
- `PredicateCorrelation = false` — частичная зависимость условий.
- `ShowExplainCardinality = false` — показывать оценку строк в плане.
- `HashJoinBatchMemory = 16M` — память, в которую hash join загружает сторону, сброшенную на диск.
- `TempCachePlanPercent = 80` — доля временного кэша, на которую рассчитывает план.
- `JoinOrderDP = false`, `JoinOrderDPBudget = 100000` — поиск порядка динамическим программированием.
- `OptimizerPageMissCost = 100` — цена промаха страничного кэша (0 выключает).
- `AggregateJoinCounting = true` — счёт агрегата без чтения строк.
- `AggregateHashMemory = 8M` — бюджет хеш-группировки и hash unique (0 выключает).
- `LoopJoinWorstCase = true`, `LoopJoinWorstCaseWeight = 64` — правило худшего случая вложенного цикла.

## Измеренные результаты

Здесь только числа, которые получены в проверках 20–22.11.2026 на стенде dellg15 и локально.

- **Счёт агрегата по цепочкам (4.40).** 289 из 691 запроса стенда изменили план. Время этих запросов:
  2787 с против 3067 и 3140 с. Запрос `scale_014`: 68 с, раньше не заканчивался за 300 с.
- **`FIRST 1 ... GROUP BY` после исправления.** 27 832 обращения к страницам вместо 1 031 261.
- **Хеш-группировка на TPC-H, JCC-H, DSB (масштаб 1), база `68e755c29d`.** План меняется у 97 запросов из
  531. Замер этих запросов: 4 круга (без хеша, с хешем, с хешем, без хеша), 95 запросов завершились во всех
  кругах, 2 упёрлись в тайм-аут 300 с в обоих режимах.
  - Лучшее время из двух кругов, сумма: 304,0 с без хеша, 284,4 с с хешем (быстрее на 6 %).
  - Сумма двух кругов: 635,4 с без хеша, 660,5 с с хешем (медленнее на 4 %). Круги одного режима
    расходятся на 6–13 %, поэтому обе цифры лежат в пределах шума стенда.
  - По наборам (лучшее время): TPC-H 0,91; JCC-H norm 0,89; JCC-H skew 0,86; DSB s1 0,97; DSB s2 1,00.
  - Быстрее больше чем на 10 %: 17 запросов. Медленнее больше чем на 10 %: 7 запросов. Остальные 71 в
    пределах 10 %.
  - Явный выигрыш: группировка большой таблицы в малое число групп. `tpch_01`: 14,0 → 10,0 с;
    `jcch_skew_09`: 18,9 → 13,6 с; `tpch_11`: 0,93 → 0,74 с.
  - Hash unique (10 запросов DSB, шаблон 054): 28,8 → 30,3 с, без выигрыша.
- Результаты запросов с хешем и без него совпадают во всех 95 запросах во всех четырёх кругах.

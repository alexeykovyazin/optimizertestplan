### 1.2. Почему MCV и гистограммы не помогают

Размер соединения k таблиц по одному ключу: `J = Σ по v Π cᵢ(v)`, где `cᵢ(v)` — число строк таблицы i с ключом v.
Чтобы его посчитать, нужны числа строк **одного и того же ключа** в разных таблицах.

- **Гистограмма** хранит границы корзин. Число строк отдельного ключа в ней не хранится.
- **MCV-список** хранит до 100 значений на колонку. У `movie_id` около 2.5 млн значений.
- **Списки разных таблиц держат разные ключи.** 100 самых частых фильмов `cast_info` — не те же, что у
  `movie_keyword`. Произведение считается только по пересечению списков.
- **В режиме SCAN список строится по выборке строк.** Размер выборки — 300 × BINS = 30 000 строк
  (`Collector.cpp`, `scanTableSampled`). Для `cast_info` это 0.083% таблицы. Фильм с 1 000 строк даёт в выборке
  0.83 строки (расчёт). Список для такой колонки — почти случайные ключи с неверными счётчиками.
- **После первого соединения оценка по распределениям отключена.** `InnerJoin::estimateCost` вызывает
  `getJoinSelectivity` с признаком `position == 1` (`InnerJoin.cpp`, строки 538–546). Причина в комментарии: после
  соединения значения ведущей стороны размножены, парная оценка неверна. С третьей таблицы действует среднее на ключ.

Вывод: нужна структура, которая даёт `cᵢ(v)` для **общих** ключей нескольких таблиц.

### 1.3. Чего замер не показывает

- Замер 1.1 сделан без фильтров. Он показывает связь числа строк между таблицами.
- Запросы scale и job-light несут фильтры (`t.kind_id = 1`, `mi.info_type_id = 4`). Фильтр может быть связан с
  числом строк на ключ: у полнометражных фильмов больше актёров, чем у серий (не проверено).
- Медианы scale (2.1 / 5.9 / 44) близки к множителям замера без фильтров (2.0 / 14.6 / 116) по порядку величины.
  Это довод, что главная причина — связь между таблицами. Это довод, а не замер.

## 3. Рекомендуемый вариант подробно

Название объекта: **выборка ключей** (key sample).

### 3.1. Синтаксис

**Версия 1: нового синтаксиса нет.**

```sql
-- сбор: существующая команда, режимы SCAN (по умолчанию) и FULL
ALTER DATABASE REFRESH STATISTICS;
ALTER DATABASE REFRESH STATISTICS FOR TABLE CAST_INFO;
ALTER DATABASE REFRESH STATISTICS SCAN FOR TABLE CAST_INFO COLUMN MOVIE_ID;

-- режим SAMPLE выборку ключей не строит; прежняя остаётся
ALTER DATABASE REFRESH STATISTICS SAMPLE;
```

- Включение: параметр базы `ExtStatisticsKeySample = <m>` в `firebird.conf` / `databases.conf`. `m` — бюджет
  записей на колонку. `0` — не собирать и не использовать. Значение по умолчанию в первой версии — `0`.
- Обновление: любой REFRESH в режиме SCAN или FULL, который покрывает таблицу или эту колонку.
- Удаление: параметр в `0`, затем REFRESH таблицы удаляет её строки вида «выборка ключей». Команда
  `ALTER DATABASE DROP EXTENDED STATISTICS` удаляет всё хранилище, как сейчас.
- `BINS n` на выборку ключей не влияет.
- Просмотр: `SHOW EXTENDED STATISTICS` и `SHOW STATISTICS FOR <таблица>` показывают строку структуры (число записей,
  покрытие, размер). Значения не декодируются, как и у остальных структур.

**Версия 2 (только если версия 1 себя оправдает): регистрация в форме заметок 3.9.**

```
CREATE EXTENDED STATISTICS <имя> ON <таблица> (<колонка>) KEYS [ENTRIES <n>];
DROP EXTENDED STATISTICS <имя>;
ALTER DATABASE REFRESH STATISTICS <имя> [SCAN | FULL];
```

```sql
CREATE EXTENDED STATISTICS KS_CI_MOVIE ON CAST_INFO (MOVIE_ID) KEYS;
CREATE EXTENDED STATISTICS KS_MK_MOVIE ON MOVIE_KEYWORD (MOVIE_ID) KEYS ENTRIES 4096;
ALTER DATABASE REFRESH STATISTICS KS_CI_MOVIE;
DROP EXTENDED STATISTICS KS_CI_MOVIE;
```

Как это ложится на 3.9:

- `KEYS` — третье слово вида рядом с `NDISTINCT` и `MCV`. Слово не резервируется, проверяется командой.
- Вид `KEYS` требует **ровно одну** колонку. Сейчас 3.9 требует от двух до шестнадцати; правило расширяется только
  для этого вида. Слово `KEYS` обязательно: одна колонка без слова остаётся ошибкой.
- `ENTRIES <n>` — новое необязательное слово, бюджет записей этой структуры. Без него действует параметр базы.
- Именованная структура владеет колонкой: автоматическая по ней не собирается (то же правило, что в 3.9).
- `REFRESH <имя> SAMPLE` — ошибка: выборке ключей нужен полный проход.
- Права — как у `CREATE INDEX`, как в 3.9.

Отношение к `CREATE JOIN STATISTICS` (заметки 5.6):

- Join-профиль 5.6 — объект **пары**: FK-колонка потомка и колонка родителя. Он отвечает на вопрос «сколько строк
  потомка у родителей с таким значением атрибута». Таких объектов нужно по одному на каждую пару.
- Выборка ключей — объект **одной колонки одной таблицы**. Поэтому она идёт в семейство `EXTENDED STATISTICS`,
  а не `JOIN STATISTICS`.
- Они не заменяют друг друга. Связь фильтра с числом строк на ключ (предел из раздела 4.2) — территория 5.6.
  У 5.6 как раз есть проблема масштаба, которую называет рецензент.

### 3.2. Какие колонки и кто решает

### 3.3. Алгоритм сбора

**Хэш.** `h(v) = hash64(canon(v))`. Функция — та же, что в `DistinctCounter.h`: FNV-1a по байтам плюс финализатор
Murmur3. `u(v) = h(v) / 2^64` — число в `[0, 1)`.

**Почему хэш значения должен совпадать между таблицами.** Отбор решает только `u(v)` и число строк ключа. Ключ с
малым `u(v)` попадает в выборку каждой таблицы, где он есть. Поэтому пересечение выборок не пусто, и для общих
ключей известны счётчики во всех таблицах. При независимом отборе пересечение выборок размера 1/K было бы 1/K².

**Каноническая форма.** Равные для движка значения должны давать равные байты. Области хэша версии 1:

| Область | Типы | Байты для хэша |
|---|---|---|
| 1, целые | SMALLINT, INTEGER, BIGINT, NUMERIC/DECIMAL с масштабом 0 на этих типах | int64, 8 байт, младший байт первым |
| 2, текст | CHAR, VARCHAR с набором символов и колляцией | ключ равенства колляции; параметры области — набор и колляция |
| 3, байты | CHAR/VARCHAR OCTETS, BINARY, VARBINARY | байты значения |
| 4, дата | DATE | int32 |
| 5, время и дата | TIMESTAMP без зоны | 8 байт |

- Две колонки сопоставимы, только когда область и её параметры равны. `INTEGER` и `BIGINT` сопоставимы.
- Вне версии 1: INT128, числа с масштабом, FLOAT, DOUBLE, DECFLOAT, TIME, типы с зоной, BOOLEAN, BLOB.
- Не проверено по коду: какая функция движка даёт ключ равенства колляции и как сравниваются `CHAR` разной длины.
  Если это сложно, версия 1 оставляет области 1, 3, 4, 5.

**Правило отбора.** Ключ v с числом строк c(v) входит в выборку, когда

```
u(v) < min(1, c(v)^α / T)
```

- `m` — бюджет записей. `T` подбирается так, чтобы записей было не больше `m`.
- `α` — показатель правила, один на базу, записан в заголовке структуры:
  - `α = 0`: вероятность одна для всех ключей (`hash mod K` из наброска, `K = T`);
  - `α = 1`: вероятность растёт с числом строк; ключ с `c(v) ≥ T` входит всегда (end-biased sampling);
  - `α = 1.5`: правило из работы Chen и Yi для соединений «многие ко многим».
- Какое α брать, решает шаг E2 эксперимента. Источники расходятся (раздел 6).
- Выборка при большем `T` — подмножество выборки при меньшем `T`. Это позволяет уменьшать её на ходу.

**Проходы.**

| Режим REFRESH | α = 0 | α > 0 |
|---|---|---|
| FULL | Из сортированного потока колонки (он уже есть, заметки 3.4) | То же |
| SCAN | В полном проходе `scanTableNd`, рядом со счётчиком HyperLogLog | Колонка-кандидат дополнительно подаётся в `ValueSorter` в том же проходе |
| SAMPLE | Не строится, прежняя выборка остаётся | То же |
| Малая таблица (читается целиком) | Строится | Строится |

- **α = 0, проход SCAN.** Хэш значения в этом проходе уже считается для HyperLogLog (сейчас по сырым байтам; нужна
  каноническая форма). Для значений с `u(v) < 1/T` ведётся хэш-таблица «хэш → счётчик». Когда записей больше
  `1.25·m`, `T` удваивается и лишние записи удаляются. Счётчики точны: ключ, который проходит порог, считается с
  первой строки. Память — `m` записей на колонку. Дополнительного чтения нет.
- **α > 0.** Решение о ключе зависит от его полного числа строк. Оно известно только в конце. Нужен поток
  `(значение, число строк)` по всем ключам. Его даёт существующий `ValueSorter`: внешняя сортировка слиянием,
  1–8 МБ памяти на колонку, остальное во временных файлах. Поток прокачивается один раз: счётчик, хэш, проверка
  порога, буфер на `1.25·m` записей с тем же удвоением `T`.
- Попутно поток даёт точные `Σc²`, максимум `c` и точное число различных значений. Они пишутся в заголовок.

**Что может и чего не может выборка строк.** Выборка доли f видит ключ с c строками в среднем `c·f` раз. При
f = 0.083% и c = 15 это 0.012. Число строк отдельного ключа из неё не получить. Она находит только ключи с
`c ≳ 5/f` (для `cast_info` — от 6 000 строк) и даёт частоты частот для оценки числа различных значений. Поэтому
режим SAMPLE выборку ключей не строит.

**Другой источник, не для версии 1: проход по листьям индекса.** Индекс хранит ключи по порядку, число строк ключа
— длина серии дубликатов. Так уже работает `SET STATISTICS INDEX`.

- Плюсы: читается только индекс; сортировка не нужна; работает и в режиме SAMPLE.
- Минусы: счётчики включают невидимые версии записей; ключ индекса нужно перевести в каноническую форму (нового
  кода для этого нет); только индексированные колонки.

### 3.4. Что хранится

Одна строка `STAT$MULTI_COLUMNS` на колонку. Новых таблиц и колонок нет.

| Колонка | Значение |

### 3.5. Инвалидация и старение

- Каждый REFRESH увеличивает `GENERATION` и сбрасывает кэши операторов всех присоединений (заметки 4.1). Нового
  механизма нет.
- Кэш статистики присоединения читает строку вида 2 вместе с остальными структурами таблицы. Декодирование —
  по первому запросу оценки, а не при загрузке таблицы (память, раздел 5.3).
- **Рост таблицы.** Оценка умножается на `кардинальность сейчас / N` каждой стороны. Это допущение: все ключи
  растут одинаково. Новые ключи выборка не видит. Так же стареет MCV-список.
- **Предел возраста.** Выборка не используется, когда кардинальность таблицы ушла от N больше чем вдвое.
- **REFRESH SAMPLE** выборку не трогает. Её возраст виден в `STAT$UPDATED`.
- **Разное время сбора в разных таблицах** допустимо: каждая сторона масштабируется сама.
- Удалённая или ставшая вычисляемой колонка: строку удаляет обычная очистка (3.7, 3.9).
- Строка с неизвестной версией, хэш-функцией или областью не используется. Оценка идёт прежним путём.

### 3.6. Использование оптимизатором

**Обозначения.** Класс равенства E — колонки, связанные равенствами соединения. S — потоки запроса с колонкой из E.
`cᵢ(v)` — число строк ключа v в колонке потока i. `πᵢ(v) = min(1, cᵢ(v)^α / Tᵢ)` — вероятность, с которой ключ
вошёл в выборку потока i. `Sᵢ` — выборка.

**Два потока.**

```
Ĵ(A, B) = Σ по v из S_A ∩ S_B   a(v) · b(v) / min(π_A(v), π_B(v))
```

**k потоков одного класса.**

```
Ĵ(S) = Σ по v из ∩ Sᵢ   Π cᵢ(v) / min по i πᵢ(v)
```

- Ключ попадает в пересечение с вероятностью `min πᵢ(v)`: решает один и тот же `u(v)`. Деление на неё делает
  оценку несмещённой.
- При α = 0 и одном K для всех таблиц формула совпадает с наброском: `K × Σ Π cᵢ(v)`.
- NULL в выборке нет. `IS NOT DISTINCT FROM` выборкой не обслуживается.

**Особые стороны.**

| Сторона | Что делает оценка |
|---|---|
| Уникальная колонка (PK, UNIQUE) | В произведение не входит: `c = 1`, считается, что каждый ключ других сторон в ней есть |
| Колонка с полным MCV-списком (nd ≤ BINS) | Список служит полной выборкой: `π = 1`, хэши значений считаются при загрузке |
| Один поток в классе | `Ĵ = N` (кардинальность), выборка не читается |
| Колонка без выборки | Потоки с выборками оцениваются формулой; этот поток присоединяется прежним правилом «среднее на ключ» |
| Разные области хэша или идентификаторы хэш-функции | Прежний путь для всего класса |

- Уникальная сторона вынесена намеренно. Её выборка дала бы каждому ключу вероятность `m / N`, и она стала бы
  минимумом для всех ключей. Тяжёлые ключи терялись бы.
- Допущение «каждый ключ есть в уникальной колонке» верно при объявленном FK. Без FK оно не проверяется.

**Локальные фильтры.** Фильтр потока i с селективностью `sᵢ` считается независимым от числа строк на ключ:

```
Ĵ_f(S) = Ĵ(S) · Π sᵢ
```

При независимости это точно в среднем: произведение линейно по каждому `cᵢ`. При связи фильтра с числом строк
ошибка остаётся (раздел 4.2). Сейчас модель делает то же допущение.

**Где вызывается.** `InnerJoin::estimateCost(position, stream, …)`, для любой позиции от 1.

1. Собрать потоки префикса `joinedStreams[0 … position−1]`, у которых есть равенство по колонке того же класса,
   что у присоединяемого потока i. Это множество P.
2. Число строк потока i на одну строку префикса: `f = Ĵ(P ∪ {i}) / Ĵ(P) · sᵢ`.
3. Это число идёт туда, куда сейчас идут парная оценка 4.9 и условная 4.13: в оценку индексного поиска по колонке
   соединения и в селективность соединения для hash join. Оба метода должны получать одно число.

Проверка формулы на простых случаях:

- `P = {title}` (уникальная), i = `cast_info`: `f = N_ci / N_title` — среднее на ключ, как сейчас и как 4.18.
- `P = {cast_info}`, i = `movie_keyword`: `f = Σ a·b / Σ a` — среднее число ключевых слов, взвешенное по числу
  актёров. Это и есть поправка: строки префикса сосредоточены на тяжёлых ключах.

**Память оценок.** Результат `Ĵ` запоминается на компиляцию по паре (класс, множество потоков), как `joinSelMemo`.
Предел — 64 записи на класс; дальше прежний путь.

**Сочетание с существующими оценками.**

| Оценка | Правило |
|---|---|
| 4.18, FK к своему ключу | Работает первой, как сейчас. С выборкой согласована: уникальная сторона даёт то же число |
| 4.13, фильтр внешнего потока через совместный MCV | Имеет приоритет на своей паре: она знает фильтр. Открытый вопрос 9 |
| 4.9, слияние MCV-списков пары | Остаётся для пар без выборок. При выборках на обеих сторонах её заменяет формула выше |
| «MCV-часть» из наброска | Отдельно не существует. При α > 0 тяжёлые ключи уже в выборке, двойного счёта нет |

Не проверено по коду: как именно число из шага 3 доходит до `Retrieval::getInversionCandidates` на позициях от 2
и до расчёта кардинальности реки. Точки вызова названы по образцу 4.9.

Предел хэш-таблицы в 4 млн записей (`HashJoin::maxCapacity`) не затрагивается. Меняется только вход существующего
выбора между формами.

### 3.7. Размер выборки и ожидаемая ошибка

Дисперсия оценки (формула Горвица–Томпсона, `x(v) = Π cᵢ(v)`, `π(v) = min πᵢ(v)`):

```
Var(Ĵ) = Σ по v   x(v)² · (1/π(v) − 1)
CV = sqrt(Var) / J
```

- При α = 0: `CV² = (K − 1) · Σ x² / (Σ x)²`. Всё решает доля суммы на самых тяжёлых ключах.
- При α = 1, два потока (мой вывод, грубая граница): `CV² ≤ (T_A · b_max + T_B · a_max) / J`, где `a_max`, `b_max`
  — наибольшие числа строк лёгких ключей.
- Реальные значения CV для IMDB неизвестны. Шаг E2 считает их точно, без случайности, по формуле выше.

Выбор `m`:

- `m = 1024` — предлагаемое значение для первого включения. Порог при α = 1 равен `N / m`: для `cast_info`
  (36 244 344 строк) T ≈ 35 400, для `movie_keyword` около 4 400 (расчёт; размер таблицы — по стандартному дампу
  JOB, на стенде не сверял).
- Ошибка падает примерно как `1/sqrt(m)`. Учетверение `m` уменьшает CV вдвое.
- Цель: CV ≤ 0.5 для звезды из четырёх таблиц. Это ошибка в пределах ×2 в большинстве случаев. Сейчас ошибка — 116.
- Отбор детерминирован: между обновлениями в выборку входят те же ключи. Оценка не скачет от REFRESH к REFRESH.
  Обратная сторона: неудачная выборка не исправляется повторным сбором.

## 4. Ответ на возражение 2: сколько объектов и что не покрыто

### 4.1. Счёт объектов

**Это статистика колонки, а не пары и не соединения.**

| Подход | Объектов для n ключевых колонок одного класса |
|---|---|
| Выборка ключей | n |
| Статистика на пару колонок | n·(n−1)/2 |
| Статистика на соединение k таблиц (DB2 statistical view, индексированное представление SQL Server) | до 2ⁿ |

Для восьми колонок `movie_id` стенда: 8 выборок против 28 пар и 247 подмножеств из двух и более таблиц.

- Одна выборка колонки служит любому соединению по этой колонке: с любой таблицей, в любом числе таблиц.
- Это следует из общего правила отбора: выборки складываются при компиляции, а не при сборе.
- Сравнение со статистикой на комбинации колонок неточно. Там объект нужен на каждую комбинацию. Здесь — на
  каждую колонку.

### 4.2. Что не покрыто

| Случай | Что происходит |
|---|---|
| Ключи разных классов равенства (`ci.movie_id = t.id AND ci.person_id = n.id`) | Каждый класс оценивается отдельно, классы считаются независимыми — как сейчас |
| Фильтр, связанный с числом строк на ключ (`t.kind_id = 1`, если у фильмов больше строк, чем у серий) | Фильтр считается независимым. Ошибка остаётся. Это главный предел |
| Фильтр по самой ключевой колонке (`mk.movie_id < 100000`) | Значений в выборке нет. Считается независимым |
| Составные ключи (два равенства между одними потоками) | Не обслуживается. Остаются совместные MCV 4.9 |
| Выражения в условии соединения | Не обслуживается |
| Неравенства, `IS NOT DISTINCT FROM` | Не обслуживается |
| Внешние соединения | Версия 1 — только `InnerJoin` |
| Таблица собрана в режиме SAMPLE и раньше не собиралась в SCAN | Выборки нет, прежний путь |
| Ключи, которых нет в уникальной колонке без FK | Завышение |

- Строка про фильтр — самая важная. Работа Vengerov и др. решает её хранением **строк** выборки целиком и
  применением фильтра к ним при компиляции. Здесь хранятся только счётчики. Хранить строки — другой объём
  работы: все колонки, длинные значения, вычисление предикатов при подготовке запроса.
- Самосоединение по одной колонке покрыто: `Ĵ = Σ c²/π`, оно же `Σc²` из заголовка.

## 5. Цена

### 5.1. Сбор

| Правило | Дополнительное чтение | Дополнительная работа |
|---|---|---|
| α = 0 | Нет | Хэш уже считается; поиск в таблице на `m` записей для доли `1/T` строк |
| α > 0 | Нет чтения таблицы; запись и чтение временных файлов сортировки | Внешняя сортировка всех не-NULL значений колонки |

- Для α > 0 цена на колонку — та же, что платит режим FULL за одну колонку. `cast_info`: три колонки-кандидата
  (`movie_id`, `person_id`, `person_role_id`), по 36 млн значений.
- **Время не замерено.** Способ замера без нового кода:
  `ALTER DATABASE REFRESH STATISTICS FULL FOR TABLE CAST_INFO COLUMN MOVIE_ID` против того же с `SCAN`. Разница —
  цена сортированного потока одной колонки.
- Временное место на колонку `cast_info` — порядка сотен МБ в худшем случае (расчёт: 36 млн значений по 4 байта
  плюс служебные поля; сортировщик сливает равные значения внутри чанка, реальное число меньше).
- Проход по листьям индекса (раздел 3.3) был бы дешевле: индекс `MOVIE_ID_CAST_INFO` в разы меньше таблицы (не
  проверено, размер индекса на стенде не смотрел).

### 5.2. Хранение

| Величина | Значение |
|---|---|
| Одна колонка, `m = 1024` | около 16 КБ, не больше 20.5 КБ |
| Одна колонка, `m = 4096` | около 66 КБ |
| Стенд IMDB, 15 колонок, `m = 1024` | около 250 КБ |
| JSON-копия (временная) | около 50 байт на запись, 50 КБ на колонку |
| Строк в `STAT$MULTI_COLUMNS` | +15 |

Для сравнения: совместный MCV держит до 10 000 записей на структуру (заметки 3.8).

### 5.3. Компиляция и память

- **Оценка.** Слияние k отсортированных массивов: около `k · m` сравнений. Для 5 таблиц и `m = 1024` — 5 000
  шагов, микросекунды (расчёт). На компиляцию — не больше 64 оценок на класс.
- **Первое обращение.** Чтение блоба (16 КБ — три страницы по 8 КБ) и разбор. Один раз на присоединение и таблицу.
- **Память.** Кэш статистики — свой у каждого присоединения (заметки 4.1). 16 КБ на колонку на присоединение.
  1 000 присоединений × 5 колонок = 80 МБ в худшем случае (расчёт). Меры: декодировать только по запросу оценки;
  меньший `m`.
- **Выполнение.** Нет затрат.

### 6.3. Что заимствовано и что новое

- **Заимствовано:** общий хэш значения соединения (2006, 2015); хранение точных пар «значение, частота» с порогом
  (2006); формула оценки и её несмещённость (2006); k таблиц одного класса (2015); показатель 1.5 (2017).
- **Новое только в инженерной части:** хранение как постоянной статистики колонки в серийном оптимизаторе; хэш
  вместо значения; использование в виде отношения `Ĵ(P ∪ {i}) / Ĵ(P)` внутри перебора порядка; уникальная сторона
  без выборки.
- **Возражение 1 по существу верно:** серийные СУБД решают задачу иначе. Либо объектом на соединение (DB2, SQL
  Server), либо выборкой при компиляции (Oracle), либо никак (PostgreSQL, DuckDB, MySQL).

## 7. Риски и обратимость

| Риск | Чем он неудобен позже | Как удержать обратимость |
|---|---|---|
| Формат | Хэш-функция и каноническая форма типов становятся частью формата на диске | Идентификаторы хэша и области в заголовке. Неизвестная версия не читается, оценка идёт прежним путём. Пересбор дёшев: это статистика, не данные |
| Синтаксис | DDL нельзя убрать после выпуска | В версии 1 DDL нет |
| Смена планов | Оценки звёзд меняются на порядки, планы меняются | Параметр базы; значение по умолчанию 0; прогон трёх наборов до включения |
| Завышение | Сейчас ошибка односторонняя (63 занижения против 6 завышений). Несмещённая оценка с разбросом иногда завышает в 2–3 раза | Проверить в E3 долю завышений; сравнить планы |
| Бэкап и восстановление | `STAT$`-таблицы — обычные таблицы, переносятся с базой (заметки 2.1) | Запись не содержит идентификаторов отношений. Номера набора символов и колляции сверяются при загрузке |
| Репликация | Строки приходят на реплику как обычный DML | Загрузчик без поддержки вида 2 пропускает такие строки: `StatisticsCache.cpp`, условие `kind != MULTI_KIND_JOINT_MCV` → `continue`. Не проверено: что делает с ними REFRESH и очистка старой сборки |
| Переход между версиями | Старый движок видит новые строки | То же правило пропуска. Новый движок старых строк не требует |
| Память | 16 КБ на колонку на присоединение | Декодирование по запросу; предел `m` |
| Постоянная выборка | Те же ключи при каждом сборе; неудачный набор не исправить | Хэш-функция — часть формата; смена — новая версия формата |
| Первые в отрасли | Нет чужого опыта эксплуатации | Версия 1 выключена по умолчанию и удаляется параметром |

Порядок отката:

1. `ExtStatisticsKeySample = 0` — оптимизатор перестаёт читать выборки сразу после перезагрузки конфигурации.
2. Следующий REFRESH таблицы удаляет её строки вида 2.
3. Таблицы хранилища не менялись — пересоздавать их не нужно.

Цель: доказать или закрыть идею запросами SQL. Движок не меняется. Запросы **не запускались**.
Стенд — когда освободится. Все шаги кроме E0 читают только вспомогательную таблицу и идут секунды–минуты.

### E0. Таблица счётчиков по ключу

```sql
CREATE TABLE X3_KEY (
  MOVIE_ID INTEGER NOT NULL,
  C_CI  BIGINT NOT NULL,
  C_MK  BIGINT NOT NULL,
  C_MI  BIGINT NOT NULL,
  C_MC  BIGINT NOT NULL,
  C_MII BIGINT NOT NULL,
  U DOUBLE PRECISION NOT NULL,
  CONSTRAINT X3_KEY_PK PRIMARY KEY (MOVIE_ID)
);
COMMIT;

INSERT INTO X3_KEY (MOVIE_ID, C_CI, C_MK, C_MI, C_MC, C_MII, U)
SELECT d.movie_id, SUM(d.ci), SUM(d.mk), SUM(d.mi), SUM(d.mc), SUM(d.mii),
       BIN_AND(HASH(CAST(d.movie_id AS VARCHAR(12)) USING CRC32), 16777215) / 16777216e0
FROM (
  SELECT movie_id, COUNT(*) ci, 0 mk, 0 mi, 0 mc, 0 mii FROM cast_info GROUP BY movie_id
  UNION ALL
  SELECT movie_id, 0, COUNT(*), 0, 0, 0 FROM movie_keyword GROUP BY movie_id
  UNION ALL
  SELECT movie_id, 0, 0, COUNT(*), 0, 0 FROM movie_info GROUP BY movie_id
  UNION ALL
  SELECT movie_id, 0, 0, 0, COUNT(*), 0 FROM movie_companies GROUP BY movie_id
  UNION ALL
  SELECT movie_id, 0, 0, 0, 0, COUNT(*) FROM movie_info_idx GROUP BY movie_id
) d
GROUP BY d.movie_id;
COMMIT;
```

- `U` — число в `[0, 1)` из хэша ключа, заменяет `u(v)`.
- После эксперимента: `DROP TABLE X3_KEY; COMMIT;`. Таблица в базе стенда влияет на `REFRESH STATISTICS` всей базы.
- Если `HASH(… USING CRC32)` даст плохую равномерность (проверка: `SELECT COUNT(*), AVG(U), MIN(U), MAX(U)`,
  среднее должно быть около 0.5), взять три байта `CRYPT_HASH(… USING SHA1)`.

### E2. Точный разброс оценки для трёх правил и трёх бюджетов

Считает CV по формуле раздела 3.7. Случайности нет.

```sql
WITH par AS (
  SELECT a.A, m.M
  FROM (SELECT 0e0 AS A FROM RDB$DATABASE UNION ALL
        SELECT 1e0 FROM RDB$DATABASE UNION ALL
        SELECT 1.5e0 FROM RDB$DATABASE) a
  CROSS JOIN
       (SELECT 256e0 AS M FROM RDB$DATABASE UNION ALL
        SELECT 1024e0 FROM RDB$DATABASE UNION ALL
        SELECT 4096e0 FROM RDB$DATABASE) m
),
tot AS (
  SELECT p.A, p.M,
    SUM(IIF(x.C_CI > 0, POWER(x.C_CI, p.A), 0e0)) / p.M AS T_CI,
    SUM(IIF(x.C_MK > 0, POWER(x.C_MK, p.A), 0e0)) / p.M AS T_MK,
    SUM(IIF(x.C_MI > 0, POWER(x.C_MI, p.A), 0e0)) / p.M AS T_MI,
    SUM(IIF(x.C_MC > 0, POWER(x.C_MC, p.A), 0e0)) / p.M AS T_MC
  FROM X3_KEY x CROSS JOIN par p
  GROUP BY p.A, p.M
),
k AS (
  SELECT t.A, t.M,
    CAST(x.C_CI AS DOUBLE PRECISION) * x.C_MK * x.C_MI * x.C_MC AS X,
    MINVALUE(1e0,
      POWER(x.C_CI, t.A) / t.T_CI, POWER(x.C_MK, t.A) / t.T_MK,
      POWER(x.C_MI, t.A) / t.T_MI, POWER(x.C_MC, t.A) / t.T_MC) AS PI
  FROM X3_KEY x CROSS JOIN tot t
  WHERE x.C_CI > 0 AND x.C_MK > 0 AND x.C_MI > 0 AND x.C_MC > 0
)
SELECT A, M,
  COUNT(*) AS KEYS,
  SUM(X) AS J,
  SUM(PI) AS MATCHED_EXPECTED,
  SQRT(SUM(X * X * (1e0 / PI - 1e0))) / SUM(X) AS CV
FROM k
GROUP BY A, M
ORDER BY A, M;
```

- `T` здесь — `Σ c^α / m`: ожидаемое число записей на колонку не больше `m`.
- `MATCHED_EXPECTED` — сколько ключей в среднем попадает в пересечение четырёх выборок.
- Для двух, трёх и пяти таблиц изменить три места: произведение `X`, список в `MINVALUE`, условие `WHERE`.
  Для пяти добавить `T_MII` в `tot`.

### E3. Распределение оценки по 64 выборкам

Для выбранных в E2 α и m. 64 выборки получаются сдвигом `U` на `s/64`.

```sql
WITH RECURSIVE s AS (
  SELECT 0 AS N FROM RDB$DATABASE
  UNION ALL
  SELECT s.N + 1 FROM s WHERE s.N < 63
),
par AS (SELECT 1e0 AS A, 1024e0 AS M FROM RDB$DATABASE),
tot AS (
  SELECT
    SUM(IIF(x.C_CI > 0, POWER(x.C_CI, p.A), 0e0)) / MAX(p.M) AS T_CI,
    SUM(IIF(x.C_MK > 0, POWER(x.C_MK, p.A), 0e0)) / MAX(p.M) AS T_MK,
    SUM(IIF(x.C_MI > 0, POWER(x.C_MI, p.A), 0e0)) / MAX(p.M) AS T_MI,
    SUM(IIF(x.C_MC > 0, POWER(x.C_MC, p.A), 0e0)) / MAX(p.M) AS T_MC
  FROM X3_KEY x CROSS JOIN par p
),
k AS (
  SELECT x.U,
    CAST(x.C_CI AS DOUBLE PRECISION) * x.C_MK * x.C_MI * x.C_MC AS X,
    MINVALUE(1e0,
      POWER(x.C_CI, p.A) / t.T_CI, POWER(x.C_MK, p.A) / t.T_MK,
      POWER(x.C_MI, p.A) / t.T_MI, POWER(x.C_MC, p.A) / t.T_MC) AS PI
  FROM X3_KEY x CROSS JOIN tot t CROSS JOIN par p
  WHERE x.C_CI > 0 AND x.C_MK > 0 AND x.C_MI > 0 AND x.C_MC > 0
),
e AS (
  SELECT s.N, SUM(k.X / k.PI) AS EST, COUNT(*) AS MATCHED
  FROM k CROSS JOIN s
  WHERE (k.U + s.N / 64e0) - FLOOR(k.U + s.N / 64e0) < k.PI
  GROUP BY s.N
),
j AS (SELECT SUM(X) AS J FROM k)
SELECT
  COUNT(*) AS SAMPLES,
  AVG(e.EST / j.J) AS R_AVG,
  MIN(e.EST / j.J) AS R_MIN,
  MAX(e.EST / j.J) AS R_MAX,
  SUM(IIF(e.EST BETWEEN j.J / 2 AND j.J * 2, 1, 0)) AS IN_X2,
  SUM(IIF(e.EST BETWEEN j.J / 10 AND j.J * 10, 1, 0)) AS IN_X10,
  SUM(IIF(e.EST > j.J * 2, 1, 0)) AS OVER_X2,
  MIN(e.MATCHED) AS MATCHED_MIN,
  MAX(e.MATCHED) AS MATCHED_MAX
FROM e CROSS JOIN j;
```

- `R_AVG` должен быть около 1 — проверка несмещённости.
- `SAMPLES < 64` означает, что в части выборок пересечение пусто (оценка 0).
- `IN_X2` — сколько выборок из 64 дали ошибку не больше ×2.

### E4. Вариант (c2): доля суммы на тяжёлых ключах

```sql
WITH r AS (
  SELECT
    CAST(C_CI AS DOUBLE PRECISION) * C_MK * C_MI * C_MC AS X,
    ROW_NUMBER() OVER (ORDER BY C_CI DESC) AS R_CI,
    ROW_NUMBER() OVER (ORDER BY C_MK DESC) AS R_MK,
    ROW_NUMBER() OVER (ORDER BY C_MI DESC) AS R_MI,
    ROW_NUMBER() OVER (ORDER BY C_MC DESC) AS R_MC
  FROM X3_KEY
)
SELECT n.TOPN,
  SUM(IIF(r.R_CI <= n.TOPN AND r.R_MK <= n.TOPN AND r.R_MI <= n.TOPN AND r.R_MC <= n.TOPN, r.X, 0e0))
    / SUM(r.X) AS SHARE_IN_ALL,
  SUM(IIF(r.R_CI <= n.TOPN OR r.R_MK <= n.TOPN OR r.R_MI <= n.TOPN OR r.R_MC <= n.TOPN, r.X, 0e0))
    / SUM(r.X) AS SHARE_IN_ANY
FROM r CROSS JOIN
     (SELECT 100 AS TOPN FROM RDB$DATABASE UNION ALL
      SELECT 1000 FROM RDB$DATABASE UNION ALL
      SELECT 10000 FROM RDB$DATABASE) n
GROUP BY n.TOPN
ORDER BY n.TOPN;
```

`SHARE_IN_ALL` — доля размера соединения, которую дал бы список из TOPN точных тяжёлых ключей на колонку.

### E5. Вариант (c1): границы без ключей

### E6. Фильтры: что остаётся после идеальной выборки

Решающий шаг. Пример — scale_351: `title`, `cast_info`, `movie_info` с `info_type_id = 4`, `movie_info_idx`.
Оценка движка 9.1 млн, на деле 40.7 млн.

```sql
SELECT
  (SELECT SUM(CAST(C_CI AS DOUBLE PRECISION) * C_MI * C_MII) FROM X3_KEY) AS J_UNFILTERED,
  (SELECT COUNT(*) FROM movie_info WHERE info_type_id = 4) * 1e0
    / (SELECT COUNT(*) FROM movie_info) AS S_MI,
  (SELECT SUM(CAST(k.C_CI AS DOUBLE PRECISION) * f.C * k.C_MII)
     FROM X3_KEY k
     JOIN (SELECT movie_id, COUNT(*) AS C FROM movie_info
           WHERE info_type_id = 4 GROUP BY movie_id) f ON f.movie_id = k.MOVIE_ID) AS J_TRUE
FROM RDB$DATABASE;
```

- `J_TRUE` должен совпасть с эталоном запроса.
- `J_UNFILTERED × S_MI` — оценка идеальной выборки ключей при независимом фильтре.
- `J_TRUE / (J_UNFILTERED × S_MI)` — **остаточная ошибка**: то, что выборка ключей не исправит никогда.

Для фильтра по `title` (job_light_051: `t.production_year > 1950 AND t.kind_id = 1`, оценка 16.4 млн, на деле 151 млн):

```sql
SELECT
  (SELECT SUM(CAST(C_CI AS DOUBLE PRECISION) * C_MK) FROM X3_KEY) AS J_UNFILTERED,
  (SELECT COUNT(*) FROM title WHERE production_year > 1950 AND kind_id = 1) * 1e0
    / (SELECT COUNT(*) FROM title) AS S_T,
  (SELECT SUM(CAST(k.C_CI AS DOUBLE PRECISION) * k.C_MK)
     FROM X3_KEY k JOIN title t ON t.id = k.MOVIE_ID
     WHERE t.production_year > 1950 AND t.kind_id = 1) AS J_TRUE
FROM RDB$DATABASE;
```

Набор для E6: scale_014, scale_351, job_light_051 и ещё не меньше 20 запросов из 63 заниженных
(`results/scale_c1_partial_summary.csv`), поровну по числу таблиц. Для всех 63 нужен генератор запросов по
тексту — отдельная небольшая задача.

### Условия решения

| Результат | Решение |
|---|---|
| E2: CV ≤ 0.5 для четырёх таблиц при `m ≤ 4096` хотя бы у одного α; E3: `IN_X2 ≥ 58` из 64 | Выборка работает как оценка. Дальше смотреть E6 |
| E2: CV > 1 при `m = 4096` у всех α | Закрыть вариант (b) |
| E2: α = 0 даёт CV не больше чем в 1.5 раза хуже лучшего | Взять α = 0: сбор без затрат |
| E4: `SHARE_IN_ALL ≥ 0.8` при TOPN = 1000 | Хватит варианта (c2) |
| E5: граница по рангу в пределах ×3 от `J4` | Рассмотреть (c1): без ключей и без хэша |
| E6: остаточная ошибка ≤ 3 у половины проверенных запросов и больше | Выборка исправляет основную часть ошибки. Строить |
| E6: остаточная ошибка > 10 у большинства | Главная причина — фильтры. Выборка ключей не поможет. Вариант (d); думать о 5.6 или о выборке строк |
| После предложения 1: из 63 заниженных запросов плохой план остался меньше чем у 10 | Отложить: выигрыша во времени нет |

## Дефект: условие подзапроса только по внешней таблице

### Проявление

```sql
select count(*) from p
where not exists (select 1 from d where d.k = p.k and p.x = 3);
```

Таблица `P` — 2 000 строк. Верный ответ — 1 750 строк. Сборка `913fdd7fb3` с `SubQueryConversion = true`
возвращала 250 строк.

`DELETE` с таким `NOT EXISTS` удалял 250 строк вместо 1 750.

До исправления неверный результат давали **24 запроса из 165**. Все они одного вида: в подзапросе есть равенство,
которое не ссылается на таблицы подзапроса. Формы:

| Форма условия в подзапросе | Пример | Верно | Было |
|---|---|---|---|
| Внешний столбец = константа | `d.k = p.k and p.x = 3` | 1 750 | 250 |
| Два внешних столбца | `d.k = p.k and p.x = p.j` | 1 846 | 189 |
| Только внешнее условие, без ключа | `from d where p.x = 3` | 1 500 | 0 |
| `IS NOT DISTINCT FROM` по внешнему столбцу | `d.k = p.k and p.j is not distinct from 1` | 1 845 | 189 |
| Выведенное равенство | `d.k = p.k and d.k = p.j` | 1 926 | 53 |
| Условие между двумя внешними таблицами | `d.k = p.k and p.j = c.j` | 1 845 | 140 |
| Вложенные циклы по индексу | `c.k = p.k and p.x = 3`, 9 внешних строк | 8 | 2 |

### Причина

`findDependentBooleans` выносит из подзапроса каждое равенство (`=`, `IS NOT DISTINCT FROM`), которое ссылается на
внешний запрос. Такое равенство может не ссылаться на таблицы подзапроса вообще. Кроме того, оптимизатор сам выводит
такие равенства: из `D.K = P.K` и `D.K = P.J` получается `P.K = P.J`.

- Для **полусоединения** (`EXISTS`) это условие — фильтр внешней стороны. Это верно.
- Для **антисоединения** это условие — часть условия совпадения. Внешняя строка, которая его не выполняет, не имеет
  пары. Запрос должен её вернуть.

Код применял условие как фильтр внешней стороны в двух местах `Optimizer::compile`:

1. `applyLocalBoolean` для потока внешней части брал все условия оптимизатора.
2. `CrossJoin` для единственного потока внешней части вызывал `applyBoolean` со всеми базовыми условиями. Это
   происходит до компиляции внутренней стороны.

### Исправление

Файл `src/jrd/optimizer/Optimizer.cpp`:

- Поток внешней части антисоединения получает только условия родителя (как внешняя сторона `LEFT JOIN`).
- `CrossJoin` получил параметр `applyConditions`. Внешняя часть антисоединения соединяется с `applyConditions = false`.
- Hash-антисоединение берёт в остаточное условие все неиспользованные базовые условия, а не только условия с
  внутренними потоками.
- Антисоединение вложенными циклами проверяет эти условия над внутренним источником записей (это уже делал `CrossJoin`
  для не первого потока).

Полусоединение не изменено.

### Второй коммит: `NOT EXISTS` без условия по своим таблицам остаётся подзапросом

После исправления подзапрос, у которого все равенства ссылаются только на внешний запрос
(`not exists (select 1 from d where p.x = 3)`), шёл антисоединением вложенными циклами. Результат был верный, но для
внешней строки, которая условие не выполняет, читалась вся внутренняя таблица. Как подзапрос он для такой строки не
открывается.

Коммит `99757f4952` (`findPossibleJoins` в `src/jrd/RecordSourceNodes.cpp`): преобразование `NOT EXISTS` требует хотя
бы одно условие, которое ссылается на поток подзапроса. Без него `NOT EXISTS` остаётся подзапросом. `EXISTS` не изменён.

| Запрос (2 000 внешних строк, 3 000 внутренних) | Антисоединение (первый коммит) | Подзапрос (второй коммит) |
|---|---|---|
| `not exists (select 1 from d where p.x = 3)` | 0,43 с, 4 694 863 обращения к страницам (fetches) | 0,001 с, 2 863 обращения к страницам (fetches) |

## Антисоединение из `LEFT JOIN`: что проверено

Все 86 запросов дают одинаковый результат с преобразованием и без него. Проверенные случаи:

- hash-соединение и вложенные циклы, в том числе уникальный индекс и явный `PLAN`;
- `NULL` в ключе внешней и внутренней стороны, пустая внутренняя таблица;
- дополнительные условия в `ON`: по внутренней таблице, по внешней таблице, неравенство между сторонами;
- ключ, равный константе; ключ из двух столбцов; ключ-выражение на внешней стороне;
- `IS NULL` по столбцу, который не является ключом (преобразования нет);
- другие условия `WHERE` по внутренней стороне рядом с проверкой `IS NULL`;
- `RIGHT JOIN`; три таблицы; вложенное внешнее соединение на внутренней и на внешней стороне;
- проверка `IS NULL` в `ON` внешнего соединения верхнего уровня;
- внутренняя сторона — производная таблица, агрегат, `UNION ALL`, представление;
- коррелированный подзапрос с таким соединением внутри; `EXISTS` и `NOT EXISTS` рядом с ним;
- `COUNT(*)` без других столбцов (подсчитываемые потоки), `GROUP BY`, `FIRST ... SKIP` с `ORDER BY`;
- `IS NOT DISTINCT FROM`, `OR` в `ON`, `OR` в `WHERE` (преобразования нет);
- строковые ключи, ключ с регистронезависимой сортировкой, `NUMERIC` против `INTEGER`.

По коду: проверка `IS NULL` снимается с родителя только тогда, когда соединение помечено как антисоединение, и оба
пути `OuterJoin::process` (hash-соединение и вложенные циклы) получают этот признак. Если признак не дошёл до
родителя, родитель применяет проверку ещё раз; это не меняет результат.

## Замечания без изменения кода

- **Оценка числа строк.** Антисоединение оценивается как половина строк внешней стороны, без статистики.
- **Выбор алгоритма.** `p left join c on c.k = p.k where c.k is null` при индексе по `c.k` идёт через hash-соединение
  с полным чтением `C`. Это решение стоимостной модели; время не измерялось.
- **Комментарий в `generateEquiJoin`.** Вставка блока special join разорвала комментарий о пакетном hash-соединении.
  Исправлено.

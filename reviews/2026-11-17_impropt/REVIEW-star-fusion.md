## F1 (critical). Слитый узел принимает реку с другим списком ключей

**Что происходит.** Многосторонний `HashJoin` сопоставляет каждую хэшируемую реку с **одним** хэшем ведущей
стороны. Хэш считается по склеенным байтам всех ключей стороны (`computeJoinHash`). Поэтому список ключей каждой
реки должен совпадать со списком ведущей стороны по числу ключей и по порядку классов.

Проверка в `InnerJoin::formRiver` этого не требует. Она требует только, чтобы каждый ключ со стороны префикса уже
был среди ключей узла (`fusedKeyFields`):

```cpp
for (FB_SIZE_T k = 0; absorb && k < keys[0]->getCount(); k++)
{
    const auto field = (*keys[0])[k];
    bool found = false;
    for (FB_SIZE_T j = 0; j < fusedKeyFields.getCount(); j++)
        if (field->sameAs(fusedKeyFields[j], false)) { found = true; break; }
    if (!found) absorb = false;
}
```

Река с меньшим или большим числом ключей проходит проверку. Её хэш считается по другому числу байт, с хэшем
ведущей стороны он почти никогда не совпадает, и река «не находит» строк. У слитого узла нет своего условия, а
фильтр над рекой может только отбросить лишние строки, но не вернуть потерянные.

**Воспроизведение** (`tests/65_star_fusion.sql`; четыре таблицы по 60 000 строк; каждый запрос сверяется с планом
nested loop):

| Случай | Запрос | parent | commit | nested loop |
|---|---|---|---|---|
| S2 | у первого соединения два ключа, у третьей таблицы один: `t1.x = t2.x and t1.y = t2.y and t1.x = t3.x` | 896 220 | **300** | 896 220 |
| S3 | у первого соединения один ключ, у третьей таблицы два: `t1.x = t2.x and t1.x = t3.x and t2.y = t3.y` | 896 305 | **200** | 896 305 |
| S5 | один класс, `=` и `IS NOT DISTINCT FROM` по тому же ключу | 2 694 600 | **1 800** | 2 694 600 |
| доп. | `t1.x = t2.x and t1.x = t3.x and t2.z = t3.z` | 389 220 | **50** | 389 220 |
| H2 теста 64 | `p.id = b.pid and p.id = g.pid and g.pid is not distinct from b.pid` | 3 992 000 | **200** | — |

Случаи с одинаковой формой ключей верны: S1 (один ключ), S4 (два ключа, условия в другом порядке), S6 (только
`IS NOT DISTINCT FROM`), S7 (четыре таблицы), S8 (четвёртая таблица по другому ключу — узел её не принимает).

**Почему S5 тоже ломается.** Равенство `IS NOT DISTINCT FROM` никогда не пропускается как повтор, поэтому у третьей
таблицы два ключа (`t3.x` дважды), а у ведущей стороны один.

**Исправление** (`fusion_keys.patch`, 15 строк): река принимается, только если

1. число её ключей равно числу ключей ведущей стороны: `keys[0]->getCount() == fusedKeys[0]->getCount()`;
2. ключ со стороны префикса на позиции `k` совпадает с ключом какой-либо реки узла **на той же позиции** `k`.

```cpp
bool absorb = fusedLeader && fusedRsb &&
    rsbs.getCount() == 1 && rsbs[0] == fusedRsb &&
    newRows < HashJoin::maxCapacity() &&
    fusedHashedRows + newRows < (FB_UINT64) HashJoin::maxCapacity() * 2 &&
    keys[0]->getCount() == fusedKeys[0]->getCount();

for (FB_SIZE_T k = 0; absorb && k < keys[0]->getCount(); k++)
{
    const auto field = (*keys[0])[k];
    bool found = false;

    for (FB_SIZE_T j = 0; j < fusedKeys.getCount(); j++)
    {
        if (field->sameAs((*fusedKeys[j])[k], false))
        {
            found = true;
            break;
        }
    }

    if (!found)
        absorb = false;
}
```

Проверка на сборке keyfix: все восемь случаев теста 65 и дополнительные запросы верны. S1, S4, S6, S7 остаются
слитыми; S2, S3, S5 идут цепочкой. После правки массив `fusedKeyFields` не нужен.

Смешанные типы ключей (int и bigint, разные длины строк) ошибку не дают: `getEquiJoinKeys` оборачивает ключ в
`CastNode`, такой ключ не совпадает с полем узла, и река не принимается (тест 64, H3).

## Замечания

- **W1. Нет теста на форму ключей.** В описании коммита проверены границы ёмкости (стенд `tst14star`), но не
  соединения по двум ключам. Тест 65 закрывает этот пробел.
- **W2. Узел без условия зависит от фильтра над рекой.** Сейчас это верно: фильтр проверяет равенства слитого узла.
  Любая правка, которая помечает эти равенства как использованные, сломает проверку коллизий хэша. В PR #35 это
  учтено при слиянии: равенства слитого узла остаются в фильтре.
- **W3. Отказ от слияния необратим до конца реки.** После одной неподходящей позиции новое слияние не начинается
  («no new fusion starts until the river ends»). Для порядка `A, B(2 ключа), C, D` звезда `C, D` уже не сольётся.
  Это потеря скорости, не ошибка.

## Что не проверено

- Границы ёмкости (4 млн строк на реку, 8 млн в сумме) и BHJ над слитой рекой.
- IMDB (CEB, job-light, scale) на сборке коммита: стенд dellg15 занят прогоном scale для PR #35.
- Внешние формы соединений из описания коммита проверены только одним случаем (`LEFT JOIN` над слитой рекой).

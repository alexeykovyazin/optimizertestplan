План: `PLAN-hash-aggregate-improvements.md`. База работ: ветка `v5.0-impr-opt`, коммит `e12e120dfd`.
Стенд: 531 запрос TPC-H, JCC-H (norm, skew), DSB (s1, s2); `TempCacheLimit` = 2000M.
Локальный микротест: 2 млн строк, лучшее из двух-трёх кругов.

   статистики полей, цена при неизвестном числе строк входа, оценка `UNION`.
4. **Стенд.** PR 60 и PR 61 дают выигрыш на стенде. PR 62 на стенде нейтрален в пределах шума: его шаги
   ускоряют формы запросов, которых в эталонных наборах мало.
5. **Не сделаны шаги 3.2–3.5 и этап 5.** Причины и оценка — в разделе «Что не сделано».

   шаг не даёт устойчивого замедления, разница до 10 %.

## Проверки

- **Результаты.** Шесть наборов запросов, каждый на шести настройках памяти (хеш выключен; по умолчанию; 16K и
  512K с `TempCacheLimit` = 0; 512M; 16K с `TempCacheLimit` = 4M): 44 запроса GROUP BY / DISTINCT, 42 с
  ключами-выражениями, 18 с `MIN`/`MAX` по строке, 22 с `UNION`, 17 с первичным ключом, 16 с соединениями.
  Отличий от пути через сортировку нет.
- **Одно видимое отличие поведения:** ошибка выражения в середине входа возникает до возврата первой группы
  (хеш-агрегирование сначала читает весь вход).
- **Возврат памяти временного кэша** проверен сборкой с журналом в 10 сценариях (прерванный `FIRST`, `EXISTS`,
  ошибки, сброс на диск, повторное выполнение): взято 736M, возвращено 736M.
- **Регрессионный набор** (68 тестов) после каждого шага: 5 известных падений (18, 19, 20, 45, 54). План
  меняется в одном тесте: в тесте 71 `MAX` по строке теперь идёт через Hash Aggregate.
- **Новые тесты 75–80** (`tests/`): по одному на шаг. Каждый случай сравнивает запрос с его вариантом через
  сортировку и печатает `diff 0`. Эталонные выводы: `tests/out_hash_75…80_*.txt`.

## Что не сделано

| Шаг | Что это | Почему не сделано | Что нужно |
|-----|---------|-------------------|-----------|
| 3.2 | Свёрнутая сторона hash join с `SUM`/`MIN`/`MAX` | Нужна операция слияния частичных состояний агрегатов; её у `AggNode` нет | Новый метод слияния для `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`; новый поток записей через Hash Join |
| 3.3 | Группировка в хеш-таблице соединения | Зависит от 3.2 | — |
| 3.4 | Группировка по батчам батчированного hash join | Зависит от общего разбиения на секции у двух методов | Одинаковые биты хеша у соединения и группировки |
| 3.5 | Ключ группировки в поиске порядка соединения | Меняет поиск порядка; нужен отдельный замер риска | Начать с частного случая: хешировать таблицу без ссылок (см. ниже) |
| 5 | `COUNT(DISTINCT)` с GROUP BY, `LIST` | В плане помечено «позже»; набор пар (ключ, значение) резидентной группы нельзя сбросить на диск в текущей схеме | Слияние состояний (как в 3.2) или жёсткая оценка памяти |

Наблюдение для 3.5. Шаг 3.1 даёт выигрыш, только когда таблица без ссылок оказывается на хешируемой стороне
соединения. Порядок соединения выбирается без учёта подсчёта. В локальном тесте из четырёх запросов в одном
оптимизатор хешировал другую сторону, и время не изменилось (1,15 с вместо возможных 0,2 с).

## Замечания к тестам 71 и 72

строке теперь идёт через хеш). Результаты запросов в них верны. Тесты нужно пересмотреть под текущие правила.

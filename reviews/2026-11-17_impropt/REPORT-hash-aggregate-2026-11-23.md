## Почему локальный выигрыш PR 62 не виден на стенде

Проверка 23.11.2026: планы и времена чередующегося прогона, состояние стенда под нагрузкой.

**Причина в данных запросов, не в стенде.** Новые методы в планах DSB s1 есть, но работать им не над чем.

| Изменение плана | Запросов из 63 | Время, база → новый | Почему нет выигрыша |
|-----------------|----------------|---------------------|---------------------|
| Hash Join со счётом строк | 33 (44 узла) | 45,5 → 46,1 с | Считаемая таблица: `DATE_DIM` (33 узла), `WEB_PAGE`, `ITEM` (по 5). Соединение идёт по уникальному ключу, счёт каждого ключа равен 1, строки не сворачиваются |
| Ключ группировки без зависимых столбцов | 20 | 41,5 → 42,4 с | Ключ короче (98 → 15 байт, 211 → 5 байт), но на вход группировки приходят сотни строк, а не миллионы |
| Hash Unique | 4 | 2,9 → 2,9 с | Мало строк |

- Оценка входа Hash Aggregate в планах: медиана 181 строка; больше 1 млн строк в 4 запросах из 59.
- Локальный микротест подаёт в группировку 2 млн строк (8 млн строк соединения) и сворачивает 100 строк на
  ключ. Выигрыш шагов растёт с числом строк на входе группировки. В DSB время уходит на чтение и соединение
  таблиц фактов.
- Локальный тест с формой DSB (считаемая сторона с уникальным ключом, 2 млн строк) тоже не даёт выигрыша:
  0,61 → 0,57 с.

**Стенд не тротлит.** Один запрос выполнен 40 раз подряд (85 с): 2,05–2,20 с в начале и в конце серии. Частота
занятого ядра всю серию 166–186 % от номинала (3,8–4,3 ГГц). Событий ограничения скорости процессора прошивкой
за 7 дней нет. Максимальное состояние процессора в схеме питания 100 %.

**Стенд не простаивает.** Фоновые процессы постоянно занимают около половины ядра: служба WMI, Defender,
Alienware Command Center, служба планшета, три агента HQbird; запущено семь экземпляров Firebird. Примерно раз в
минуту идёт всплеск на 3–5 ядер длиной несколько секунд. Запрос, попавший на всплеск, идёт на 10–40 % дольше
(2,34–2,53 с и 2,96 с вместо 2,1 с). Источник всплесков не установлен.

**Разрешение замера ниже измеряемой разницы.** Каждый запрос в круге выполняется один раз. Контроль на одном
движке: нечётные круги базы против чётных дают +5,2 % (52 запроса из 63 медленнее). Разница база → новый по
лучшему из четырёх кругов: +2,8 %; без первой пары кругов: +1,6 %. Вывод: ускорения PR 62 на DSB нет;
замедление до 3 % этим замером не подтверждено и не исключено.

Что нужно для замера точнее 3 %: три выполнения каждого запроса в круге с выбором лучшего; остановить фоновые
службы и лишние экземпляры Firebird на время прогона.

## Проверки

- **Результаты.** Шесть наборов запросов, каждый на шести настройках памяти (хеш выключен; по умолчанию; 16K и
  512K с `TempCacheLimit` = 0; 512M; 16K с `TempCacheLimit` = 4M): 44 запроса GROUP BY / DISTINCT, 42 с
  ключами-выражениями, 18 с `MIN`/`MAX` по строке, 22 с `UNION`, 17 с первичным ключом, 16 с соединениями.
  Отличий от пути через сортировку нет.
- **Одно видимое отличие поведения:** ошибка выражения в середине входа возникает до возврата первой группы
  (хеш-агрегирование сначала читает весь вход).
- **Возврат памяти временного кэша** проверен сборкой с журналом в 10 сценариях (прерванный `FIRST`, `EXISTS`,
  ошибки, сброс на диск, повторное выполнение): взято 736M, возвращено 736M.
- **Регрессионный набор** (68 тестов) после каждого шага: 5 известных падений (18, 19, 20, 45, 54). План
  меняется в одном тесте: в тесте 71 `MAX` по строке теперь идёт через Hash Aggregate.
- **Новые тесты 75–80** (`tests/`): по одному на шаг. Каждый случай сравнивает запрос с его вариантом через
  сортировку и печатает `diff 0`. Эталонные выводы: `tests/out_hash_75…80_*.txt`.

## Что не сделано

| Шаг | Что это | Почему не сделано | Что нужно |
|-----|---------|-------------------|-----------|
| 3.2 | Свёрнутая сторона hash join с `SUM`/`MIN`/`MAX` | Нужна операция слияния частичных состояний агрегатов; её у `AggNode` нет | Новый метод слияния для `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`; новый поток записей через Hash Join |
| 3.3 | Группировка в хеш-таблице соединения | Зависит от 3.2 | — |
| 3.4 | Группировка по батчам батчированного hash join | Зависит от общего разбиения на секции у двух методов | Одинаковые биты хеша у соединения и группировки |
| 3.5 | Ключ группировки в поиске порядка соединения | Меняет поиск порядка; нужен отдельный замер риска | Начать с частного случая: хешировать таблицу без ссылок (см. ниже) |
| 5 | `COUNT(DISTINCT)` с GROUP BY, `LIST` | В плане помечено «позже»; набор пар (ключ, значение) резидентной группы нельзя сбросить на диск в текущей схеме | Слияние состояний (как в 3.2) или жёсткая оценка памяти |

Наблюдение для 3.5. Шаг 3.1 даёт выигрыш, только когда таблица без ссылок оказывается на хешируемой стороне
соединения. Порядок соединения выбирается без учёта подсчёта. В локальном тесте из четырёх запросов в одном
оптимизатор хешировал другую сторону, и время не изменилось (1,15 с вместо возможных 0,2 с).

## Замечания к тестам 71 и 72

строке теперь идёт через хеш). Результаты запросов в них верны. Тесты нужно пересмотреть под текущие правила.

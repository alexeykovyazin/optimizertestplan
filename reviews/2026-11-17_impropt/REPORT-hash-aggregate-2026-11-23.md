## Почему локальный выигрыш PR 62 не виден на стенде

Проверка 23.11.2026: планы и времена чередующегося прогона, состояние стенда под нагрузкой.

**Причина в данных запросов, не в стенде.** Новые методы в планах DSB s1 есть, но работать им не над чем.

| Изменение плана | Запросов из 63 | Время, база → новый | Почему нет выигрыша |
|-----------------|----------------|---------------------|---------------------|
| Hash Join со счётом строк | 33 (44 узла) | 45,5 → 46,1 с | Считаемая таблица: `DATE_DIM` (33 узла), `WEB_PAGE`, `ITEM` (по 5). Соединение идёт по уникальному ключу, счёт каждого ключа равен 1, строки не сворачиваются |
| Ключ группировки без зависимых столбцов | 20 | 41,5 → 42,4 с | Ключ короче (98 → 15 байт, 211 → 5 байт), но на вход группировки приходят сотни строк, а не миллионы |
| Hash Unique | 4 | 2,9 → 2,9 с | Мало строк |

- Оценка входа Hash Aggregate в планах: медиана 181 строка; больше 1 млн строк в 4 запросах из 59.
- Локальный микротест подаёт в группировку 2 млн строк (8 млн строк соединения) и сворачивает 100 строк на
  ключ. Выигрыш шагов растёт с числом строк на входе группировки. В DSB время уходит на чтение и соединение
  таблиц фактов.
- Локальный тест с формой DSB (считаемая сторона с уникальным ключом, 2 млн строк) тоже не даёт выигрыша:
  0,61 → 0,57 с.

**Стенд не тротлит.** Один запрос выполнен 40 раз подряд (85 с): 2,05–2,20 с в начале и в конце серии. Частота
занятого ядра всю серию 166–186 % от номинала (3,8–4,3 ГГц). Событий ограничения скорости процессора прошивкой
за 7 дней нет. Максимальное состояние процессора в схеме питания 100 %.

**Стенд не простаивает.** Фоновые процессы постоянно занимают около половины ядра: служба WMI, Defender,
Alienware Command Center, служба планшета, три агента HQbird; запущено семь экземпляров Firebird. Примерно раз в
минуту идёт всплеск на 3–5 ядер длиной несколько секунд. Запрос, попавший на всплеск, идёт на 10–40 % дольше
(2,34–2,53 с и 2,96 с вместо 2,1 с). Источник всплесков не установлен.

**Разрешение замера ниже измеряемой разницы.** Каждый запрос в круге выполняется один раз. Контроль на одном
движке: нечётные круги базы против чётных дают +5,2 % (52 запроса из 63 медленнее). Разница база → новый по
лучшему из четырёх кругов: +2,8 %; без первой пары кругов: +1,6 %. Вывод: ускорения PR 62 на DSB нет;
замедление до 3 % этим замером не подтверждено и не исключено.

Что нужно для замера точнее 3 %: три выполнения каждого запроса в круге с выбором лучшего; остановить фоновые
службы и лишние экземпляры Firebird на время прогона.

Находки по ходу:

1. **Без расширенной статистики Hash Aggregate не выбирается.** В рабочей базе IMDb хранилище статистики
   старого формата (нет столбца `STAT$WEIGHTED_DEGREE`), `ALTER DATABASE REFRESH STATISTICS` на ней падает.
   Правило выбора требует число различных значений каждого столбца группировки; без него остаётся сортировка,
   и выбор не откладывается. Пример: `SELECT gender, COUNT(*) FROM name GROUP BY gender` (4,3 млн строк,
   3 группы) идёт через сортировку. На такой базе ни один из 90 запросов набора с GROUP BY не получил
   Hash Aggregate ни на одном движке. Кандидат на улучшение: откладывать выбор и при неизвестном числе
   различных значений.
2. **Ключ типа BLOB.** Шаблоны 9a, 9b, 10a (45 запросов) группируют по столбцам `info` типа BLOB и остаются на
   сортировке.

**Регрессия шага 3.1 (4.51).** Во всех 18 запросах один `MIN` без GROUP BY, и соединение под ним потеряло счёт
строк (`counted streams`, узел `Count`). Причина: агрегат с одним MIN или MAX до компиляции входа запрашивает
блок сортировки (путь через индекс), и правило счёта ему в этот момент отказывает. Оптимизатор убирает блок,
когда индекс не даёт порядок, и раньше правило спрашивалось повторно после компиляции. Шаг 3.1 стал
запоминать первый ответ.

**Исправление:** агрегат без GROUP BY спрашивает правило повторно; группировка держит первый ответ. Коммит
`b40359c034`, PR 63 (в него же вошли 10 коммитов PR 62: PR 62 был влит в ветку PR 61 уже после слияния PR 61,
и в PR 60 они не попали).

Проверки исправления:

- Планы job на стенде: исправленный движок даёт планы PR 61 во всех 113 запросах на обеих базах.
- Время 18 запросов (прогрев и замер, лучшее из двух кругов, результаты равны на всех кругах): PR 61 - 193,6 с;

- Регрессионный набор, 75 тестов, сравнение с выводами PR 62: 57 выводов равны; 16 отличаются только оценками
  выборочной статистики (выборка случайна); тест 81 отличается возвращёнными отметками; тесты 18 и 19 зависят

## Набор horses-fdb (закрытая база): два дефекта, исправлены

Новый набор: 8 запросов по закрытой базе horses (описание: `bench/datasets/horses/README.md`). Запрос 01 взят

1. **Дефект 1: внешнее хеш-соединение превратилось во вложенный цикл с полным чтением.** На сборке 18.11
   `COVER` (787 206 строк) читается один раз под `Hash Join (outer)`. На сборках с 21.11 стоит

   Ломается только вариант с оконной функцией внутри `LATERAL`; шесть других вариантов держат хеш-соединение.
2. **Дефект 2: Hash Aggregate в производной таблице, которая выполняется заново на каждую строку.** Раньше
   группировка шла по порядку индекса `FK_REGISTRATION_HORSE` без сортировки. Теперь стоит `Hash Aggregate`, и
   хеш-таблица создаётся 578 228 раз на 1-2 строки входа. Сборка от 22.11 до PR 58 даёт прежний план: дефект

   Проверка идёт после `rse->computable()`, когда потоки выборки производной таблицы уже не активны. Ссылка на

   потоки выборки активны на время проверки отображения. **Дефект есть и в `v5.0-release`.**
2. **Причины дефекта 2 — две.** (а) Хеш-таблица каждого открытия имела размер по оценке групп всей таблицы.

## Запрос 13: хеш-соединение внешних соединений в HQbird 5.0

**Причина.** В `v5.0-release` у внешнего соединения один метод — вложенный цикл. В запросе 13 (`CUSTOMER LEFT JOIN
ORDERS`) у `ORDERS` нет индекса по `O_CUSTKEY`, поэтому `ORDERS` (1,5 млн строк) читается целиком для каждого из
150 000 клиентов. Запрос не завершается за 600 с.

**Исправление.** [PR 71](https://github.com/IBSurgeon/hqbird/pull/71) переносит в `v5.0-release` заметку 4.11 ветки
оптимизатора (хеш-соединение внешних соединений, 8 коммитов). Отличия от ветки: доля совпадений ключей берётся
только равномерной (собранных статистик соединений в этой ветке нет); внутреннее хеш-соединение не меняется.
Второй коммит добавляет внешнему соединению свой предел: до 4 001 000 строк вместо 1 009 000, хеш-таблица растёт
с числом строк (1009, 2003 или 4001 корзина). Без него запрос 13 оставался на вложенном цикле: внутреннее
соединение сверх предела уходит в соединение слиянием, у внешнего такого метода нет. Третий коммит (замечание
рецензента: таблица всегда в памяти, цепочка таких соединений умножает её) делает предел бюджетом всего запроса:
строки сверх старого предела считаются по запросу, соединение сверх бюджета остаётся вложенным циклом. Первый
вариант предела был 16 001 000 строк на каждое соединение.

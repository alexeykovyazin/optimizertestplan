Критичные: неверный результат и остановка сервера

  • V1критичнотест

    Outer hash join берёт в своё условие чужие конъюнкты

    optimizer/OuterJoin.cpp:393–402 · 7426e92a7a

    Исправление M2 берёт в условие HJ все неиспользованные конъюнкты. В списке есть конъюнкты родителя: ON внешнего INNER JOIN и WHERE. Проверки «ссылается на внутренний поток» нет. Флаги USED уходят родителю (Optimizer.cpp:768), и родитель теряет своё условие join.

    oa left join ob on oa.x = ob.x join oc on oc.k = oa.x → no current record for fetch operation (верно 20 000). С and ob.y > oa.z → 400 000 000 / 20 000 (верно 20 000 / 9 000). f2888abf7c даёт верные числа.

    tests/31_oj_parent.sql — A1, A2
  • V2критичнотест

    ANY/ALL над LEFT JOIN: X и NOT X оба TRUE

    optimizer/OuterJoin.cpp:395–401 · 7426e92a7a

    Та же причина. Сравнение ANY/ALL (FLAG_RESIDUAL) ссылается только на внешний поток и попадает в условие HJ, а Filter для setAnyBoolean не строится. При oa.z = 10: 5 > all (…) → 1 (верно 0), not (5 > all …) → 1, 5 = any (…) → 1 (верно 0). f2888abf7c: 0, 1, 1, 0.

    tests/31_oj_parent.sql — B1–B4
  • V3критичнотест

    PREPARE запроса с LIKE '%_%' останавливает сервер

    extstat/StatisticsCache.cpp:1300–1338 · ab9730e98b

    Фрагмент, у которого все символы ушли на _, получает frag.fixed = 0. Тогда k = MIN(0u, 4u) − 1 = 0xFFFFFFFF, и SUBSTR_CHAR_SELECTIVITY[k] читается далеко за массивом. Access violation, сервер остановлен. Хватает SET PLANONLY. То же — '_%', '___', '%__%'. Исправление: пропускать фрагменты с fixed == 0, вычитать каждый _ из своего фрагмента.

    tests/32_like_crash.sql
  • V4критичнотест

    ORDER BY над BHJ теряет фильтры WHERE

    optimizer/InnerJoin.cpp:740–746, 871–876 · 91564c44db

    При BHJ и sortUtilized formRiver начинает заново. Первый проход пометил локальные конъюнкты CONJUNCT_USED, перезапуск эти флаги не сбрасывает. Второй проход строит потоки без фильтров. rc join rb … where rc.x < 600001 order by rc.x → 48 000 000 строк, max 800 000 (верно 36 000 000 и 600 000). Без ORDER BY — верно. GROUP BY по навигируемому ключу — тоже неверно.

    tests/33_sort_bhj.sql

Под этот фильтр в разделе ничего нет.

Низкие

  • REFRESH зависит от отладочной колонки STAT$LEN_BOUNDS_TEXT, которую обещают убрать до релиза (Collector.cpp:635–651).
  • LIKE '%' → 43 188 при 200 000. Якорь и escape не учитываются: '_a%' ×3.0, '%\_%' escape '\' → 49 940 при 0.
  • Диапазоны по тексту NONE — всё ещё 0.5: sn >= 'v5' → 50 000 при 11 000. Hex у VARCHAR NONE/OCTETS включает 2 байта длины.
  • Локальное равенство в ON становится ключом хэша и занижает долю совпадений; результат верный. Позиции с полом игнорируют join-оценку < 1 строки на пробу.
  • Уникальный путь берёт максимум выборки: часть «улучшений» 12_geq/13_hist — от выборки.
  • BHJ: 3 буфера на батч при сбросе (до 61 МБ при 64 батчах, P2 хуже); пропущенные батчи держат буферы до close; нет конечного состояния после EOF. Перезапуск formRiver оставляет потоки первого прохода активными [код].
  • TempCachePlanPercent вне границ → 80, а документация пишет «к границе». Устаревший комментарий tempSpillExpected. EXPLAIN печатает Window Buffer (rows=0.000000).

6Миграция хранилища STAT$ (V6, N1)

Сработало на стенде dellg15 без потери именованных структур. Хранилищу без STAT$SCALE нужен ещё ADD STAT$SCALE SMALLINT. REFRESH на dellg15 — около 73 с.

ALTER TABLE STAT$COLUMNS
  ADD STAT$LEN_COUNT BIGINT, ADD STAT$LEN_SUM BIGINT, ADD STAT$LEN_MIN INTEGER,
  ADD STAT$LEN_MAX INTEGER, ADD STAT$LEN_BOUNDS BLOB SUB_TYPE BINARY,
  ADD STAT$LEN_BOUNDS_TEXT BLOB SUB_TYPE TEXT CHARACTER SET UTF8;
COMMIT;
ALTER DATABASE REFRESH STATISTICS;

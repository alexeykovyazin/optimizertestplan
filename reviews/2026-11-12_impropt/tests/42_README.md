# Тест 42 — матрица вариантов Hash Join (outer)

Проверяет исправление W1 и все формы outer join, для которых строится `Hash Join (outer)`.

## Как устроен эталон

Каждый случай — один запрос в двух формах:

- **H** — ключи соединения записаны как `x = y` или `x is not distinct from y`. Оптимизатор сам выбирает
  Hash Join (outer) или вложенный цикл.
- **N** — те же ключи записаны диапазоном: `(x >= y and x <= y)`, а для INDF —
  `((x >= y and x <= y) or (x is null and y is null))`. Равенства нет, поэтому план всегда вложенный цикл.
  Это эталон. Он не зависит от `PLAN` и от индексов.

Для каждого случая скрипт печатает две строки:

- `<тег> H` — форма H отдельно. По её `EXPLAIN` видно, какой метод выбран.
- `<тег>` — `PASS` или `FAIL`: формы H и N сравниваются в одном запросе по `count(*)`,
  по числу совпавших строк и по контрольной сумме id соединённых строк.

`42_check.sh` дополнительно сверяет план формы H с `42_expected.txt`: число узлов `Hash Join (outer)`
и число узлов outer join (0 — соединение стало внутренним). `-` — любое значение.
Расхождение плана — не ошибка результата. Оно показывает, что оптимизатор выбрал другой метод.
На штатном сервере Hash Join (outer) нет, поэтому там почти все планы отличаются — это нормально.

## Данные

- `ta` (300 строк, внешняя сторона): `k` = 0..59, NULL у каждой 11-й строки; `k2` = 0..6 с NULL.
- `tb` (300 строк, внутренняя сторона, без индексов): `k` = 10..74 с NULL. Значения 0..9 есть только
  в `ta`, значения 60..74 — только в `tb`. Ключи повторяются (соединение «многие ко многим»).
- `tbi` — копия `tb` с индексом по `k`; `tc` (100 строк) — третья таблица; `tt` (10 строк) — для подзапросов.
- `te` — пустая; `tu`, `tup` — уникальный ключ без индекса и с первичным ключом; `tw` — запись длиннее 64 КБ;
  `gtb` — временная таблица.
- Колонки `tb` с другими типами ключа: `bigint`, `numeric(9,2)`, `char(10)`, `unicode_ci`, `timestamp`, BLOB.
- Представления `v_a`, `v_b`, `v_ab` (с outer join внутри), процедуры `sp_a`, `sp_b`.

## Правила, которые проверяют группы E и H

- Внутренняя (необязательная) сторона — табличное выражение → всегда вложенный цикл (`hj=0`).
- Внешняя сторона — табличное выражение, внутренняя — таблица → Hash Join разрешён (`hj=1`).
- Внутренняя сторона — табличное выражение, `WHERE` отбрасывает её NULL-строки → соединение остаётся
  внешним (`outer=1`). Если внутренняя сторона — таблица, оно становится внутренним (`outer=0`).

## Найдено этим тестом

- **X1 (исправлено).** `HashJoin::isDependent` не учитывал условие хэш-соединения. LATERAL-производная
  таблица с Hash Join (outer), у которого ON ссылается на таблицу слева, и условие обратного соединения
  по индексу этой таблицы:
  ```sql
  select count(*) from tup p
    cross join lateral (select a.id, b.id as bid from ta a
                        left join tb b on a.k = b.k and b.y > p.k) x
  where p.id = x.id;
  ```
  06041718cc — `no current record for fetch operation`; a3cfa97218 — 90 063 строки при 363.

## Наблюдения (не ошибки результата, не исправлялись)

- `where b.id is not null` не запускает OuterJoinConversion (случай D04). На штатном сервере так же.
  Сравнение (`b.id > 0`) запускает.
- FULL JOIN, у которого одна сторона — табличное выражение, выполняется двумя вложенными циклами (E22).
  Вероятная причина (по коду, не проверено отладкой): поток-река в FULL-соединении не активен при поиске ключей.
- Равенство колонки внутренней стороны с константой или со ссылкой на внешний запрос (`b.k2 = 1`,
  `b.k2 = p.k`) становится ключом хэша (C03). Результат верный.
- ON с константой FALSE (`1 = 0`) всё равно строит Hash Join (B19). Результат верный.
